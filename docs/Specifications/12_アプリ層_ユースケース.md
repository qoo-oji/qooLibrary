## 12.0 合成根 `LibraryServices` [A-01][A-02][ST-01]

**`QooPersistence`（DB）と `QooInfrastructure`（走査・監視）の両方に依存して
よい唯一の層がアプリケーション層**なので、接続を開き・リポジトリを組み立て・
スキャンを配線する仕事をここ 1 箇所に集める。UI 層は `LibraryServices.shared`
だけを見て、GRDB もリポジトリの実装型も知らない。

```swift
@MainActor @Observable
public final class LibraryServices {
    public static let shared: LibraryServices

    public private(set) var libraries: [LibrarySummary]
    public private(set) var presetTemplates: [LibraryTypeTemplate]
    public private(set) var startupFailure: StoreStartupFailure?
    public var isReady: Bool

    public func bootstrap(storeURL: URL? = nil) async
    public func library(registrationUUID: UUID) -> LibrarySummary?
    public func isEnabled(registrationUUID: UUID) -> Bool
    public func enable(registrationUUID:displayName:url:bookmarkData:template:) async throws -> LibraryID
    public func disable(registrationUUID: UUID, keepLabels: Bool) async throws
    public func scan(libraryID:mode:root:onProgress:) async throws -> ScanSummary
}
```

|---|---|
| LS-01 | 起動時に `bootstrap()` を 1 度だけ呼ぶ。何度呼んでも 1 回しか効かない |

### 登録フォルダとライブラリは別物 [設計判断、ユーザー判断]

フェーズ 1 の登録フォルダ（`registeredFolders.json`）は**ライブラリタイプの
概念を持たない**。起動時に全件へ既定の型を当てて自動生成すると、**推測した型で
実蔵書数千件をいきなり走査する**ことになる。1 件ずつ明示的に有効化させれば、
使い捨てのボリュームで先に試してから実蔵書へ当てられる。

入口はフォルダツリーの登録ルート行のコンテキストメニュー。出し分けは
`LibraryMenuVisibility` が値として返す（View の条件式に埋めない——テストで
固定できないため）。

| 状態 | 出す項目 |
|---|---|
| 未有効・オンライン | ライブラリとして有効にする… |
| 未有効・オフライン | （なし。`resolvedPath`/`volumeUUID` を実測できない）|
| 有効・オンライン | 今すぐ再スキャン／ライブラリ機能を無効にする |
| 有効・オフライン | **ライブラリ機能を無効にする**（再スキャンは出さない）|

**縮退した登録は `DegradedRegisteredFolderRow` という別の行型で描かれ、
通常のコンテキストメニューを通らない。** 登録ルート行に項目を足すときは
**必ず両方の行型に配線すること**。

### 走査結果の提示 [ER-01][ER-11][IF-05]

**注意が要るときだけ出す**［ユーザー判断］。孤立 > 0 [ID-06]・未解決 > 0
[AL-31]・1 冊扱いの解除 [IF-05] のいずれかがあるときにシート（強度 2）で知らせ、
何も無ければ黙る。「今すぐ再スキャン」は日常的に走らせる操作なので、変化が
無いのに毎回出すと**本当に見てほしいときの 1 枚まで読み飛ばされる**。

成功そのものの要約は `ScanEngine` が診断ログへ書く。**強度 4（一時通知）は
提示先が無くログだけになる**ため使わない。

### 登録解除はライブラリ行も消す [RG-06]

登録だけ解除するとライブラリ行とファイルのレコードが DB に取り残され、誰も
片付けられない（同じフォルダを再登録すると新しい UUID で 2 件目ができ、古い行が
永久に残る）。**完全削除による強制解除（`DeletePermanentlyCommand`）も同様。**

`LibraryRepository.unregister` は `keepLabels` をまだ見ずに連鎖削除するので、
**フォルダツリーからの登録解除では「ラベル・評価が失われる」確認を挟む**。
ラベル保管庫（2-11）が入ったら「保持する／破棄する」の選択へ変える。
完全削除の経路では確認しない——実体が既に消えており、それを指すラベルは
意味を持たないため。

## 12.4 ライブラリへの移動 [12.4 節]

**2 フェーズ実行**: ① 解析フェーズ → ② 実行フェーズ [MV-13]。

```swift
public struct MoveToLibraryUseCase: Sendable {
    public struct Plan: Sendable {
        public var movable: [MoveEntry]      // 移動先が確定したもの
        public var pending: [PendingEntry]   // ペンディング [MV-14]

public struct PendingEntry: Sendable, Identifiable {
    public let id: UUID
    public let sourceURL: URL
    public var filename: String
    public let reason: PendingReason         // [MV-19]
    public var parsedFields: [FieldRef: String]   // 抽出できたもの。できなかったものは欠落
    public var resolvedDestination: String?  // 判定できた場合のみ
    public var state: State                  // .pending / .resolved
}

public enum PendingReason: String, Sendable, Codable {
    case formatMismatch        // (a) どのフォーマットにも一致しない [MV-14a]
    case libraryTypeMismatch   // (b) @librarytype の値が不一致       [MV-14b][RW-01]
    case missingHierarchyValue // (c) 階層割り当てに必要な値が欠落     [MV-14c]
```

```pseudo
analyze(files, library):
    settings = snapshot(library)
    for url in files:
        parsed = FilenameParser.parse(basename(url), settings, .moveToLibrary)
        if parsed == nil:
            # ライブラリタイプ不一致が原因かを切り分ける [MV-14a][MV-14b]
            loose = FilenameParser.parse(basename(url), settings, .libraryScan)
            reason = (loose != nil && loose.libraryTypeMismatch)
                     ? .libraryTypeMismatch : .formatMismatch
            pending.append(PendingEntry(url, reason, loose?.fields ?? [:]))
            continue

        dest = library.root
        for (level, mapping) in settings.folderLevelMappings.sorted(by: level):
            value = valueForLevel(mapping, parsed)
            if value == nil:
                pending.append(PendingEntry(url, .missingHierarchyValue, parsed.fields))  # [MV-14c]
                continue outer
            dest = dest / sanitize(value)
        # 階層割り当てがなければライブラリ直下 [MV-05]
        movable.append(MoveEntry(url, dest))
        if !exists(dest): foldersToCreate.insert(dest)          # [MV-04]
```

## 12.6 重複ファイル [14.3.1 節]

> **実装済み（2026-08、2-18）。** 判定キーと代表・残す 1 件の決定は
> `QooKit` の `DuplicateGrouping` / `DuplicateGroupKey` / `DuplicateSelection`
> （すべて純粋関数）。グループ化そのものは**SQL の窓関数**が行う
> （`SQLiteManagedFileRepository.groupedSubquery`）——正規化済みタイトルを
> `managedFile.titleKey`（v6 で追加、再生成可能）へ書いておき、モードで
> `PARTITION BY` を切り替える。**モードの変更に再スキャンは要らない。**
>
> **下の擬似コードの `groupKey` は「1 つの文字列を作る」形だが、実装はそう
> していない**——SQL 側で組み立てるため、正規化済みタイトルと巻数の 2 列を
> そのまま区画に使う。`DuplicateGroupKey.make` は同じ規則を 1 つの文字列で
> 表した**テスト・診断用**の表現で、両者が一致することを
> `DuplicateGroupingQueryTests` が固定している。
>
> **`nil` の扱いが要点**: タイトルを取れなかったファイルは**組を作らない**。
> SQLite の `PARTITION BY` は NULL どうしを同じ区画と見なすので、素の
> `titleKey` で区切ると**未解決ファイル [AL-30] が全部 1 組に畳まれ、
> 1 行を残して画面から消える**。問い合わせは `titleKey IS NOT NULL` の枝と
> そうでない枝に分けてあり、不変条件が式の細工ではなく**問い合わせの形**で
> 表されている。
>
> 比較・削除の UI と決定事項は 15章 §15.14。
