## 9.2 文字化け対策 [AR-02〜AR-04]

対象は zip / 7z のみ。RAR はアーカイブ側がエンコーディング情報を持つため対象外 [AR-03][C-06]。

```swift
public enum ArchiveNameEncodingHeuristic {
    public struct Candidate: Sendable {
        public let encoding: String.Encoding      // .utf8 / .shiftJIS (CP932)
        public let score: Double                  // 0.0〜1.0
        public let decodedSamples: [String]
    }
    /// UTF-8 フラグ未設定時の推定 [AR-02]
    public static func evaluate(rawNames: [Data]) -> [Candidate]
}
```

```pseudo
evaluate(rawNames):
    # ① UTF-8 として妥当にデコードできるか
    utf8Score = 妥当にデコードできた件数 / 全件
              - (U+FFFD や制御文字の出現率 × ペナルティ)
    # ② CP932 としてデコードした結果の妥当性
    cp932Score = デコード成功率
               + (日本語文字クラス〔ひらがな・カタカナ・CJK〕の出現率 × ボーナス)
               - (機種依存の未定義領域の出現率 × ペナルティ)
    # ③ よくある化けパターン（"ﾁ" "�" "?" の連続、Latin-1 由来のモジバケ）を減点
    return [utf8, cp932].sorted(byScoreDesc)
```

### ステージング [EX-01〜EX-04]

```swift
public struct ExtractOptions: Sendable {
    public var destination: URL
    public var encoding: String.Encoding?
    public var followSymlinks: Bool = false          // [EX-12]
    public var limits: ExtractLimits = .default      // [EX-21]
}

public struct ExtractResult: Sendable {
    public let extractedCount: Int
    public let rejected: [(entry: String, reason: RejectionReason)]  // [EX-14]
    public let renamedForCaseCollision: [(from: String, to: String)] // [EX-15]
    public let totalBytesWritten: Int64
}
```

```pseudo
extract(archive, options):
    staging = appContainer/staging/<uuid>/          # [EX-01][EX-03]
    defer { removeRecursively(staging) }

    # 事前チェック [EX-23]
    declared = 宣言された非圧縮サイズの合計
    if freeSpace(options.destination) < declared + AppLimits.freeSpaceMargin:
        throw .insufficientFreeSpace

    written = 0; entryCount = 0
    for entry in archive.entries:
        entryCount += 1
        if entryCount > limits.maxEntries: throw .tooManyEntries        # [EX-21]

        # ── パストラバーサル対策 ──
        name = normalize(entry.pathname)
        if name.isEmpty                       : reject(.emptyName)      # [EX-10]
        if name.hasPrefix("/")                : reject(.absolutePath)
        if name.components.contains("..")     : reject(.parentTraversal)
        if name.containsNULOrControlChars     : reject(.invalidCharacters)
        if entry.isSymlink and !followSymlinks: reject(.symlinkSkipped)  # [EX-12]
        if entry.isHardlink || isDevice || isFIFO: reject(.specialEntry) # [EX-13]

        target = (staging / name).standardizedFileURL.resolvingSymlinksInPath()
        if !target.path.hasPrefix(staging.resolved.path + "/"):
            reject(.escapesDestination)                                  # [EX-11]

        # 大文字小文字のみ異なるエントリの衝突 [EX-15]
        if caseInsensitiveSeen.contains(target.lowercased):
            target = nextAvailableName(target); record(renamed)

        # ── 展開爆弾対策 ──
        stream = entry.dataStream
        while chunk = stream.next():
            written += chunk.count
            if written > limits.maxUncompressedBytes: throw .expansionLimitExceeded  # [EX-20][EX-21]
            ratio = Double(written) / Double(archive.compressedSize)
            if ratio > limits.ratioAbort:  throw .compressionRatioExceeded
            if ratio > limits.ratioWarn:   warnOnce()
            write(chunk, to: target)
        if Task.isCancelled: throw CancellationError()                   # [EX-24]

    # 最終位置へ移送。FileOperationService 経由 + 台帳登録 [EX-04]
    try await fileOps.promoteFromStaging(staging, to: options.destination)
```

| EXI-02 | 上限は環境設定で変更できる。中断時は理由と該当する上限を明示する [EX-22] |

**実装状況（1-12 環境設定「圧縮／展開」タブ）**: 圧縮形式（zip/7z）・zip の圧縮レベル・7z のコーデック（PPMd/bzip2/deflate/copy）・zip の暗号化方式（なし/Traditional/AES-128/AES-256）は環境設定の既定値として設定可能にした。AR-11「圧縮…」ダイアログは環境設定の既定形式に従うのみで、**操作のたびに形式を選び直す UI は未実装**（この表の「ファイル名・形式・保存先を指定する」の「形式」部分は環境設定側の既定を使う設計に簡略化している）。7z は libarchive の書き込み側に暗号化オプションが存在しないため、暗号化は zip 選択時のみ有効。パスワード文字列自体は環境設定に保存せず、暗号化が有効なときは圧縮のたびに `ArchivePasswordSheet` で入力させる。展開の安全上限（`ExtractLimits`）も同タブで調整可能。詳細は CLAUDE.md 参照。

### 圧縮エントリ名の Unicode 正規化 [設計判断][AR-10][AR-11]

macOS の Foundation API（`FileManager`/`URL`）はファイル名を NFD（濁点・半濁点等が
結合文字に分解された形）で返すことが多い。これをそのまま zip のエントリ名として
書き込むと、NFC を前提とする Windows 側の展開ツールで文字化けしたり、見た目は同じ
なのにバイト列が異なる別名として扱われたりする（Mac 製 zip アーカイバでよく知られた
問題）。**圧縮時は各エントリ名を NFC 正規化してから書き込み、UTF-8 フラグも明示的に
立てる**（Keka 等と同じ方式、EN-01 参照）。N-01〜N-03 のラベル照合用正規化
（`TextNormalizer`、3章）とは目的も適用箇所も別物で、両者を混同しない。

#### 実装（2-10 の第 3 段、2026-08）

**①②③ の判定は `CoverEditorModel`（`QooApplication`）が 1 箇所で持つ。**
出どころが DB（①）・実体（②）・`ThumbnailService`（③）と分かれているので、
判定を View に散らすと「いま何が出ているのか」を誰も答えられなくなる。
モデルが返すのは**表示に使う URL 1 つ**で、生成とキャッシュは従来どおり
`ThumbnailService` が担う——①②の複製・サイドカーはどちらも素の画像ファイル
なので、既存の経路にそのまま乗る（サムネイル非表示トグル [DS-06] も無償で効く）。

| 段 | 出どころ | DB に書くか |
|---|---|---|
| ① ユーザー指定 | `UserCoverStore` の複製（`usercovers/<libraryUUID>/<uuid>.<ext>`）| **書く**（`coverImageSource` / `coverImageRef`）|
| ② サイドカー | `covers/<同名>.<画像拡張子>` | **書かない**（下記）|
| ③ 先頭画像 | `CoverImageSourceResolver` | — |

**②を DB に書かない。** 疑似コードも②で DB を見ずに実体を探している。保存すると、
あとから `covers/` に画像を置いた・消したときに DB が古いまま残り、画面と実体が
食い違う。名前の突き合わせは**拡張子を除いた名前**で行い、完全一致を優先し、
無ければ大小文字を無視して探す（ボリュームが大小文字を区別するかは `covers` を
作った人ではなくファイルシステムの都合。見つからないより見つけすぎるほうが害が
小さく、誤って拾っても「既定に戻す」[CV-07] で外せる）。

**①の複製は「捨ててはいけない」保管領域**なので、`CoverImageCache`（`covers/v2/`）
とはディレクトリを分ける——同じ場所に置くと `prune` [IV-09] と「キャッシュを
空にする」が巻き添えで消し、元画像が既に無ければ CV-08 に反して二度と戻らない。

#### カバーに使うページを選ぶ [CV-05][TH-06]

`ArchiveCoverPicker`（`QooInfrastructure`）が候補の一覧と 1 件ずつの読み出しを持つ。
`CoverImageSourceResolver`（先頭 1 枚だけを解決する）とは目的も費用の性質も違うので
型を分けてある——混ぜると、サムネイル生成の経路が誤って全エントリを読む形へ育ちうる。

- **読み出しは 1 本に直列化し、後から要求されたものを先に処理する** [TH-02]。
  一覧のセルは可視範囲だけが生成される（`LazyVGrid`）ので、素直に書くと十数件が
  同時に読み出しを始める。zip は安いが、**solid 圧縮の 7z / RAR は N 件目を
  取り出すのに 1〜N 件目を復号する**ため、同時に走らせると費用が積の形で効く。
- 一覧の上限は `AppLimits.Thumbnail.defaultCoverPickerCandidates`（500）。

**実測（zip、この開発機、2026-08）**: 250KB × 100 エントリ（圧縮しづらい中身、
25MB）で `listEntries` **13.3 ms**、`readEntry` × 100 が **56.6 ms（0.57 ms/件）**。
libarchive は seekable な zip を先頭から読み直さないので、素直に 1 件ずつ読んでよい。
→ **可視セルごとの遅延読み込みで足りる**（一覧を開いた瞬間に全件を復号しない）。

> **測り直すときは圧縮しづらい中身を使うこと。** 単色 PNG は 100 枚で 71KB まで
> 縮み、走査の費用がまったく出ない（最初にそれで測って 1 桁見誤りかけた）。

> **フォルダに対する限界.** フォルダの更新日時は直下の項目の増減・改名でしか
> 動かないため、孫以下の画像を差し替えただけではカバーが古いままになり得る。
> `QuickLookCoverStore` も同じ前提。完全な追随は Phase 2 のカバー解決
> （ユーザー指定・サイドカー）を実装するときに改めて検討する。

| DS2-06 | 右ペインのカバー表示 [CV-01] と Quick Look の**独自カバー** [QL-03] も同じトグルに従う [DS-06] |
| DS2-07 | 現在の状態と、非表示になっている理由をステータスバーに示す [DS-07] |

**実効値の合成 [設計判断、ユーザー確認済み]**: 要件 DS-04 の文言は「ライブラリごとに
既定値を持てる」だが、**「入った時点で全体トグルの値を書き換える」形にはしない**
——全体トグルは DS-03 によりアプリ全体で共有される状態なので、あるウインドウが
ライブラリへ移動しただけで**他のウインドウの表示まで巻き添えで変わる**。
代わりに全体トグルとは独立した制約として持ち、

```
実効値（そのウインドウで隠すか） = 全体トグルが非表示 || 今いる登録フォルダが強制非表示
```

と合成する。要件が挙げる運用（「特定のライブラリだけ常に非表示にする」）はこれで
素直に満たせる。**合成に必要な「今どの登録フォルダの中にいるか」を知っているのは
UI 層だけ**（`NavigationRoot`、14章）なので、判定は UI 層に置き、
`ThumbnailService` が持つのは全体トグルの関門だけにする。

**DS2-07 の見せ方**: ステータスバーに常設のトグルボタンを置き、非表示のときだけ
強調する。ライブラリ側の強制非表示が効いている間は、全体トグルを反転しても
そのウインドウの見た目は変わらないためボタンを無効化し、ツールチップで
どのフォルダの設定によるものかを示す [ユーザー判断]。

**ネットワークボリュームとの関係（1-16b）**: サムネイル生成は**ファイル本体を
丸ごと読む**ため、ネットワークボリュームでは I/O 増幅の最大の発生源になる
（8章 NV-37）。File Provider 系クラウド（`~/Library/CloudStorage/`）では、
一括生成が**ユーザのストレージを全件ダウンロードさせる**（NV-73）。DS-04 の
「登録フォルダごとの強制非表示」はこの縮退の器としてそのまま使えるが、
**ネットワークボリュームで既定を非表示にすべきか、`AppLimits.Thumbnail.maxConcurrent`
をネットワークでは下げるべきか（NV-38）は 1-16b で決める。** →  8章 §8.11

### バックグラウンド動画サムネイル生成 [ユーザー要望、要件定義書には無い]

登録済みライブラリ／テンポラリフォルダ配下（サブフォルダを含む）の**動画**の
サムネイルを、アプリ起動中にバックグラウンドで先回り生成する
（`BackgroundThumbnailWarmer`）。生成そのものは `ThumbnailService` に委ねる
（同時実行スロット [PF-11]・動画のタイムアウト・キャッシュの鍵 [TH-08] が
そのまま効く）ため、掃引側が持つのは「何を・いつ・どの順で頼むか」だけ。

| 決めごと | 内容 |
|---|---|
| 実行時機 | **アプリ起動中のみ**。常駐ヘルパー（launchd エージェント等）は作らない [設計判断、ユーザー確認済み: app-scope の Security-Scoped Bookmark は作成したアプリ本体しか解決できず、別プロセスに持たせると権限管理が二重になる。起動直後に掃引を始めれば次回以降は差分だけになるため、終了中生成の利点はほぼ得られる] |
| 掃引の合図 | 起動時・登録フォルダの増減や DS-04 の切替等（`RegisteredFolderIndex.refresh()` に集約）・全体トグルの再表示（`ThumbnailVisibility.onGlobalVisibilityChanged`）・環境設定での有効化。合図は短く待ち合わせて 1 回にまとめる |
| 優先度 | 逐次 1 本（スロット 4 本のうち最大 1 本）＋ `.background`。UI のオンデマンド要求が常に勝つ |
| 形式単位のスキップ | 同じ拡張子が 1 度も成功しないまま 3 回失敗したら、そのセッションでは以降スキップ。**意図的に永続化しない** — QuickLook 拡張の有無を列挙する公開 API は無く、「次回起動時に再試行」が「対応する拡張をインストールしたら自動的に生成される」を検知コードなしで満たす最も堅い方法のため |
| 対象外 | ネットワークボリューム上の登録フォルダ [NV-37]・dataless なファイル [NV-73]・DS-04 強制非表示のフォルダ・全体トグル非表示中 [DS-05] |
| 無効化 | 環境設定「キャッシュ」タブのトグル（既定は有効）[ユーザー要望] |

### 動画サムネイルが作れない 2 つの理由と、その回避 [ユーザー報告、要件定義書には無い]

ユーザーのライブラリ（動画 79 本）で 3 本だけサムネイルが出ない事象を実測で
切り分けた結果、**原因は 2 つあり、どちらもファイルの中身側**だった。
いずれも `QLThumbnailErrorDomain code 102` を **0.02〜0.04 秒で即座に**返す
——タイムアウト・サンドボックス権限・形式スキップのいずれでもない。

| # | 実体 | なぜ失敗するか | 回避 |
|---|---|---|---|
| ① | mp4 / HEVC の **`hev1`** タグ（1 本） | AVFoundation は `hvc1` しか復号しない。`hev1` は仕様上正当だが Apple のメディアスタック全体で非対応（`decodable=false`）| `RetaggedHEVCThumbnailLoader` |
| ② | **実体は Matroska、拡張子だけ `.mp4`**（2 本） | UTI は拡張子から決まるので mp4 パーサへ渡る。mkv を扱える拡張が呼ばれることすら無い | `MediaContainerSniffer` ＋ `Request.contentType` |

**どちらも元ファイルを 1 バイトも書き換えずに回避できる。**

#### ② 型を宣言し直す

`QLThumbnailGenerator.Request` には **`contentType: UTType?`**（macOS 11+）が
あり、拡張子より優先される。先頭 16 バイトで実体のコンテナを見分け、拡張子と
食い違うときだけ宣言し直す。

| 渡した型 | 結果（`.mp4` を名乗る Matroska に対して）|
|---|---|
| なし（拡張子任せ）| FAIL 102 |
| `UTType(filenameExtension: "mkv")` | **OK** |
| `public.movie`（汎用の上位型）| FAIL 102 |

- **型の識別子を決め打ちしてはいけない。** `.mkv` の UTI は
  インストール済みアプリ次第で、この開発機では Infuse が宣言した
  `com.firecore.fileformat.mkv` に解決され、`org.matroska.mkv` は
  **存在しなかった**。必ず `UTType(filenameExtension:)` でシステムに尋ねる。
- **汎用の上位型では通らない。** 拡張が実際に登録した具体型でなければならない。
- **副産物としてアスペクト比の補正も正しくなった。** 以前は補正の対象を
  *拡張子で*ゲートしていたため（8MB のヘッダ読みを避けるための節約）、
  拡張子違いの mkv は正方形のままだった。マジックバイト判定に置き換えると、
  同じ 16 バイトの読み取りが「型の差し替え」と「ゲート」を兼ねる。

#### ① タグを付け直して自前でデコードする

**「復号できない」のではなく「タグを見て入口で断られている」だけ**だった
——該当ファイルの `hvcC` には VPS/SPS/PPS が揃っており（実測: array 3 本、
nal_type 32/33/34）、ファイルは自己記述的である。

1. `AVAssetReaderTrackOutput(track:, outputSettings: nil)`（パススルー＝
   デコードしない）でキーフレームを取る。**`decodable=false` のトラックでも
   読める。**
2. 元の format description の extensions（`hvcC` を含む）をそのまま流用し、
   subtype だけ `kCMVideoCodecType_HEVC`（= `hvc1`）で作り直す。
3. 同じデータバッファに新しい description を付けた `CMSampleBuffer` を組む。
4. `VTDecompressionSession` へ渡す。**VideoToolbox は受け付ける。**

`CompositeVideoThumbnailLoader` が **QuickLook → 再タグ付け**の順に試す
（QuickLook が作れるものを最小限の代替経路で置き換えないため）。対象は
実測で確かめた `hev1` のみ——Dolby Vision の `dvhe` も同型の関係にあるが、
検証できるファイルを持たないため入れていない。

**この問題は稀ではない。** ffmpeg は libx265 の mp4 出力に**既定で `hev1` を
付ける**ので、動画ライブラリとしては継続的に踏む。

#### 実測して駄目だったもの（同じ道を再訪しないために）

| 試したこと | 結果 |
|---|---|
| シンボリックリンクで拡張子を付け替える | **駄目。** QuickLook は実体パスまで解決してそちらの拡張子で判定する（既知の良品 mkv がリンク経由で成功する対照で切り分け済み）|
| `AVURLAssetOverrideMIMETypeKey` で Matroska と宣言 | **駄目。** AVFoundation 自体が Matroska を読めない（実 mkv でも `-11828`）。サムネイル拡張の mkv 対応は **QuickLook 経由でしか効かず AVFoundation には及ばない**——Media Extensions の format reader を入れれば話は変わるが、それは第三者拡張のインストールであってアプリ側の対応ではない |
| `contentType` で `hev1` を救う | 駄目。型判定は正しく、断っているのはデコーダ側 |

#### ファイル側の修復（実装とは独立、**ユーザー判断で今は行わない**）

- ① は **4 バイトの書き換え**で足りる（`hev1`→`hvc1`）。`hvcC` が揃っている
  ため 3.8GB の再多重化も ffmpeg も不要。`ffmpeg -c copy -tag:v hvc1` が
  やっているのも実質これ。
- ② は拡張子を `.mkv` に直すだけ。
- どちらも実データの改変なので、**明示的な指示があるまで行わない**。

## 9.9 埋め込みメタデータの読み取り [8.11 節][EM-01〜EM-63]

ファイル自身が持つメタデータから著者・タイトル・シリーズ・巻数を読み、
**ファイル名・フォルダ名から抽出した値より優先する** [EM-03]。

### 層の分担

**解析は `QooKit`、取り出しは `QooInfrastructure`** に分ける [A-01]。

| 層 | 型 | 役割 |
|---|---|---|
| `QooKit/Metadata/` | `EmbeddedMetadata` | 読み取り結果の値型。4 つのフィールドと出どころを持つ |
| | `ComicInfoParser` | XML のバイト列 → `EmbeddedMetadata`。**純粋関数** |
| | `OPFMetadataParser` | OPF のバイト列 → `EmbeddedMetadata`。**純粋関数** |
| | `XMPMetadataParser` | XMP のバイト列 → `EmbeddedMetadata`。**純粋関数** |
| | `EmbeddedMetadataMerge` | パース結果への優先適用（§4.10.1） |
| `QooInfrastructure/FileOps/Metadata/` | `EmbeddedMetadataReader` | URL → `EmbeddedMetadata`。容器を見分け、該当するバイト列を取り出して上のパーサへ渡す |
| | `PDFMetadataExtractor` | CoreGraphics で情報辞書と XMP ストリームを取り出す |

**バイト列とパースを分けるのが要点。**パーサは実ファイルに触らないので、
ゴールデンテストが標本の XML を直接与えて固定できる。読み取り側は「どのエントリを
取り出すか」だけを持ち、形式ごとの解釈を持たない。


### 容器ごとの取り出し

| 容器 | 取り出すもの | 経路 |
|---|---|---|
| `zip` / `cbz` / `rar` / `cbr` / `7z` / `cb7` | ルート直下、または単一のトップレベルフォルダ直下の `ComicInfo.xml` [EM-20] | `ArchiveReading.listEntries` → `readEntry` |
| ブックフォルダ | 直下の `ComicInfo.xml` | `FileManager` の読み取り |
| `epub` | `META-INF/container.xml` → OPF の `<metadata>` [EM-40] | `ArchiveReading`（`EpubCoverResolver` と同じ経路） |
| `pdf` | 文書カタログの `/Metadata`（XMP）と `/Info`（情報辞書）[EM-50] | `CGPDFDocument` |

**`ComicInfo.xml` の照合は大文字小文字を無視する** [EM-21]。仕様は
`ComicInfo.xml` を要求するが、小文字で書き出すツールが実在する——
「機械が人間に合わせる」（CLAUDE.md 冒頭の大原則）に従い、完全一致を優先しつつ
大文字小文字違いも拾う。

**「単一のトップレベルフォルダ直下」まで見る**のは、`作品名/ComicInfo.xml` という
構造が実際に多いため。トップレベルの項目が 2 つ以上ある場合は、どれが本体か決められない
ので**ルート直下しか見ない**——複数巻をまとめたアーカイブで誤った巻数を拾うより、
読まないほうが害が小さい。

### PDF は CoreGraphics だけで完結する [実測]

追加の依存（PDFKit 等）は要らない。使い捨てのプローブで、**手で組み立てた最小 PDF**
に対して次を確認した:

| 確認したこと | 結果 |
|---|---|
| 情報辞書の UTF-16BE 文字列（日本語）| `CGPDFStringCopyTextString` が正しくデコードする |
| 文書カタログの `/Metadata` | `CGPDFDictionaryGetStream` + `CGPDFStreamCopyData` で XMP が取れる（875 バイト、UTF-8）|
| XMP 内の Calibre 名前空間 | `calibre:series/rdf:value` と `calibreSI:series_index` が読める |
| XMP を持たない PDF | `CGPDFDictionaryGetStream` が false を返す（例外にならない）|

**`CGContext` の PDF 生成は XMP を書かない**ので、テストフィクスチャは
バイト列から組み立てる必要がある（`PDFFixtureBuilder`）。

### XML の安全性 [EM-60][実測]

`XMLParser`（libxml2）は**既定で安全**であることを実測で確かめた。

| 攻撃 | 結果 |
|---|---|
| XXE（`<!ENTITY xxe SYSTEM "file:///…">`）| **漏洩しない**。`shouldResolveExternalEntities = true` を明示しても読まれない |
| 外部 DTD でのネットワークアクセス | **一切出ない**（ローカル HTTP サーバへの到達 0 件）。`resolveExternalEntityName` は呼ばれるが `systemID` が `nil` |
| パラメータ実体（`%remote;`）| エラー 111 で拒否 |
| Billion laughs（10 段の実体展開）| エラー 111 で拒否 |
| 10 万段の深い入れ子 | 0.030 秒で完走、クラッシュしない |

**`resolveExternalEntityName(_:systemID:)` を実装しないこと。**実装しなければ
`nil` を返すのと同じで、外部実体は解決されない。既存の `EpubCoverResolver` も
実装していない。

読み込むバイト数は `AppLimits.Metadata.maxDocumentBytes`（1 MB）で制限する [EM-61]。
実際の `ComicInfo.xml` は数 KB、OPF でも数十 KB に収まる。

### 費用 [実測]

**メタデータを持たないファイルでも「無い」と判定するために容器を開く**必要がある。
この費用が蔵書全体にかかるため、実測してから設計を決めた。

| 容器 | 「無い」の判定（`listEntries`）| 読み取り |
|---|---|---|
| zip 20 頁 / 4 MB | 0.136 ms | 0.283 ms（先頭）／ 0.344 ms（末尾）|
| zip 200 頁 / 60 MB | 1.140 ms | 0.455 ms（先頭）／ **1.438 ms（末尾）** |
| 7z 200 頁 / 60 MB（無圧縮）| 0.301 ms | 0.439 ms |
| 7z 200 頁 / 60 MB（deflate）| 0.284 ms | **4.961 ms** |
| EPUB 200 頁 | 1.178 ms | 2.000 ms（container + OPF の 2 エントリ）|
| PDF（頁数によらず）| — | **0.070 ms** |
| RAR 120 項目（初回、§8.11.16 の既存実測）| **51.6 ms** | — |
| ネットワーク zip 121 項目（初回、§8.11.16）| **12 ms** | — |

**費用はファイルサイズではなくエントリ数に比例する。**zip は中央ディレクトリを
読むので大きさに引きずられない [NV-95] が、**エントリを 1 つ取り出す費用は位置に
依存する**（libarchive が先頭から走査するため、末尾にあると 3 倍）。7z の圧縮ありは
圧縮ブロックの構造上さらに高くつく。

5 万件での見積もり（逐次）: ローカルの小さい zip なら 7 秒、大きい zip で 55 秒、
**ネットワークなら 10 分、RAR 中心なら 43 分**。

**そのため次の 3 つで抑える**:

| 手段 | 効果 |
|---|---|
| **キャッシュ** [EM-07] | 更新日時とサイズが変わらなければ開かない。2 回目以降の走査は無費用 |
| **並行読み取り** | `FileIO` 経由で上限つき並行（`AppLimits.Metadata.maxConcurrentReads` = 4）。I/O 待ちが支配的なので実時間が縮む。協調スレッドプールは塞がない [NV6-01] |
| **ライブラリ単位の設定** [EM-06] | メタデータをまず持たない蔵書（同人誌等）では切って走査を速くできる |

### 読まない条件

| 条件 | 理由 |
|---|---|
| ライブラリ設定が無効 [EM-06] | ユーザーの選択 |
| **dataless（クラウドから追い出された実体）** [EM-62] | 読むとダウンロードが走る。サムネイル生成が同じ理由で避けている |
| キャッシュの印が一致する [EM-07] | 読み直す理由が無い |
| 対象拡張子でない | そもそも走査対象でない |

### 実機で確かめたこと [2026-08]

使い捨てのボリュームに**合成名**の標本を 6 種置いて確認した（実蔵書には触れていない）。

| 標本 | 結果 |
|---|---|
| `ComicInfo.xml`（`Number` のみ）| 題・シリーズ・巻数 7・**著者 2 名に分割**（`Writer` のカンマ区切り）|
| `ComicInfo.xml`（`Number`=12 ≠ `Volume`=2）| **衝突として記録**され、巻数はファイル名の `第05巻` のまま [EM-34] |
| `ComicInfo.xml`（`Title` 無し）| **タイトルだけファイル名由来**、シリーズと巻数はメタデータ由来 [EM-04] |
| 単一トップレベルフォルダ内の `ComicInfo.xml`（日本語フォルダ名）| 読めた [EM-20] |
| EPUB 3 | `title-type=main` を選び、**`role=ill` の creator を著者から除外**した [EM-41][EM-42] |
| PDF（Calibre 互換の XMP）| **XMP の題を情報辞書より優先**し、`series_index` の `6.00` を `6` として扱った [EM-50] |
| メタデータ無しの `.cbz` | 何も変わらない |

**判断を確定したあと再スキャンしても覆らない**ことも実機で確認した——判断の結果を
`metadataJSON` にも書き戻しているため（印が一致する限り読み直さないので、
ここへ残さないと衝突のままに見える）。

**ネットワーク上の PDF は読み切ってから解析する** [EM-63][NV6-08]。
`CGPDFDocument(url:)` は後備ファイルをメモリマップするため、**解析中に共有が落ちると
`SIGBUS` でアプリごと落ちる**（`try` では捕まえられない）。既存の
`CoreGraphicsPDFThumbnailLoader` が同じ対策を持つ。
