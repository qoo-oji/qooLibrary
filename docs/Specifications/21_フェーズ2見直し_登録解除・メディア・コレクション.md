## 21.1 段 A — 登録解除で「ライブラリデータを残す」を選べる [RG-06]

### 現状（実装を読んで確かめた事実）

- **登録解除は常にライブラリデータを消す。** `LibraryEnableAction.unregister` →
  `LibraryServices.disable(registrationUUID:)` → `SQLiteLibraryRepository.unregister`
  が `library` 行を消し、`managedFile`／`label`／`fileLabel`／`shelf`／各設定表が
  連鎖で消える。確認ダイアログ（`LibraryUnregisterConfirmationDialog`）もそう明示している
  （`library.unregister.explanation`／`.warning`）。
- `unregister(id:keepLabels:)` の `keepLabels` は **v1 から引数だけあって誰も読まない**
  （`_ = keepLabels`）。RG-06 の「保持」側の受け皿が無い。
- 逆向きの状態（**登録はあるがライブラリ行が無い**）は正規の経路がある
  （`LibrarySetupPrompt` が次の起動でウィザードをステップ 3 から再開。
  環境設定「リセット」の `deleteLibrary` がこの状態を作る）。
- `library` 行は **`uuid`（＝登録フォルダ ID）に加えて `bookmarkData`／
  `resolvedPath`／`volumeUUID` を自分でも持っている**。登録が消えても
  「どこのフォルダのライブラリだったか」は行だけで分かる。
- BK-02（破壊的操作の直前の控え）は `disable` と `deleteLibrary` の両方で呼ばれるが、
  **BK-07 の既定はすべて OFF**——既定の利用者は控え無しで消している。

### 決めごと

| ID | 内容 |
|---|---|
| RG4-01 | 登録解除の確認ダイアログに **「ライブラリのデータも削除する」チェックボックス（既定 OFF）** を置く。OFF で解除すると `library` 行と配下は残る（**既定の反転**——今は常に削除）。ON なら現行どおり連鎖削除 |
| RG4-02 | データを残した状態のライブラリ行を **「切り離し（detached）」** と呼ぶ。`RegisteredFolderStore` に対応する登録が無い `library` 行がそれ。**新しい列は要らない**——`services.library(registrationUUID:)` と `RegisteredFolderStore.folders(kind: .library)` の突き合わせで導出する（`LibrarySetupPrompt` が逆向きを同じ方法で導出している）|
| RG4-03 | **再登録時に同じ UUID を再利用して結び直す。** `RegisteredFolderStore.register(url:kind:displayName:)` に **`reusingID: UUID?`** を足し、`LibraryEnableAction.registerAndEnable` は登録前に `LibraryServices.detachedLibrary(matching: url)` を引き、見つかれば ①その `uuid` で登録し ②ウィザードのステップ 3〜5 を**飛ばして**既存の設定のまま再スキャンする。**`library.uuid` は登録フォルダ ID そのもの** [07章 §7.3] なので、ここを再利用しない限り旧行は永久に孤児になる（以前まさにこの形の欠陥を直している）|
| RG4-04 | 照合の鍵は **`(volumeUUID, resolvedPath)` の完全一致**。ボリューム識別子は `VolumeIdentity.identifier(for:)`（SMB の代替識別子を含む）で登録時と同じ関数を通す。**パスだけ・名前だけで照合しない**——同名フォルダを別ボリュームに持つ蔵書は普通にある |
| RG4-05 | 一致する切り離し行が複数あることは構造的に無い（`uuid` UNIQUE で、切り離しの契機は解除だけ）。一致しなければ従来どおり新規登録 |
| RG4-06 | **切り離し行はどこにも表示しない**——フォルダツリーには登録が無いので出ず、環境設定「リセット」の一覧には従来どおり出る（`deleteLibrary` で消せる）。「ライブラリの設定からいつでも削除できる」という認識には**リセットタブがその置き場所**である旨を、ダイアログの説明文で言う［判断待ち: 設定ウインドウにも削除ボタンを足すか。推奨は足さない——リセットタブが「消す操作だけ」の場所として整理済み］|
| RG4-07 | チェック ON の削除では、確認文に **BK-07 の設定状態**を添える（「バックアップの設定が OFF なので、この削除は控えを取りません」）。ダイアログから設定を変えさせはしない |
| RG4-08 | **走査の砦は変えない。** 切り離し行は `isOnline` を `false` へ落とす（`setOnline(false)`）——監視対象から外れ [SY-01]、再登録で `true` へ戻る。孤立判定 [ID-06] を切り離し中に走らせない |
| RG4-09 | 完全削除に伴う強制解除（`DeletePermanentlyCommand` の `registrationsInvalidated`）は**従来どおり削除**（実体が消えるので残す意味が無い）。制御口 `library:unregister` は `keepData` 引数（既定 `false` ＝ 現行の挙動を保つ。**破壊的な側を既定にするのは、口の既存の呼び出しを壊さないため**）|
| RG4-10 | ユーザー指定カバー（`usercovers/`）は切り離しでは消さない（行が残るので参照が生きている）。ON の削除では従来どおり `removeAll(libraryUUID:)` |

### 実装の置き場所

| `QooApplication` | `LibraryServices.disable(registrationUUID:keepData:)`、`detachedLibrary(matching url:)`、`reattach(libraryID:registrationUUID:)`（`setOnline(true)` ＋ 再スキャン）|
| `qooLibraryApp` | `LibraryUnregisterConfirmationDialog` にチェック（`@State`、既定 `false`）と RG4-07 の文。`LibraryEnableAction.registerAndEnable` に RG4-03 の分岐。ウィザード（`LibraryRegistrationWizard`）は**切り離し行があるときはステップ 1・2 だけ**で「以前の設定を引き継いで登録」と要約を出す |
| 文字列 | `library.unregister.keepData`（チェック）・`.keepDataHint`・`.noBackupWarning`・`libraryWizard.reattachSummary` |

### テストと検証

- 単体: 切り離し → 同じフォルダを再登録 → **同じ `uuid`・同じ `library.id`**・ラベル／評価／保護スコープが無傷。別ボリュームの同名フォルダは結び直さない（RG4-04 の変異: `volumeUUID` の照合を外すと落ちる）。切り離し中に走査が走らない（`isOnline=false`）。
- 変異の候補: ①`reusingID` を無視する ②照合を `resolvedPath` だけにする ③`detach` が `isOnline` を落とさない ④チェック OFF でも `unregister` を呼ぶ。
- 実機は**制御口で通る**（`library:unregister {keepData:true}` → `db:counts` → `library:register` → 同じ UUID）。GUI が要るのはダイアログの見た目だけ。
- 要件定義書 **v2.20**: RG-06 を「既定は保持、削除は明示」に改訂、RG4-01〜10 を新設、BK-02 の注記（「退避先がまだ無い」）を更新。**3 段まとめて上げるので、段 A の時点では版を上げていない。**

### 実装で分かったこと

- **`enable` の冪等分岐がそのまま結び直しになる。** 同じ `uuid` で登録し直せば
  `repository.library(uuid:)` が既存の行を返すので、**新しい経路を 1 本も
  作らずに済んだ**（草案・テンプレートの選択は使われない）。ウィザードが
  ステップ 3〜5 を飛ばすのは、選ばせても効かない画面を見せないため。
- **検出は 2 か所で行う。** ウィザードのステップ 2（「引き継ぐ」と予告する）と
  `registerAndEnable`（実際に `reusingID` を渡す）。**規則は
  `detachedLibrary(matching:)` の 1 つ**で、用途が 2 つ（表示と挙動）。
  ウィザードを通らない経路（制御口の `library:register`）でも結び直しは効く。
- **照合の規則を純粋関数へ切り出した。** ボリューム識別子を落としても
  パスだけで当たってしまう、という壊れ方は**実機では別ボリュームを用意しないと
  再現できない**ため。
- **`swift test` 中は絞らない。** 擬似ライブラリは実の `registeredFolders.json`
  に無いので、絞ると `libraries` が常に空になりテストが一斉に落ちる
  （`defaultAppDataLocation` と同じ理由・同じ形）。切り離しを試すテストは
  `ServicesWorkspace(tracksRegistrations: true)` で登録一覧を差し替える。

### 実機で確かめること（未了）

制御口 [MT-33] で通せるのは ①`library:unregister {keepData:true}` → `db:counts` で
行が残る ②`library:register` で同じ `uuid`・同じ設定に戻る ③`db:query` で
ラベルと評価が無傷。**GUI が要るのは 2 つだけ**——登録解除ダイアログのチェックと

## 21.2 段 B — メディア向けの予約語 [MF-01〜]

### 現状（実装を読んで確かめた事実）

- 予約語は **`FieldRef.swift` の 10 語に固定**（`@title` `@series` `@volume` `@author`
  `@circle` `@event` `@genre` `@keyword` `@booktype` `@ignore`）。`ReservedWordTable.entries` は
  `SemanticKeyword.allCases` ＋ 3 語から**導出**され、`check-localization-keys` も
  このファイルの `"@…"` リテラルから正の集合を取る。
- **ユーザー定義フィールドはファイル名から抽出できない**（ステージ 5 で `@labelgroupN` を
  撤去し、「足りない軸は `SemanticKeyword` に case を足す」と決めている）。
- 型付き照合は 2 種——`@volume`（`FieldKind.volume`、`VolumeMatcher` ＋ ライブラリごとの
  `volumeFormat` 表）と `@booktype`（`.enumerated(語彙)`）。**型付きは境界になる**
  [FF-18] ので、自由文字列の隣に置ける。
- `@title` の無いフォーマットは通る [FF-19]（`@series` か `@volume` があれば足りる）。
- **`seriesTitleCompositionFormat` [SE-33] は保存されるだけで誰も読まない**
  （`MANUAL.md` にもそう明記）。
- 構造化列は `title` `seriesName`/`seriesKey` `volumeNumber`/`volumeKind`/`volumeRaw`
  `authorName` の 4 系統。並びは `orderClause` と `seriesStackSubquery` の合成鍵が
  `volumeNumber` を見る。

### 着手前の実測（2026-09-08）— 設計を 3 箇所書き換えた

**この節の数字が MF-09・MF-19 の根拠である。** 実蔵書のコーパス
（`Tests/GoldenDataset/private/corpus/`）から**集計と形だけ**を取り出した [MT-32 層 0]。
個別のファイル名はコード・文書・会話のどこにも写していない。

映像ライブラリ **79 ファイル**（`.mp4` 64／`.mkv` 15、フォルダ 35、階層 2〜4）:

| パターン | 出現 | 当初の設計 |
|---|---|---|
| **`SxxEyy`** | **0 件（0%）** | `ES-Standard` の**筆頭**に置いていた |
| **`1x01`／`EP01`／`#01`** | **0 件（0%）** | 同セットに含めていた |
| **`第N話`／`N話`** | **7 件（8.9%）** | 含む |
| **シーズン表記**（`S01`／`シーズン`／`第N期`）| **0 件（0%）** | `SS-Standard` を新設 |
| `「…」`（全部日本語）| 7 個 | `@subtitle`。**`第N話` と同数**＝`第N話「サブタイトル」` の形 |
| **年号 4 桁** | **14 件（17.7%）** | 記述が無かった → MF-19 |
| 日付 `2024-01-15` | **0 件（0%）** | 同上 |
| `[…]`（**全部日本語**）| 18 個 | `@actor` の受け皿 |
| `(…)`（**ASCII が 15**）| 17 個 | 解像度・コーデック＝`@ignore` で捨てる |

**1 フォルダあたりのファイル数**は 1 件が 19 フォルダ・2 件が 9 で、シリーズものは
2 フォルダ（15 件・18 件）だけ——**単発作品が主体**。MF-14 が「映像作品／映像（単発）」の
2 プリセットに分けたのは、この形と合っている。

コミック側（成年コミック 396／同人誌 1,804／同人CG 146）は**年号が 0.2% 以下**で、
括弧は **100% の名前が持ち 1 件あたり 2 個以上**の定型（既存プリセットが拾い切っている）。
対して映像は括弧が 1 件あたり 0.5 個で、**構造が桁違いに疎**。

> **この実測が覆したもの**: 着手前に私は「メタデータ標準（ComicInfo v2.0 の 40
> フィールド・Kodi NFO）に載る軸のうち、ファイル名に現れるもの」を推測で列挙し、
> 出版社・レーベル・年齢制限・言語・監督が「よく出る」と書いた。**実データでは
> 1 件も現れない。** ファイル名から**取れる**軸と、メタデータとして**持てる**軸は
> 別物で、前者から後者を推測してはならない［ユーザーの指摘、2026-09-08］。

### 判断の決着（2026-09-08）[ユーザー判断]

| 論点 | 決定 |
|---|---|
| 予約語の足し方 | **A 案**（`SemanticKeyword`／`FieldRef` へ固定で足す）。B 案（利用者が名前付き予約語を定義）の**実需要は実データに無い**——汎用の軸を必要とする構造がファイル名に現れないため。**B へ移るときも A の語はそのまま既定の語彙として残る**ので手戻りは無い |
| `@episode` の型条件に素の数字を含めるか | **含める**（`@volume` と同じ [SE-24]）。ただし Jellyfin #3669（`1080p` を話数と誤認）と同じ壊れ方をしないことを**実装時に合成名で測る**——qooLibrary はフォーマット全体で照合するので構造的に起きにくい**はず**だが、これは想定であって実測ではない |
| 日付ベースの番組 | **`@date` として一般化する**（映像固有の `airDate` にしない）。年・月・日を持てる形。→ MF-19 |
| `@season` | **足す**（実データ 0 件だが、段 C のコレクション分けが「シーズン」を軸にする設計。列を後から足すより安い）|
| `ES-Standard` の中身 | **実測優先＋一般規約も入れる**（`第N話` を先頭に、`SxxEyy`・`1x01`・`EP01`・`#01` も同じセットに置く。照合は最長一致なので順序は結果を変えない [VM2-01]）|

### 決めごと

| ID | 内容 |

### 実装で分かったこと（2026-09-08、既定セットまで）

**役割の出どころを 1 つに決めた [MF-07 の補足]。** `volume-sets.json` の行に
`role` を書く案と、テンプレートの鍵（`episodeSet:`）が決める案の両方を書いてみて、
**後者を採った**——両方に持たせると `episodeSet: "VS-Full"` のように名前と中身が
食い違ってもコンパイラも静的検査も止められない。`patterns(named:role:)` が
呼び出し側から役割を受け取り、`LibraryTypeTemplate.patternSetNames` が
「どの鍵がどの役割か」を 1 箇所で決める。**JSON の集合は正規表現の袋にすぎず、
役割を知らない。**

**`numericValue` は役割と同じ名前のキャプチャを最優先する [MF-06]。**
`S(?<season>\d+)E(?<episode>\d+)` は 1 つの一致から 2 つの値を持つので、
既存の「`(?<volume>…)` か第 1 グループ」規則のままだと**シーズン番号が話数として
返る**——画面には数字が出るので誤りに気づけない。実装前は「あれば嬉しい改善」の
つもりだったが、`ES-Standard` を書いた時点で**必須**になった。

**役割を運び忘れる経路が 3 つあった。** どれも「行は増えて見えるのに一致しない」
という読み解けない壊れ方をする:

| 経路 | 落とすとどうなるか |
|---|---|
| `UserTemplateSettings.VolumeFormat` | 映像ライブラリをテンプレートにした瞬間に、話数・シーズン・日付の正規表現が全部巻数用として復元される |
| `TemplateDiff` の鍵と `addVolumeFormat`／`removeVolumeFormat` | 改訂で足された話数の正規表現が巻数として適用される [LT-13] |
| `TemplateInstantiation.draft`／`snapshot` | 設定画面が話数のパターンを巻数の区画に並べる |

**既定セットの語境界。** `[eE](\d+)` は `Blue7`、`(?i:ep)` は `Sleep01` の途中を
拾う（Jellyfin #3669 と同じ形）。`(?<![a-zA-Z])` を前置して塞いだ。**ICU は
`\/` を定義済みエスケープとして持たない**ので、文字クラスは `[-./]` と書く。

**ゴールデンは鍵の読み替えだけで説明できた。** public 352 件のうち差分 66 件、
private 2,346 件のうち差分 2,345 件——**全件が `@booktype`→`@mediatype` と
`@circle`→`@studio` の読み替えで一致**し、`matched`・`formatIndex`・他の値は
1 件も動いていない。適合率も基準線どおり（成年コミック 100% / 同人誌 99.9% /
同人CG 100%）。

### 残す限界

- 複数話（`S01E01E02`）・特番（`S00`）は初版で扱わない（MF-09）。絶対通し番号は
  シーズン無しの `@episode` として**既に表せる**ので追加は要らない。
- **メタデータ標準にあってファイル名から取れない軸**（出版社・レーベル・年齢制限・言語・
  監督・あらすじ・ページ数）は予約語にしない。**実データのファイル名に 1 件も現れない**
  ことを確かめてある（着手前の実測）。汎用の軸を増やす手段が `@keyword` 1 つしか無い
  という制約は残るが、実需要が見えるまで B 案は先送りする。
- `@actor` を複数人並べる形（`[A, B] @title`）は 1 ラベルになる。区切りでの分割は
  `@circle` 等にも無い機能なので、要るなら全語共通の「区切りで複数ラベル」として別に起票する。

## 21.3 段 C — コレクション分け（ライブラリ表示モードの再定義）[CX-01〜]

### 現状（実装を読んで確かめた事実）

- ライブラリ表示モードの独自性は **フラット表示 [VM-10]・シリーズスタック・重複の畳み・
  未整理ビュー・シェルフ節**——いずれも「見せ方」で、「ライブラリとして管理する」概念は無い。
  メモの認識どおり。
- ラベルフィルタ（`LabelFilterPane`／`LabelFilterModel`）は**フォルダ・ライブラリ両モードで
  同じもの**が出る（出す条件は入口がライブラリ経由か [LF-01]）。フィールド帯 → ラベル
  （多選択、グループ内 OR × グループ間 AND、ピン留め、「もっと見る」、検索欄）。
- 中央ペインの畳み（`RowGroup`: `.series`／`.duplicate`）は **`GROUP BY` で 1 ファイル 1 群**。
  行の実体は代表ファイル（`FolderEntry.id == url`）。
- ラベルは N:M（`fileLabel`）——**1 ファイルが同じフィールドの複数ラベルを持てる**ので、
  既存の畳みでは表せない。
- 左ペインの件数（`LabelSummary.fileCount`）は「生きていて保管庫の外」の数 [LA3]。
  ライブラリ全体で数える [LF-11]。10 万件で 105 ms。
- シェルフ（`ShelfCondition`）は `labelIDs`（複数フィールド）＋評価＋検索語＋並び＋表示モード。
- 「未整理のファイル」[UR3-01] は左ペイン最下部に常設で、**中央ペインの絞り込み**
  （`FileQuery.unresolvedFilter`）へ切り替える。

### 判断（4 点）[判断待ち]

| # | 論点 | 採用（推奨）| 代案 |
|---|---|---|---|
| C-1 | フォルダモードの左ペイン | **今の多選択フィルタを残す**（フォルダ＝絞り込み、ライブラリ＝分類、という役割分担）| 多選択フィルタを廃止して両モードともコレクション方式に寄せる（LF-08〜10 を要件ごと撤回）|
| C-2 | シェルフ | **廃止**（複合条件を持てない形で残しても存在理由を説明できない）| (a) フォルダモード側の機能にする (b) 「フィールド＋ラベル＋評価＋検索語」だけの薄い形へ |
| C-3 | コレクションの範囲 | **ライブラリ全体**（フィールドを選んだ瞬間にライブラリ根へ移動。未整理ビューと同じ前例）| 現在フォルダ配下 [VM-11] のまま |
| C-4 | コレクション内のシリーズスタック | **効かせる**（既定 ON のまま入れ子で畳む）| コレクション内は巻ごと |

### 決めごと

| ID | 内容 |
|---|---|
| CX-01 | ライブラリ表示モードの左ペイン下半分を **`CollectionNavigatorPane`** に置き換える。区画は上から **評価**（従来どおり、AND で効く）／**フィールド**（単一選択。`LabelFilterModel.fields` を 1 行ずつ幅いっぱいの帯で、選択中を強調）／**ラベル**（選択中フィールドのラベルを件数付きで一覧。単一選択。10 件超なら既存の検索欄 [PN-05] を出す）／**未整理のファイル**（従来どおり最下部）。フォルダモードの `LabelFilterPane` は**触らない**（C-1）|
| CX-02 | 状態は `WindowState.collection: CollectionSelection?`（`field: FieldID`、`label: CollectionKey?`。`CollectionKey = .label(LabelID) / .unclassified`）。**`labelSelection` とは別に持つ**——意味が違う（絞り込み vs 分類）ものを同じ器に入れると、モード切替で取り違える。ライブラリモードでは `labelSelection` を読まず、`collection.label` から `[field: {label}]` を**導出して** `FileQuery` に渡す |
| CX-03 | 中央ペインは **`collection.field != nil && collection.label == nil` のときだけコレクション一覧**、それ以外は従来の一覧。コレクション一覧は **`FolderEntry` を使わない専用ビュー `CollectionGridView`／`CollectionListView`**。理由: 行の実体がファイルではない（代表ファイルを流用すると `FolderEntry.id == url` が衝突する——同じファイルが複数コレクションの代表になりうる）。ファイル操作は一切出さず、できるのは「開く」だけ。`entries` の二重源の罠 [`check-raw-entries-access`] にも触れない |
| CX-04 | コレクション一覧の行は **`CollectionSummary`**（`key`・表示名・色・件数・カバー 4 件の `FileID`）。件数は `LabelSummary.fileCount` そのもの（`labels(fieldID:)` を再利用）。**「未分類」は 1 行**（そのフィールドのラベルを 1 つも持たない生きているファイルの数。`NOT EXISTS` 1 本、`SQLiteManagedFileRepository.unclassifiedCount(libraryID:fieldID:)`）。0 件の未分類は出さない |
| CX-05 | カバー 2×2: `CollectionCoverIcon`（`FolderCoverIcon` の隣。**格子で重ねない**）。素材は `firstFiles(libraryID:labelID:limit: 4)`（既定の並びで先頭 4 件）を `CoverResolution.resolve` に通す。1〜3 件なら空きは残す。右上に件数バッジ（`groupCountBadge` を流用）|
| CX-06 | コレクションを開く（ダブルクリック／Enter）＝ `collection.label` を立てる → 中央ペインは従来の一覧（`labelSelection` 導出）。左ペインのラベル一覧で該当行をハイライト。**左ペインでラベルをクリックしたのと同じ状態**になる（メモどおり）|
| CX-07 | 履歴: `TabHistoryEntry` に `collection: CollectionSelection?` を足す（`series` と同じ扱い）。戻るでコレクション一覧へ、進むで再びラベルへ。ドリルインは読み直しの合図を張らず `LibraryLoadKey` の鍵に含める（VM3S と同じ）|
| CX-08 | フィールドを選び直すと `collection.label` は落ち、一覧は即座に再構成される。ライブラリの外へ出る／フォルダモードへ戻ると `collection` ごと落とす（`LibraryContentModel.clear()` と同じ場所）。**フォルダモードに戻ったとき `labelSelection` は空**（ライブラリモードの選択を絞り込みとして持ち越さない）|
| CX-09 | 範囲はライブラリ全体（C-3）。フィールドを選んだときに現在地がライブラリ根でなければ**根へ移動**する（`UnresolvedViewNavigation` と同じ）|
| CX-10 | コレクション内ではシリーズスタックが従来どおり効く（C-4）。ラベルで絞ったうえで畳むので `isFiltering` の判定から `labelSelection` 由来の絞りを**除く**（今は「絞り込み中は畳まない」[VM3-06]。コレクションは絞り込みではなく分類なので畳んでよい）|
| CX-11 | コレクション一覧の並び: 名前順／件数順（`FieldEditorModel.rows(sortedBy:)` の規則を再利用）。未分類は**常に末尾** |
| CX-12 | 用語: 「未分類」（そのフィールドのラベルが無い）と「未整理」（どのフォーマットにも一致しない）は別概念。`20_用語集.md` に両方を載せ、コレクション一覧のツールチップで「〈フィールド名〉のラベルが付いていないファイル」と説明する |
| CX-13 | シェルフ廃止（C-2）: UI（`shelfSection`・`ShelfDialogs`・メニュー「シェルフとして保存…」）・`ShelfModel`・`ShelfCommands`・`WindowState.currentLibrarySort/pendingLibrarySort` を消す。**`shelf` 表と JSON バックアップの `shelves` は残す**（表を落とす移行は要らないし、古い文書を読めなくする理由も無い。読み出し側は捨てる）。要件 SH-01〜12 を処分表で「撤回」に |
| CX-14 | 「重複のみを表示」「未整理」はコレクション一覧では無効（従来の一覧でのみ有効）。表示メニューの `canShowDuplicatesOnly` に条件を足す |
| CX-15 | 制御口: `ax:*` で足りる。コレクション一覧の行は `AXValue` に表示名を置く（`locate` が値も見る [CT-12]）|

### 実装の置き場所

| 層 | 変更 |
|---|---|
| `QooKit` | `CollectionSelection`／`CollectionKey`／`CollectionSummary`（`Persistence/`）。`FileQuery` は変更なし（絞りは `labelSelection` の導出で足りる）|
| `QooPersistence` | `unclassifiedCount(libraryID:fieldID:)`・`firstFiles(libraryID:labelID:limit:)`・`firstUnclassifiedFiles(...)`。索引は既存の `fileLabel(labelId)` で足りる（着手時に 10 万件で実測）|
| `QooApplication` | `CollectionModel`（一覧の読み込み・並び・カバーの解決。`LabelFilterModel` の `fields`/`labels` を共有）。`LibraryContentModel.load` に `collection:` を渡す（`labelSelection` 導出と `isFiltering` の除外）|
| `qooLibraryApp` | `CollectionNavigatorPane`（左）・`CollectionGridView`／`CollectionListView`・`CollectionCoverIcon`（中央）・`MainWindowView` の出し分け（`displayMode == .library` で左ペインを差し替え）・`WindowState`（`collection`・履歴）・`FolderContentView`（`LibraryLoadKey` に `collection`）|
| 削除 | CX-13 のシェルフ一式 |

### テストと検証

- 単体（`QooUI` へ切り出せる判定）: `collection` → `labelSelection` の導出／未分類が末尾／
  フィールドを変えると `label` が落ちる／モードを戻すと `collection` が落ちる／
  `isFiltering` がコレクションを絞り込みと数えない。永続化: 未分類の件数（同じフィールドの
  別ラベルを持つファイルは数えない・保管庫は数えない）、`firstFiles` の並び。
- 変異の候補: 未分類が「どのフィールドのラベルも無い」になる／`firstFiles` が並びを無視／
  導出が `field` を落とす／モード切替で `collection` を残す／未分類を先頭に出す。
- 実機（**見た目が要るので GUI**）: 2×2 の格子とバッジ、帯の選択強調、フィールド切替の
  即時再構成、同じファイルが 2 つのコレクションに出ること、開く → 左ペインのハイライト、
  戻る／進む。制御口で先に `ax:dump` を通してから撮る。
- 要件定義書 v2.20: 14.2／14.3 節を改訂、CX-01〜15 を新設、SH-01〜12 と LF-08〜10
  （ライブラリモード側）を処分表へ。19章 §19.2「探す」の行を書き直す。

### 残す限界

- 複数フィールドの組み合わせで絞ることはライブラリモードではできない（メモが明示した
  トレードオフ。フォルダモードの多選択フィルタで行う）。
- コレクションの入れ子（フィールド A → B）は作らない。
- `@series` は構造化列であってラベルではないので、束縛していないライブラリでは
  「シリーズ」のコレクションは出ない（シリーズスタックがその役目）。統一は将来の論点。
