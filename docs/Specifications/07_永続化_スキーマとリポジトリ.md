## 7.0 なぜ SQLite（GRDB）か [設計判断、2026-08]

要件定義書 v2.8 までは SwiftData を前提としていた。フェーズ 2 の着手時に
**本プロジェクトの実スキーマ・実ファイル名・実機で測った**ところ、SwiftData は
想定規模（`C-07`: 1 ライブラリ 5 万・全体 10 万ファイル）の境界線上にあることが
確認できたため、実装前に SQLite（GRDB 7）へ切り替えた。

測定条件・全結果・そこから確定した設計判断は `Spikes/README.md` の
**「T-03 / T-04: 永続化層の性能」**にある。**このファイルの設計を変えるときは、
まずそこを読むこと。** 要点だけ:

| # | 実測が確定させたこと |
|---|---|
| 1 | PF-01〜PF-07 をすべて満たす。最も余裕が小さい PF-03（ラベルフィルタ）でも最悪 182 ms 対 目標 500 ms |
| 2 | **`LabelIndex`（メモリ上の索引）は作らない** [T-03]。「グループ内 OR × グループ間 AND」は SQL の `INTERSECT` で表現できる。索引を二重に持つと DB との整合性維持が新たな危険源になるだけ |
| 3 | **内部の行 ID は `Int64`（rowid）**。UUID 文字列に対し投入 3 倍速・DB サイズ 1/2.8 |
| 4 | **FTS5 を使わない**。`LIKE '%…%'` の全走査が 10 万件で 20.7 ms |
| 5 | **GRDB は協調スレッドプールの外（自前の直列キュー）で待つ**。8章 §8.11 の `FileIO` と同じ性質を持つため、DB のために別の逃がし先を用意しなくてよい [NV6-01][NV6-04] |

## 7.1 接続の構成 [ST-01〜ST-07]

```swift
/// アプリで単一 [ST-01]。全ウインドウ・全タブが共有する [ST-02]。
public final class QooDatabase: Sendable {
    private let pool: DatabasePool

    public static func open(at url: URL) throws -> QooDatabase
}
```

| # | 要件 |
|---|---|
| CN-01 | `DatabasePool`（WAL）を 1 つだけ持つ [ST-01][ST-02]。読み取りは並行、書き込みは直列化される |
| CN-02 | `PRAGMA journal_mode = WAL` / `synchronous = NORMAL` / `foreign_keys = ON` / `busy_timeout` を `Configuration.prepareDatabase` で設定する |
| CN-03 | 長時間処理は書き込みトランザクションを細かく区切る [ST-04][SE3-05]。WAL により読み取りは妨げられない（実測: 書き込み中の読み取り 3 ms）|
| CN-04 | メインスレッドから同期の読み書きを行わない [ST-05]。**ただし DB は常にローカル**（Application Support 配下）なので、8章 §8.11 の `FileIO` へ逃がす必要はない ——GRDB 自身が協調プールの外で待つ [実測] |
| CN-05 | 層をまたぐ受け渡しは `Sendable` な値型のみ [ST-06]。`Database` / `Row` / `Statement` を `QooPersistence` の外へ出さない |
| CN-06 | 書き込みは明示的なトランザクション。単位は Command の境界と一致させる [ST-07][A-03] |
| CN-07 | UI の追随は `ValueObservation` で行う。ポーリングしない |

## 7.2 スキーマ移行 [MG-01〜MG-04]

**v1 の時点から移行の器を用意する。** 移行対象がない段階でも、初版スキーマを
最初の移行として登録した `DatabaseMigrator` をファイルとして持つ [MG-01][MG-02]。

```swift
public enum QooMigrations {
    public static var migrator: DatabaseMigrator {
        var m = DatabaseMigrator()
        // eraseDatabaseOnSchemaChange は決して有効にしない（データを消すため）
        m.registerMigration("v1_initial") { db in … }       // §7.3
        m.registerMigration("v2_regexPatterns") { db in … }  // 下記
        m.registerMigration("v3_embeddedMetadata") { db in … } // 下記
        return m
    }
}
```

### v2_regexPatterns [2026-08]

巻数フォーマットと保護文字列を正規表現へ移す（04章 §4.6 / 05章 §5.1）。

| 対象 | 変更 |
|---|---|
| `volumeFormat.source` | `??` / `<space>` の独自記法 → 正規表現 |
| `volumeFormat.ordinalRank` | → `kind`（`volume` / `separator`）。**序列巻数の廃止に伴い、順位を持っていた行は「区切り専用」になる** |
| `protectedToken.text` | → `pattern`（完全一致のリテラル → 正規表現） |
| `volumeOutputStyle.ordinalTemplate` | 出力すべき序列が無くなったので削除 |
| `managedFile.volumeKind` | `ordinal` は取りうる値でなくなったので `none` へ |

**変換は `LegacyVolumeNotation`（`QooKit`）が行い、JSON バックアップの取り込みと
同じ関数を使う。** 片方だけ直すと、以前書き出した文書と DB とで変換結果が食い違う。

| # | 要件 |
|---|---|
| SC-01 | スキーマ移行中はアプリ終了を許可しない [LK-42] |
| SC-02 | **登録済みの移行は追記のみ。後から書き換えない** [MG-04]。適用済みの環境と食い違い、検出できない不整合になる |
| SC-03 | 移行の識別子は `v<連番>_<内容>` 形式。時系列で並ぶこと |
| SC-04 | ストア内のメタデータ（`storeMetadata`）とアプリの期待値を毎起動で突き合わせる [MG-03] |
| SC-05 | 移行は必ずテストを伴う。「1 つ前の版のスキーマでデータを作り、移行して、期待どおりになる」ことを検証する。GRDB の `migrator.migrate(_:upTo:)` で途中の版を再現できる |

### v15_bookTypeAsLabel [2026-09-04]

本の種別を「ライブラリ固有の設定」から「ラベル」へ [TY-01]。

| 対象 | 変更 |
|---|---|
| `libraryType.libraryTypeName` | **DROP**。本の種別は本の属性であってライブラリの属性ではない［ユーザー判断］——`@booktype` は**語彙**（プリセットの本の種別 ∪ そのライブラリの「本の種別」ラベル）で照合する |
| `managedFile.libraryTypeMismatch` | **DROP**。「このファイルの印が**このライブラリの型名**と違う」警告なので、型名が無くなれば計算できない。同じことはラベルフィルタで「本の種別」を絞れば分かる（宣言した状態ではなく観測から導く [P4]）|

**列を落とす前に、型名を語彙へ移す。** 型名を編集していたライブラリは、
そのまま落とすと `(@booktype)` が二度と一致しなくなり（プリセット由来の語彙に
しか当たらないため）、次の走査で全件が未整理になって自動ラベルが消える。
そこでライブラリごとに「本の種別」フィールドを用意し、それまでの型名を
ラベルとして入れてから列を落とす（`carryBookTypeNamesIntoLabels`）。

フィールド名は**予約語の綴り**（`booktype`）を使う——移行は表示言語を知らない
[A-01] ため。**名前は身元ではない**ので利用者が後から自由に改名できる [§19.2]。

**型条件そのものは残す。** 外して自由文字列にすると、プリセットの
`(@booktype) …` が `(@event) …` と同型になって先頭の括弧を何でも吸い、
public ゴールデン 352 件のうち **48 件でイベントが取れなくなる**［実測］。
実蔵書での適合率は 3 つとも不変（成年コミック 100% / 同人誌 99.9% / 同人CG 100%）。

### v14_labelVisibility [2026-09-03]

ラベルの非表示モデルと非正規化件数の撤去（v3 ステージ 11、[§19.12][§19.13 #1]）。

| 対象 | 変更 |
|---|---|
| `label.fileCount` | **DROP**。非正規化をやめ、表示のたびに数える [DB-02 撤回] |
| `label.isArchived` | → **`isHidden`**（RENAME COLUMN）。値はそのまま運ぶ——「保管庫」と「手動で非表示」はどちらも「フィルタから外す」という同じ効果を持っていた [LA3-02] |

**列の綴りを分けたのは `managedFile.isArchived`（ファイル保管庫 [FA-05]、
存続する）との取り違えを構造的に消すため**［ユーザー判断］。ラベルの側だけ
概念が無くなるので、同じ綴りのまま意味だけ変えると次に読む人を誤らせる。

**索引・トリガはどちらの列も参照していない**（`fl_label` は `fileLabel` 側）ので、
素の `ALTER TABLE` で足りる。

**撤去して遅くならないことを先に測った**（10 万件・50 万紐づけ、Release）:
旧経路 109.4 ms → 相関副問い合わせ 105.3 ms。旧実装が既に
`fileCountIncludingArchived` の副問い合わせを走らせていたためで、
**列を持つ費用は速度ではなく「数え直しを忘れるとずれる」危険だけだった**
——実際その穴は 2 度踏んでいる（2-14 の `state`、2-11 の `isArchived`）。

### v12_shelf [2026-09-01]

シェルフ（保存した絞り込み）の表を足す [SH-01]。**既存の行には触れない**
——新設のみなので移行の失敗様式が無い。`AUTOINCREMENT` にするのは、削除の
⌘Z が**同じ行 ID で**戻すため [SH-11]（`label` と同じ理由）。

### v3_embeddedMetadata [2026-08]

埋め込みメタデータの読み取り（09章 §9.9）のための列を足すだけ。**既存の行は
`metadataStamp` が NULL になり、次のスキャンで「まだ読んでいない」として扱われる**
——移行時に読みに行かない（移行はストアを開く前に走るので、ボリュームが接続されて
いるとは限らない）。

| 対象 | 変更 |
|---|---|
| `managedFile` | `metadataStamp` / `metadataSource` / `metadataJSON` / `hasVolumeConflict` を追加 |
| `library.settingsJSON` | `readsEmbeddedMetadata`（既定 `true`）と `comicInfoVolumeSource`（既定 `ask`）を追加。**JSON なので移行では触らない** — `Codable` の既定値で読める形にしておく |
| `library.settingsJSON` | ~~`identityMatchPolicy`（既定 `sameName`）を追加 [ID-13]~~ ステージ 1 で撤回 [§19.8]。旧 DB に鍵が残っていても読み飛ばされる |

**`settingsJSON` の新しいキーは `Bool?` / `String?` にはしない。** Swift の合成された
`Decodable` は**プロパティの既定値を使わず**、キーが無いと `keyNotFound` で失敗する
[実測、`AppAssociationStore` で踏んだ罠]。`LibrarySettingsPayload` は
`var readsEmbeddedMetadata: Bool = true` のように**宣言時の既定値を持つ非 Optional**
にし、`init(from:)` を手で書いて `decodeIfPresent` で読む。

### 起動シーケンス [MG-10〜MG-13][RB-03][RB-06]

```pseudo
bootstrapStore():
    if !exists(storeURL): 新規作成 → migrator.migrate() → 完了

    # [MG-12] アプリが知らない移行が適用済み = 新しすぎる。起動中止
    if try migrator.hasBeenSuperseded(db):
        abort with .schemaTooNew

    if 未適用の移行がある:
        # [MG-10] 移行前に必ずスナップショット + ストア複製
        JSONExporter.exportAll()
        pool.backup(to: backups/pre-migration-<日時>.sqlite)   # オンラインバックアップ
        do:   try migrator.migrate(pool)
        catch: 読み取り専用モードで開く + 復元を提示          # [MG-11][RB-06]
        JSONExporter.exportAll()                              # [MG-13] 移行後も自動
    if PRAGMA integrity_check が失敗:
        自動バックアップからの復元を提案                       # [RB-03]
```

**`hasBeenSuperseded` が MG-12 をそのまま満たす**——アプリが知らない識別子の移行が
適用済みなら真を返す。バージョン番号の自前比較より確実である。

## 7.3 テーブル定義

### ID の方針 [設計判断]

**内部の参照はすべて `Int64`（rowid）。**UUID 文字列は使わない（実測で投入 3 倍・
サイズ 2.8 倍の差）。JSON 入出力の同一性キーはもともと UUID ではなく自然キー
（相対パス + ファイル名 等）なので [JS-04]、外部仕様は変わらない。

**外部から参照されるものだけ**が安定した外部キーを併せ持つ:

| テーブル | 外部キー | 誰が外から参照するか |
|---|---|---|
| `library` / `temporaryFolder` | `uuid TEXT UNIQUE` | フェーズ 1 の `registeredFolders.json` の登録 ID。環境設定の「起動時に開くフォルダ」、`NavigationRoot.registeredFolder(id:)`、ウインドウ状態復元 |
| `libraryType` | `presetKey TEXT UNIQUE`（ユーザー定義は NULL）| アプリ更新をまたいだプリセットの同定 [LT-10] |
| `label` / `labelGroup` | なし。ただし `AUTOINCREMENT` | ウインドウ状態復元がラベルフィルタの選択を保持する [ST-20]。**rowid が再利用されると復元後に別のラベルが選ばれる** |
| `managedFile` / `fileLabel` | なし | 生存中の参照はすべて外部キー制約（`ON DELETE CASCADE`）。操作履歴・通知は**パスとファイル名を非正規化して持つ**ため、行が消えても意味を保つ |

> **［訂正、2026-08］全テーブルが `AUTOINCREMENT` である。** この表と
> CLAUDE.md は長く「`label` と `labelGroup` だけに付ける、`managedFile` には
> 付けない」と書いていたが、`QooMigrations` は最初から全テーブルで
> `autoIncrementedPrimaryKey`（GRDB のこれは `autoincrement: true`）を使って
> おり、ライブストアの `sqlite_master` にも `managedFile … AUTOINCREMENT` が
> ある［実測］。T-03 の性能実測（10 万件投入・DB サイズ）もこの実装で
> 取っているので、**数値は現状のまま有効**である。
>
> 実装を仕様へ寄せる（外す）のではなく**記録のほうを実態へ合わせた**。外すと
> 既存ストアの移行が要るうえ、付いていることが実際に役立っている——
> 削除した行を**同じ ID で復元できる**性質は、ラベルの削除・統合の Undo
> [LE-07][LB-07] に続いて**孤立レコードの削除・再紐づけの Undo**
> [OR-02][OR-04] でも土台になっている（§15.7）。上の表が言う「再利用を
> 禁じる理由」は `label` / `labelGroup` について特に強い、と読むこと。

### 保護スコープを 1 列で持つ理由 [PR-02][設計判断]

保護の単位は**基本情報**（タイトル・シリーズ名・巻数・著者名を 1 かたまり）と
**フィールド**（ラベルの軸ごと）の 2 つで、`["basic","field:12"]` のような
JSON 配列として持つ。

- **別テーブルにしない。** 判定は常にファイル単位（`applyParsedFields` も
  `replaceAutoLabels` も 1 ファイルを扱う関数）で、集合を丸ごと読めば足りる。
  列 1 本なら `RegenerabilityDeclaring` の網羅性検査 [MG-23] にも素直に乗る。
- **綴りは決定的に並べる**（`ProtectionScopeCoding.encode` が昇順にする）。
  揃っていないと、同じ集合が毎回違う文字列になって意味の無い UPDATE と
  JSON の差分が出る。移行の SQL も同じ並びで書く。
- **`field:` の数字は行 ID。** JSON バックアップでは**フィールド番号**へ
  翻訳する [JS-04 と同じ理由]——行 ID を書くと、別の環境で取り込んだときに
  無関係なフィールドを保護する。翻訳は `SQLiteBackupRepository` に閉じてある。

### 設定を JSON 列で持つ理由 [MT-10][MT-15][設計判断]

`library.settingsJSON` には、**可変長で・件数上限が将来変わりうる**設定
（区切り文字集合、保護文字列、`semanticBindings`、`labelGroupOrder`、
`targetExtensions` / `imageExtensions`、`seriesTitleCompositionFormat` 等）を
まとめて格納する。固定カラムにすると上限の引き上げがスキーマ変更を伴うため
[MT-10]。**ただし SQL で絞り込む必要があるものは列にする**——検索・フィルタ・
ソートの対象になるものを JSON へ入れてはならない。

一方 `filenameFormat` / `volumeFormat` / `folderLevelMapping` /
`protectedToken` / `volumeOutputStyle` は**優先順の並べ替え・個別の有効／無効・
編集画面での一覧**があるため、独立したテーブルにする。

#### プロパティ名がそのまま鍵になる型は、Swift の呼び名と切り離す

`LibrarySettingsPayload`・`LibraryBackup`・`FieldBackup`・`TemplateDefinition` は
**合成 `CodingKeys`**（＝プロパティ名がそのまま JSON の鍵）で書き出す。したがって
**プロパティを改名すると、それだけで外部形式が変わる。**

2026-09-03 の型名一括改名（ラベルグループ → フィールド）で実際に 3 件巻き込み、
テストが捕まえた。据え置いた綴りは次のとおりで、**Swift 側の呼び名だけ揃える**
（`TemplateDefinition` は `labelGroups` を実体に据え、`var fields: [FieldSpec]`
を計算プロパティとして併設した）。

| 綴り | どこの鍵か |
|---|---|
| `labelGroupOrder` | `library.settingsJSON` |
| `labelGroups` | JSON バックアップ（`LibraryBackup`）と `library-types.json` |
| `labelGroupIndex` | JSON バックアップ（`FolderLevelMappingBackup`）と DB 列 |
| `singleLabelGroup` | `folderLevelMapping.assignment` の生値 |

> **一括置換の前に「その綴りはどこかへ書き出されているか」を数えること。**
> 壊れ方は「エラーではなく既定値へ落ちる」形なので、気づきにくい。

#### 設定を 1 つ足すときに繋ぐ場所は 6 つある

**どれも既定値付きの引数なので、繋ぎ忘れてもコンパイルは通り、黙って既定に
落ちる。**[ID-13] を足したときに `settingsSnapshot` への 1 行を落とし、
「設定は保存されているのに走査の挙動が変わらない」状態を作った——DB を覗くと
正しい値が入っているので、**保存側を何度見ても原因が分からない**。

| # | 繋ぐ場所 | 落とすと |
|---|---|---|
| 1 | `LibrarySettingsPayload` のプロパティ | — |
| 2 | 同 `init(...)`（引数と代入）| 呼び出し側がコンパイルエラーになる（唯一気づける）|
| 3 | 同 **`init(from:)` の `decodeIfPresent`** | 保存はできるが読み戻せない。画面上は「設定しても次に開くと戻る」|
| 4 | `LibrarySettingsDraft`（編集用）| 設定ウインドウで触れない |

（標本は**必ず既定と違う値**にすること。既定のままだとデコードで落ちても
再エンコードが一致して空振りする）。**5 を捕まえる静的な手段は無い**ので、
その設定が実際に挙動を変えることを end-to-end のテストで固定する
——[ID-13]（現在は撤回済み [§19.8]）では `IdentityMatchPolicyScanTests` が
それにあたった。

#### `targetExtensions` を空で登録してはならない [AL-11][IF-01]

新規ライブラリには**要件定義書 11.4 節の既定**
（`zip, cbz, rar, cbr, 7z, cb7, pdf, epub`、`AppDefaults.Library.targetExtensions`）
を入れる。テンプレート（`LibraryTypeTemplate`）はこの値を持たないので、
`LibraryRepository.register` が入れるのが正しい場所になる。

**空集合は「既定」ではなく別の意味を持つ。** `LibraryEnumerator` は空を
「拡張子で絞らない＝すべてのファイルが対象」と解釈するため、空のまま登録すると
初回スキャンが `.DS_Store` やメモの `.txt` まで蔵書として取り込む。ブックフォルダ
の判定 [IF-01] も「直下に対象拡張子ファイルが 0 件」を条件にするので、空だと
画像フォルダが 1 冊と見なされなくなる。

以後の変更はライブラリ設定ウインドウ（2-12）が担う。

### ラベルフィルタ [PF-12][DB-01][LF-08〜LF-10]

**メモリ上の索引は持たない。**グループごとの `IN` を `INTERSECT` で畳むだけで
「グループ内 OR × グループ間 AND」がそのまま表現できる [T-03 実測]。

```sql
SELECT … FROM managedFile
WHERE libraryID = :lib AND state = 'active' AND isArchived = 0
  AND id IN (
        SELECT fileID FROM fileLabel WHERE labelID IN (:g1…)   -- グループ 1 の OR
  INTERSECT
        SELECT fileID FROM fileLabel WHERE labelID IN (:g2…)   -- グループ 2 の OR
  )
ORDER BY … LIMIT :limit OFFSET :offset
```

| # | 要件 |
|---|---|
| FI-01 | 上記 1 本の SQL で完結させる。フォールバック経路を設けない [DB-01] |
| FI-02 | フィルタ結果から `state = 'trashed'` [TR-02] と `isArchived = 1` [LF-13][FA-05] を除外する |
| FI-03 | 5 万件で 500ms 以内 [PF-03]。**実測 18〜182 ms**（該当件数が多いほど遅い。最悪は全件該当）|
| FI-04 | オフラインのライブラリは対象にしない |
| FI-05 | 一覧は常に `LIMIT` / `OFFSET` でページングする [PF-10]。全件を materialize しない |

#### フォルダ表示モードへ効かせる 2 つの問い合わせ [VM-02][LF-14]（2-8 で追加）

中央ペインは **DB の一覧を描くのではなく、実体の一覧を絞る**（理由は 14章 §14.2）。
そのため「どの行を残してよいか」だけを問う経路が要る。`query` の結果を呼び出し側で
畳む形にはしない——フィルタが緩いとライブラリのほぼ全件を持ち出すことになる [FI-05]。

| API | 何を返すか | いつ使うか |
|---|---|---|
| `matchingChildNames(_:)` | `scope` のフォルダ**直下の子の名前**。深い階層の該当は最初のパス成分（＝直下フォルダ名）へ畳まれる | 通常の一覧。**1 度の問い合わせで「該当ファイル」と「該当を配下に持つフォルダ」が両方**得られる [VM-02] |
| `matchingRelativePaths(_:among:)` | 候補の相対パスのうち該当するもの | 再帰検索の結果 [LF-14]。直下の名前では 1 件ずつ見分けられない |
| `bookFolderChildNames(libraryID:relativePath:)` | **直下のブックフォルダの名前** | フォルダ表示モードの印 [IF-17]。**畳まない**——ブックフォルダ「を含む」フォルダは通常のフォルダで、印を付ける対象ではない |

```sql
-- matchingChildNames: :off は `substr` へ渡す 1 起点の位置（`sqliteOffsetAfter`）
SELECT DISTINCT CASE
    WHEN instr(substr(relativePath, :off), '/') = 0 THEN substr(relativePath, :off)
    ELSE substr(relativePath, :off, instr(substr(relativePath, :off), '/') - 1)
END FROM managedFile WHERE …
```

- `scope` の `recursive` は**無視して必ず配下全体**を見る。直下だけに絞ると「該当を
  配下に持つフォルダ」を落とし、フィルタを掛けた瞬間に下の階層へ掘れなくなる。
- `matchingRelativePaths` は候補を **900 件ずつに分けて**問う。SQLite のホスト変数の
  上限（版により 999 まで下がる）を避けるためだが、**実際に効くのは速度**——
  1,805 件を 1 回で問うと 0.20 秒 → 11.14 秒になる [実測]。

#### ライブラリ表示モードへ効かせる問い合わせ [VM-10〜VM-12]（2-9 で追加）

こちらは向きが逆で、**DB の行そのものを描く**（14章 §14.3）。

| API | 何を返すか |
|---|---|
| `query(_:)` → `FilePage` | 条件に合う行（`LIMIT`/`OFFSET`）と、**絞り込み後の総数** |

- `scope` は `.folder(path:, recursive: true)`。**`recursive` を落とすと
  サブフォルダの本が 1 件も出ない**——ライブラリ表示モードは現在フォルダ
  **配下**をフラットに出すもので、範囲を現在フォルダに限る [VM-11] のは
  `path` のほうが担う。

#### 検索キーの組み立て [SR-03][SR-06][DB-03]（2-9 の残りで変更）

`managedFile.searchKey` は**ファイル名 stem ＋ タイトル ＋ シリーズ名**を
連結したもの。ライブラリ表示モードの検索がタイトル名・シリーズ名も対象にする
[SR-03] ため。組み立ては `ManagedFileSearchKey`（`QooPersistence`）1 箇所。

- **部品は U+001F（`TextNormalizer.searchKeyPartSeparator`）で繋ぐ。** 空白で
  繋ぐと `normalize` の空白畳み込みで 1 本の文字列になり、**部品をまたいだ語が
  当たる**（`作品A` ＋ `巻` で `"A 巻"` に当たる）。U+001F は幅畳み込みの写像域
  （U+FF01〜FF5E・U+3000）の外・`lowercased()` で不変・`Whitespace.isWhitespace`
  が偽なので `normalize` を素通りし、**利用者が検索欄へ打つ手段が無い**ので
  問い合わせ側の鍵には決して現れない。
- 同じ値は 1 つだけ持つ（stem とタイトルが一致するのは自動抽出ではごく普通で、
  落とさないと索引 `mf_search` が理由もなく倍になる）。
- 書き込み口は 4 つ。**`updateInPlace` は stem だけ**を書き、最終形は直後に走る
  `applyParsedFields` が書く（走査は `ScanEngine` の ②→④ でこの 2 つを必ず対に
  して呼ぶ）。**この対を崩す経路を作らないこと。**
- **書いた値ではなく行を読み直して組み立てる**（`refreshSearchKey`）。
  `applyParsedFields` の `title` は保護スコープを見て
  据え置かれることがあり、渡された値から作ると手動編集した行だけ鍵がずれる。
- 既存 DB は**再スキャン任せ**［ユーザー判断］。`searchKey` は再生成可能列。

> **`LibrarySettingsPayload` にフィールドを足したら、`init(from:)` にも
> デコードの行を足すこと。** あの初期化子は全キーを手で `decodeIfPresent` して
> いる（古い JSON を読めるようにするため）ので、**書き忘れても
> コンパイラは何も言わず、読まれないまま既定値に落ちる**——保存はできているのに
> 読み戻せない、という最も分かりにくい形になる。[IF-18] の設定を足したときに
> 実際にこの穴へ落ちた。忘れたら
> `LibrarySettingsPayloadTests.everyFieldSurvivesARoundTrip` が落ちる
> （エンコード → デコード → 再エンコードを突き合わせるので、**フィールドを
> 列挙せずに**検査できる）。
- `totalCount` は毎ページ読み直す。**走査は一覧を見ている最中にも走る**
  [SY-01] ので、古い総数のままだと「もう無いのに読み続ける」か「まだ
  あるのに止まる」のどちらかになる。行が挿入されて `offset` がずれた
  ときのために、呼び出し側（`LibraryContentModel`）が重複も落とす。
- 並べ替えは `orderClause` が担う。**メモリ上で並べ替え直さない**
  ——ページングと両立しない（読み込んだぶんの中でだけ正しくなる）。

## 7.5 リポジトリ [A-02]

**プロトコルと値型は `QooKit`**（`Foundation` のみに依存）、**GRDB 実装は
`QooPersistence`**。`QooApplication` はプロトコルにのみ依存し、GRDB を知らない。

```swift
// QooKit — ポート
public struct LibraryID: Hashable, Sendable, Codable { public let rawValue: Int64 }
public struct FileID:    Hashable, Sendable, Codable { public let rawValue: Int64 }
public struct LabelID:   Hashable, Sendable, Codable { public let rawValue: Int64 }
public struct FieldID: Hashable, Sendable, Codable { public let rawValue: Int64 }

public protocol LibraryRepository: Sendable {
    func libraries() async throws -> [LibrarySummary]
    func library(id: LibraryID) async throws -> LibrarySummary?
    func settingsSnapshot(libraryID: LibraryID) async throws -> LibrarySettingsSnapshot
    func register(url: URL, typeID: LibraryTypeID, displayName: String) async throws -> LibraryID  // [RG-01]
    func unregister(id: LibraryID, keepLabels: Bool) async throws                                   // [RG-06]
    func updateSettings(_ mutation: LibrarySettingsMutation) async throws
}

public protocol ManagedFileRepository: Sendable {
    func find(identity: FileIdentity) async throws -> FileID?                              // [ID-02]
    func findCandidates(relativePath: String, filename: String, size: Int64,
                        libraryID: LibraryID) async throws -> [ReidentificationCandidate]  // [ID-03]
    func upsert(_ snapshot: FileSnapshot) async throws -> FileID
    func upsertBatch(_ snapshots: [FileSnapshot]) async throws -> [FileID]                 // [HP2-02]
    func markOrphaned(_ ids: [FileID]) async throws                                        // [ID-06]
    func markTrashed(_ ids: [FileID], at: Date) async throws                               // [TR-01]
    func purgeExpiredTrashed(retentionDays: Int) async throws -> Int                       // [TR-06]
```

### 評価の書き込み [RA-01〜RA-08]

`filesInSameSeries(as:)` は**シリーズ名ではなく基準のファイルの `FileID` を取る**。
呼び出し側にシリーズ名を渡させると正規化の責務が UI 側へ移り、表記ゆれのある巻が
黙って対象から漏れる——漏れたことは件数を数えても分からない。基準の行が持つ
正規化済みの `seriesKey`（索引 `mf_lib_series`）でそのまま引けるので、ライブラリの
取り違えも構造的に起きない。返す範囲は `.trashed` **以外**（孤立・オフラインは含む
[ID-08]）。

`setRating` は 900 件ずつに分けて書く（`matchingRelativePaths` と同じ事情）。
**この分割は変異検証では空振りする**——この環境の SQLite はホスト変数の上限が
高いため、外しても結果は正しい。壊れるのは速度のほうなので外さないこと。

決定の全体は 14章 §14.4「評価」が持つ。

### ラベルの付け外し [RL-01〜RL-07][RP-02]

`assignments(fileIDs:)` は**複数ファイルの紐づけを 1 度に読む**。右ペインは
選択が変わるたびに読み直すので、1 件ずつ引くと選択の数だけ読み取りトランザクションが
開く。読み取りも `setRating` と同じ 900 件ずつに分ける（**この分割は変異検証では
空振りする**——壊れるのは速度のほう）。

`applyAssignments(labelID:_:protectedScopes:)` は 1 つのラベルの紐づけを、
ファイルごとに指定した状態へ揃える。`isAssigned` が `false` の項目は行ごと消す。

- **`execute()` と `undo()` がどちらもこれを使う。** 戻すことも「指定した状態へ
  揃える」ことに他ならないので、復元のための別 API を作らない。
- **保護スコープも同じトランザクションで書く** [PR-03]。別々に呼ぶと「ラベルは
  変わったが保護が付いていない」状態があり得て、次の走査で手で付けたラベルが
  黙って消える。**引数にすることで呼び出し側が忘れられない**。
- **ファイルごとに違う集合を渡せる。** 一律に戻すと、元から保護されていた
  ファイルの保護まで落とす（評価で「変更前の値を 1 件ずつ持つ」と決めたのと
  同じ [RA-06]）。
- **1 トランザクションで書く** [RP2-04]。一括付与 [RP-02] の途中で失敗したときに
  半分だけ付いた状態を残さない。**この原子性は変異検証では空振りする**——失敗を
  注入しない限り、1 件ずつのトランザクションに割っても結果は同じになるため。

`replaceAutoLabels` は**保護されたフィールドに一切触れない** [PR-01][PR-02]
——消さないだけでなく**付け足しもしない**。保護は「このフィールドの状態は
利用者が決めた」という意味なので、走査が横から足すのも約束違反になる。
判定は**その関数の中**で行う（`managedFile.protectedScopes` と
`label.labelGroupId` を読む）——呼び出し側に渡させると、次に足す呼び出し元が
忘れる（`embeddedMetadataCache` の区切りを呼び出し側に求めなかったのと同じ理由）。

決定の全体は 14章 §14.4「ラベル設定」が持つ。

### タイトルの書き込み [RP-10〜RP-12]

`setFields(_:id:protectedScopes:)` は `title` / `seriesName`（＋ `seriesKey`）/
巻数 / `authorName` と**保護スコープ**を**まとめて**書く。手動編集
[RP-10][RP-13][RP-14] も「ファイル名から再取得」[RP-12] も同じ API を通る
——**書き換える列の数が違うだけの同じ操作**なので分けない（`SetRatingCommand`
を単発と「全巻に適用」で共有しているのと同じ理由）。

- **`seriesKey` はリポジトリが導出する** [3.8 節]。呼び出し側に正規化させると
  畳み込みが 2 箇所に散り、手で直したシリーズ名では「シリーズ全巻」[RA-04] が
  引けなくなる——しかも件数を見ても気づけない。
- **保護は見ない。** `applyParsedFields` のように据え置く細工はしない
  ——守る側（走査）と、意図して書き換える側（右ペイン）は別の操作である。
  代わりに**保護スコープを引数で受け取り、同じトランザクションで書く** [PR-03]
  ——値と印を別々に書く経路を残すと、「値は変わったが保護が付いていない」
  状態があり得る。
- **再スキャンからの保護は `applyParsedFields` が担う**——基本情報スコープが
  保護されていれば、タイトル・シリーズ名・巻数・著者名の**4 つとも**据え置く
  [PR-02]。置き換える前はタイトルだけを守っており、手で直したシリーズ名は
  次の走査で黙って自動値へ戻っていた。**`lastParsedFormatID` は保護されていても
  更新する**——あれは走査の観測結果であって利用者が決めたメタデータではなく、
  止めると未整理一覧 [UR3-01] の判定が保護済みのファイルだけ古いまま凍る。
  これは v1 の実装から入っており、2-10 では書き手が現れただけ。

決定の全体は 14章 §14.4「タイトル編集」が持つ。

### カバー画像の書き込み [CV-02〜CV-08]

`setCover(_:id:)` は `coverImageSource` と `coverImageRef` を書く。

- **`.userSpecified` 以外では `ref` を消す。** 残ると「自動に戻したのに複製が
  参照されたまま」になり、起動時の掃除 [CV-06] がその複製を永久に捨てられない。
  上位（`CoverEditorModel.revert()`）は常に `ref` が `nil` の割り当てを渡すので
  普段は表に出ない不変条件だが、**変異検証で上位経由のテストだけでは空振りする
  と分かった**ため、リポジトリ層で直に固定してある。
- **サイドカー [IV-02②] は DB に書かない。** 仕様の疑似コード [9章 §9.6] も②で
  DB を見ずに実体を探している。保存すると、あとから `covers/` に画像を置いた・
  消したときに DB が古いまま残り、画面と実体が食い違う。
- **複製そのものの作成・削除はここでしない。** DB は参照だけを持ち [CL-05]、
  実体の管理は `UserCoverStore` の仕事——混ぜると「DB は書けたが複製が無い」
  「複製はあるが誰も参照していない」のどちらへも倒れ得る。
- `userCoverRefs(libraryID:)` が起動時の掃除の入力になる。**ユーザー指定のもの
  だけ**を返す。

**走査は `coverImageSource`/`coverImageRef` に触れない**（`updateInPlace` の SQL に
列が無い）ので、差し替えたカバーが再スキャンで消えることはない。

決定の全体は 14章 §14.4「カバー画像」が持つ。

### ラベルそのものの編集 [LE-07〜LE-11][LB-05〜LB-07][CO-06]

付け外し（上記）が**ファイルとラベルの関係**を書き換えるのに対し、こちらは
**ラベルの行そのもの**を書き換える。決定の全体は 15章 §15.2 が持つ。

| API | 何をするか |
|---|---|
| `deleteLabels(_:)` | 削除 [LE-07]。紐づけは `fileLabel` の `ON DELETE CASCADE` が消す [LE-08][LB-05] |
| `setColor(_:hex:)` | ラベル固有色 [LE-10][CO-06]。`nil` でグループ色の継承へ戻す |
| `merge(_:into:)` | 統合 [LB-07]。`origin` は `LabelOrigin.merging` が決める（下記）|
| `rename(_:to:)` | 改名 [LB-06]。衝突は `LabelEditError.nameAlreadyExists` |
| `snapshot(labelIDs:)` / `restore(_:)` | 削除・統合の Undo 用（下記）|

#### `snapshot` / `restore` は「ちょうどその状態へ揃える」

`applyAssignments` と同じ形にしてある——**戻すことも「ある状態へ揃える」ことに
他ならない**ので、復元専用の別の意味を持つ API を作らない。写しに含まれない
紐づけは消える。

- **`id` を明示して `INSERT` する。** `label.id` は AUTOINCREMENT なので削除された
  ID は再利用されず空いたまま残り、元の ID をそのまま取り戻せる［実測］。
- **`manuallyRemoved` の行も写しに含める。** 落とすと ⌘Z のあと再スキャンで
  ラベルが復活する [RC-04]。
- **相手のファイルが消えていたら飛ばす。** `INSERT OR IGNORE` は外部キー違反を
  無視しない（SQLite は OR IGNORE を UNIQUE / NOT NULL / CHECK にしか効かせない）
  ので、`WHERE EXISTS` で自分で外す——1 件の消失で Undo 全体が失敗しないように。
- **1 トランザクションで書く。** 統合の Undo は 2 件をまとめて戻すので、途中で
  切れると「統合元は戻ったが統合先は統合後のまま」というどちらでもない状態が残る。

#### `merge` は `origin` を突き合わせてから移す

以前は `UPDATE OR IGNORE fileLabel SET labelId = ?` 1 本で移していたが、それだと
移動先の値が無条件に残り、統合元が `manual`・統合先が `manuallyRemoved` の
ファイルで**手動付与が黙って消えていた**。両方が付いているファイルを先に
`LabelOrigin.merging`（manual > auto > manuallyRemoved）で書き換えてから移す。

**グループをまたぐ統合は断る** [LB-07]。ラベルの一意性はグループ内で定義されて
おり [LB-01]、またぐと「グループを移す」という別の操作になる。

#### `labels(groupID:)` は件数を 1 つ返し、非表示のものも返す（v3 ステージ 11）

件数は**生きている実体の数**だけ（`state = active` かつ保管庫の外 [FA-05]）。
かつては意味の違う 2 つを返していたが、0 件ラベルの赤字 [LE-04] が撤回された
[LA3-04] 時点で区別の存在理由が消えた——詳細は 15章 §15.2。

**非表示のものも返す** [LA3-03]。出し分けは呼び出し側の都合（フィルタは隠す
[LA3-05]、フィールド編集は控えめに見せる）で、リポジトリはそれを知らない
——判定は `LabelSummary.isVisible`（`!isHidden && fileCount > 0`）が 1 箇所で持つ。

**非正規化列は撤去した** [DB-02 撤回]。実測（10 万件・50 万紐づけ、Release）で
旧経路 109.4 ms に対し 105.3 ms——**旧実装が既に相関副問い合わせを 1 本
走らせていた**（`fileCountIncludingArchived` のため）ので、列を持つ費用は
速度ではなく「数え直しを忘れるとずれる」危険だけだった。

#### `archivedLabelCounts()` は撤回（v3 ステージ 11）

ラベル保管庫の整理ウインドウ [15章 §15.3] と一緒に廃止した。

### 孤立ファイルの整理 [OR-01〜OR-05][ID-05][ID-07]（2-14 で追加）

決定の全体は 15章 §15.7 が持つ。ここは問い合わせと書き込みの形だけ。

| API | 何をするか |
|---|---|
| `orphanedFiles(libraryID:)` | 孤立レコード＋ラベル件数 [OR-01] |
| `orphanedFileCounts()` | ライブラリごとの孤立件数（左ペインの出し分け用、1 問い合わせ）|
| `deleteFiles(_:)` | 不要な孤立レコードを消す [OR-04] |
| `fileSnapshots(ids:)` / `restoreFiles(_:)` | 削除の Undo 用 |

かつてあった候補・確認まわりの API（`identityMatchesAwaitingDecision` /
`acceptIdentityMatches` / `rejectIdentityMatches` / `clearIdentityRejections` /
`reattachOrphan` / `identity(of:)`）は、同一性確認の撤去 [§19.8] とともに
消えた——差し替えは走査の `reidentify` が自動で引き継ぐ。

#### 確認待ちのテーブルは撤去済み [ID-09〜ID-15 撤回、§19.8]

`identityPending`（v7）と `identityRejection`（v5）は、差し替えの確認
ダイアログ・3 段階ポリシーの撤回とともに **v8 で DROP した**（ステージ 1、
§19.10）。差し替えは走査がガード付き [ID3-08] で常に自動的に引き継ぐので、
「疑った組を覚えておく」必要も「別物だと決めた組を覚えておく」必要も
無くなった。DROP 時に残っていた確認待ち・却下の記録は確認されないまま
消える——孤立レコード自体は残るので、§15.7 の一覧から片付けられる。

再照合（`findCandidates` → `reidentify`）は `reconcile` の中だけで完結し、
孤立一覧 [OR-01] は候補を持たない（結び直しの API も撤去済み）。

#### `fileSnapshots` / `restoreFiles` は全列を持つ

`snapshot` / `restore`（ラベル）と同じ「ちょうどその状態へ揃える」形。
**再生成可能な列 [DB-03] も含めて全部**写す——孤立レコードには実体が無く、
走査が埋め直す機会が来ないため。

**列を足したら写しの両方向にも足す必要がある。** 忘れると ⌘Z のあと黙って値が
変わるので、往復テスト（`OrphanRepositoryTests.everyColumnSurvivesADeleteAndRestore`、
行を JSON へ符号化して丸ごと突き合わせる）で機械的に捕まえる。
**Optional をすべて非 nil で埋めた標本**を使うこと——`JSONEncoder` は nil の
キーを省くので、埋めないと写し漏れがあっても両側から同じように消えて一致する。

#### ~~`state` が変わったらラベルの件数を数え直す~~ **撤回（v3 ステージ 11）**

`setState` / `markUnseenAsOrphaned` / `deleteFiles` / `restoreFiles` の 4 つで
数え直していた処理は、非正規化列の撤去 [DB-02 撤回][§19.13 #1] とともに削除した。

> **この節が記録していた穴こそ、列を撤去した理由である。** 2-14 で
> 「走査が孤立にした後も、ゴミ箱へ入れた後も件数が古いまま残る」欠陥を直し、
> 2-11 で**保管庫について同じ穴をもう一度**踏んだ（下記）。
> 「`state` や `isArchived` を変える経路を新設するたびに数え直しを足す」は
> 覚えていられる約束ではなく、**列を持たなければそもそも要らない。**

### 未解決ファイルの記録と整理 [AL-30〜AL-34][UR-01〜UR-06]（2-7 / 2-14 で追加）


**記録と削除を 1 つの呼び出しにまとめてある。** 走査は収束型 [FO-20] なので、

別経路」にすると、フォーマットを足して解決したのに一覧に残り続ける、という
食い違いが呼び出し側の書き忘れで起こりうる。

書くのは `ScanEngine.reconcile` の 1 箇所だけで、判定（`EmbeddedMetadataMerge
.isUnresolved`）は**走査と再マッチングで共有する** `applyResolution` の中にある
——別々に書くと「走査では未解決なのに再マッチングでは解決する（またはその逆）」
という、画面からは理由の読み取れない食い違いになる。

#### 名前が変わったら無視を解く [AL-33]［ユーザー判断、2026-08］

無視は「**この名前は**どのフォーマットにも当てはまらないと判断した」という意味
なので、名前が変われば前提そのものが消える。`unresolvedFile.filename` に記録して
おき、`ON CONFLICT` の中で突き合わせる:

```sql
ON CONFLICT(managedFileId) DO UPDATE SET
    isIgnored = CASE WHEN unresolvedFile.filename <> excluded.filename
                     THEN 0 ELSE unresolvedFile.isIgnored END,
    filename = excluded.filename
```

`DO UPDATE SET` の右辺は**更新前の行**を見る（SQLite の仕様）ので、同じ文の中で
`filename` を書き換えても `CASE` の判定は壊れない。**名前が同じまま中身だけ
差し替えられた場合 [ID-13] は無視を保つ**——名前についての判断は生きているため。

`detectedAt` は更新しない。「いつから片付いていないか」を表す値で、走査のたびに
今へ寄せると意味を失う。

#### 「最も近いフォーマット」は毎回書き直す [UR2-05]（2026-09-01、ステージ 9）

`nearestFormatSource` / `nearestFormatReach` は**列は v1 からあったが、
ステージ 9 まで誰も書いていなかった**。走査と再マッチングが `ON CONFLICT` の中で
毎回上書きする——据え置くと、既に消したフォーマットを勧め続けることになる。

**持つのはフォーマットの本文（UUID ではない）。** フォーマットは編集も削除も
されるので、ID を覚えても後から引けるとは限らない。表示側はこの 1 列だけで
用が足りる。推定の規則そのものは 04章 §4.11。

**1 件だけの読み出し口を分けてある**（`unresolvedHint(id:)`）——右ペインは選択が
変わるたびにこれを引くので、一覧（`unresolvedFiles`）を引いて絞ると、5,000 件の
未整理を抱えたライブラリで選択のたびにその全件が流れる。

**行あたりの束縛変数が 4 → 6 に増えた**ので、1 文で扱う行数を 200 → 150 へ
下げてある（`maxBoundParameters` = 900）。**この値を戻してもこの環境のテストは
通る**（`SQLITE_MAX_VARIABLE_NUMBER` が 32,766 あるため）——壊れるのは上限の
低いビルドだけなので、通ることを理由に上げないこと（`setRating` の 900 件分割と
同じ事情）。

#### 一覧に出さないもの

| 除外 | 理由 |
|---|---|
| `state != .active` | 実体が見つからなくなったものは「見つからないファイル」[OR-01] の担当。両方に出すと同じ 1 件が 2 つの画面に別の意味で並ぶ（片方で消して、もう片方にはまだ居る、という読めない状態になる）|
| `isArchived` | 保管庫へ送ったファイルは蔵書の一覧から外れる [FA-05]。未解決一覧にだけ残ると「片付けたのに減らない」ことになる（**2-11 が入ったので実際に効くようになった**）|
| 無視したもの（既定）| [AL-33]。**行は残す** [UR2-04]——消すと次の走査でまた未解決として現れ、無視した意味が無くなる。`includeIgnored: true` で戻せる |

`unresolvedFileCounts()` は **`UnresolvedCounts`（`pending` / `ignored`）** を返す。
左ペインの「N 件」は `pending`（＝片付けるべき件数）だが、**空状態の文言は
`ignored` を知らないと嘘になる**——無視して空にしただけなのに「すべて一致して
います」と言ってしまう［実機検証で発見］。1 つの数字に畳まないこと
（`LabelSummary` が件数を 2 つ持つ [LE-05][FA-05] のと同じ形）。

#### `isIgnored` は再生成不可能 [MG-22][MG-23]

走査からは作り直せない**利用者の判断**（`origin == 'manual'` と同じ性質）なので、
JSON バックアップに含める。`unresolvedFile` は `managedFile` と 1:1 なので、
`FileBackup.isUnresolvedIgnored` としてファイルの属性へ畳んである
（`RegenerabilityRegistry` の網羅性テストがこの対応を強制する）。

**取り込みは行が既にあるときだけ立てる。** 復旧手順は「有効化 → 再スキャン →
取り込み」[MG-24] なので、取り込みの時点で走査が未解決の行を作り終えている。
行が無いのは「いまは解決している」という意味なので、そこへ無視を作ると
解決済みのファイルに人の判断が蘇ることになる。

**`Bool?` で持つ。** このキーを持たない版 1／2 の文書があり、非 Optional にすると
`keyNotFound` で**文書全体の取り込みが失敗する**（合成された `Decodable` は
プロパティの既定値を使わない [実測]）。読み込みは `<=` 判定 [IE-14] なので
`schemaVersion` は上げていない。

ときだけ無視」と読めば、見張りも行の掃除も要らない。`unresolvedFile.filename` は
走査が突き合わせているが、この提案は走査の外にあるので同じ手が使えない。

**行は残す。** 名前を戻せば無視も戻る。

### シェルフ（保存した絞り込み）[SH-01〜SH-12]（ステージ 8 で追加）

```swift

    func create(libraryID: LibraryID, name: String,
                condition: ShelfCondition) async throws -> ShelfID

```

**条件は JSON 1 列（`conditionJSON`）で持つ** [SH-05]。`library.settingsJSON` と
同じ判断で、覚える項目が増減しても移行が要らない。

**ラベルへの外部キーを張らないのは意図的**。張ると連鎖削除が条件を消し、
**ラベル削除の ⌘Z（同じ行 ID で戻る）でシェルフが生き返らなくなる**——
`label.id` は AUTOINCREMENT で再利用されないので、ID を持ち続けるほうが
往復に耐える。解決できない ID は読み出し側（`ShelfCondition.groupedSelection`）
が落とす。

一方 **`libraryId` は単一参照なので外部キーを張る**——`protectedToken` が
多相参照ゆえに連鎖できず孤児を積み上げていた轍 [PT-08] は踏まない
（`PRAGMA foreign_key_check` が空であることを連鎖の根拠にできないのは
そちらの節のとおり）。

**読めない `conditionJSON` でも行を落とさない。** 1 件壊れただけで左ペインから
シェルフが全部消え、直す手立ても無くなる。空の条件として出せば、名前は見える
ので削除・上書き保存で片付けられる [ER-01 の精神]。

**JSON バックアップでは行 ID を持ち出さない** [SH-12][JS-04]。ラベルは
`groupIndex` + ラベル名へ翻訳して出し、取り込みで引き直す——行 ID を書くと、
別の環境で取り込んだときに無関係なラベルを指す。取り込みは**名前で重ねる**
（文書に無いシェルフは消さない——復旧のつもりの取り込みで別の絞り込みを失う
経路を作らない [JS-05 と同じ判断]）。

##### 仕様との差異 3 つ（いずれも意図的。戻すなら理由ごと検討すること）

1. **取り込みはライブラリの行を作らない。** ライブラリを作るには
   Security-Scoped Bookmark が要り、**それは環境固有なので JSON に持てない**
   （別マシンでは解決できず、同じマシンでもフォルダを選び直せば別物になる）。
   DB に無いライブラリは `missing` として報告するに留める。したがって
   MG-24 の復旧手順は「新規ストア → インポート → 再スキャン」ではなく
   **「有効化 → 再スキャン → インポート」**になる。UI はこの順序を案内する。
2. **ファイルの行も作らない** [ID-06]。実体を伴わないレコードを増やすと、
   次の走査でそれが孤立として現れ「消えたファイル」の報告に混ざる。
   走査が作った行に、評価・手動ラベル・手動タイトルを載せ直す形にした。
3. **ラベル紐づけの主キーは `groupIndex`**（JS-04 は「グループ名」と書く）。
   グループ名は後から変えられるので、名前だけを頼りにすると改名した瞬間に
   別物になる。名前も併記してあるので、将来ライブラリ間マージを作るときは
   そちらを使える。

##### 書き出さないもの（**再スキャンが作り直せるものは持たない**）

**保護されていないフィールドの**ラベル紐づけ、**保護されていない**基本情報
（タイトル・シリーズ名・巻数・著者名）[PR-01]、`coverImageSource = 'auto'` の
カバー参照 [IV-03]、そして
**再生成できる情報しか持たないファイルの行そのもの**。10 万件の蔵書で
JSON が無意味に膨らむのを避けるためで、`FileBackup.carriesUnrecoverableData`
が唯一の判定点になっている（書き出しと取り込みで条件がずれないよう 1 箇所に閉じた）。

**この設計に伴い `ManagedFileRecord.regenerableColumns` へ `fileSize`／
`createdAt`／`modifiedAt` を追加した**——いずれも走査が実体から読み直して
必ず上書きするので、JSON に持つと「古い値で正しい観測を上書きする」危険
だけが残る。網羅性テストがこの分類と DTO の一致を見張っている。
