# 07. 永続化 — SQLite スキーマ・移行・リポジトリ

対応要件: DB-01〜DB-04 / MG-01〜MG-25 / 6 章全体 / IE-01〜IE-16 / BK-01〜BK-05 / PF-12 / MT-10〜MT-16

## 7.0 なぜ SQLite（GRDB）か [設計判断、2026-08]

要件定義書 v2.8 までは SwiftData を前提としていた。フェーズ 2 の着手時に
**本プロジェクトの実スキーマ・実ファイル名・実機で測った**ところ、SwiftData は
想定規模（`C-07`: 1 ライブラリ 5 万・全体 10 万ファイル）の境界線上にあることが
確認できたため、実装前に SQLite（GRDB 7）へ切り替えた。

測定条件・全結果・そこから確定した設計判断は `Spikes/README.md` の
**「T-03 / T-04: 永続化層の性能」**にある。**このファイルの設計を変えるときは、
まずそこを読むこと。** 要点だけ:

| # | 実測が確定させたこと |
|---|---|
| 1 | PF-01〜PF-07 をすべて満たす。最も余裕が小さい PF-03（ラベルフィルタ）でも最悪 182 ms 対 目標 500 ms |
| 2 | **`LabelIndex`（メモリ上の索引）は作らない** [T-03]。「グループ内 OR × グループ間 AND」は SQL の `INTERSECT` で表現できる。索引を二重に持つと DB との整合性維持が新たな危険源になるだけ |
| 3 | **内部の行 ID は `Int64`（rowid）**。UUID 文字列に対し投入 3 倍速・DB サイズ 1/2.8 |
| 4 | **FTS5 を使わない**。`LIKE '%…%'` の全走査が 10 万件で 20.7 ms |
| 5 | **GRDB は協調スレッドプールの外（自前の直列キュー）で待つ**。8章 §8.11 の `FileIO` と同じ性質を持つため、DB のために別の逃がし先を用意しなくてよい [NV6-01][NV6-04] |

## 7.1 接続の構成 [ST-01〜ST-07]

```swift
/// アプリで単一 [ST-01]。全ウインドウ・全タブが共有する [ST-02]。
public final class QooDatabase: Sendable {
    private let pool: DatabasePool

    public static func open(at url: URL) throws -> QooDatabase
}
```

| # | 要件 |
|---|---|
| CN-01 | `DatabasePool`（WAL）を 1 つだけ持つ [ST-01][ST-02]。読み取りは並行、書き込みは直列化される |
| CN-02 | `PRAGMA journal_mode = WAL` / `synchronous = NORMAL` / `foreign_keys = ON` / `busy_timeout` を `Configuration.prepareDatabase` で設定する |
| CN-03 | 長時間処理は書き込みトランザクションを細かく区切る [ST-04][SE3-05]。WAL により読み取りは妨げられない（実測: 書き込み中の読み取り 3 ms）|
| CN-04 | メインスレッドから同期の読み書きを行わない [ST-05]。**ただし DB は常にローカル**（Application Support 配下）なので、8章 §8.11 の `FileIO` へ逃がす必要はない ——GRDB 自身が協調プールの外で待つ [実測] |
| CN-05 | 層をまたぐ受け渡しは `Sendable` な値型のみ [ST-06]。`Database` / `Row` / `Statement` を `QooPersistence` の外へ出さない |
| CN-06 | 書き込みは明示的なトランザクション。単位は Command の境界と一致させる [ST-07][A-03] |
| CN-07 | UI の追随は `ValueObservation` で行う。ポーリングしない |

### 置き場所

`~/Library/Application Support/qooLibrary/qooLibrary.sqlite`（`-wal` / `-shm` を伴う）。
バックアップは `backups/` 配下 [BK-01]。

## 7.2 スキーマ移行 [MG-01〜MG-04]

**v1 の時点から移行の器を用意する。** 移行対象がない段階でも、初版スキーマを
最初の移行として登録した `DatabaseMigrator` をファイルとして持つ [MG-01][MG-02]。

```swift
public enum QooMigrations {
    public static var migrator: DatabaseMigrator {
        var m = DatabaseMigrator()
        // eraseDatabaseOnSchemaChange は決して有効にしない（データを消すため）
        m.registerMigration("v1_initial") { db in … }       // §7.3
        m.registerMigration("v2_regexPatterns") { db in … }  // 下記
        m.registerMigration("v3_embeddedMetadata") { db in … } // 下記
        return m
    }
}
```

### v2_regexPatterns [2026-08]

巻数フォーマットと保護文字列を正規表現へ移す（04章 §4.6 / 05章 §5.1）。

| 対象 | 変更 |
|---|---|
| `volumeFormat.source` | `??` / `<space>` の独自記法 → 正規表現 |
| `volumeFormat.ordinalRank` | → `kind`（`volume` / `separator`）。**序列巻数の廃止に伴い、順位を持っていた行は「区切り専用」になる** |
| `protectedToken.text` | → `pattern`（完全一致のリテラル → 正規表現） |
| `volumeOutputStyle.ordinalTemplate` | 出力すべき序列が無くなったので削除 |
| `managedFile.volumeKind` | `ordinal` は取りうる値でなくなったので `none` へ |

**変換は `LegacyVolumeNotation`（`QooKit`）が行い、JSON バックアップの取り込みと
同じ関数を使う。** 片方だけ直すと、以前書き出した文書と DB とで変換結果が食い違う。

| # | 要件 |
|---|---|
| SC-01 | スキーマ移行中はアプリ終了を許可しない [LK-42] |
| SC-02 | **登録済みの移行は追記のみ。後から書き換えない** [MG-04]。適用済みの環境と食い違い、検出できない不整合になる |
| SC-03 | 移行の識別子は `v<連番>_<内容>` 形式。時系列で並ぶこと |
| SC-04 | ストア内のメタデータ（`storeMetadata`）とアプリの期待値を毎起動で突き合わせる [MG-03] |
| SC-05 | 移行は必ずテストを伴う。「1 つ前の版のスキーマでデータを作り、移行して、期待どおりになる」ことを検証する。GRDB の `migrator.migrate(_:upTo:)` で途中の版を再現できる |

### v3_embeddedMetadata [2026-08]

埋め込みメタデータの読み取り（09章 §9.9）のための列を足すだけ。**既存の行は
`metadataStamp` が NULL になり、次のスキャンで「まだ読んでいない」として扱われる**
——移行時に読みに行かない（移行はストアを開く前に走るので、ボリュームが接続されて
いるとは限らない）。

| 対象 | 変更 |
|---|---|
| `managedFile` | `metadataStamp` / `metadataSource` / `metadataJSON` / `hasVolumeConflict` を追加 |
| `library.settingsJSON` | `readsEmbeddedMetadata`（既定 `true`）と `comicInfoVolumeSource`（既定 `ask`）を追加。**JSON なので移行では触らない** — `Codable` の既定値で読める形にしておく |

**`settingsJSON` の新しいキーは `Bool?` / `String?` にはしない。** Swift の合成された
`Decodable` は**プロパティの既定値を使わず**、キーが無いと `keyNotFound` で失敗する
[実測、`AppAssociationStore` で踏んだ罠]。`LibrarySettingsPayload` は
`var readsEmbeddedMetadata: Bool = true` のように**宣言時の既定値を持つ非 Optional**
にし、`init(from:)` を手で書いて `decodeIfPresent` で読む。

### 起動シーケンス [MG-10〜MG-13][RB-03][RB-06]

```pseudo
bootstrapStore():
    if !exists(storeURL): 新規作成 → migrator.migrate() → 完了

    # [MG-12] アプリが知らない移行が適用済み = 新しすぎる。起動中止
    if try migrator.hasBeenSuperseded(db):
        abort with .schemaTooNew

    if 未適用の移行がある:
        # [MG-10] 移行前に必ずスナップショット + ストア複製
        JSONExporter.exportAll()
        pool.backup(to: backups/pre-migration-<日時>.sqlite)   # オンラインバックアップ
        do:   try migrator.migrate(pool)
        catch: 読み取り専用モードで開く + 復元を提示          # [MG-11][RB-06]
        JSONExporter.exportAll()                              # [MG-13] 移行後も自動
    if PRAGMA integrity_check が失敗:
        自動バックアップからの復元を提案                       # [RB-03]
```

**`hasBeenSuperseded` が MG-12 をそのまま満たす**——アプリが知らない識別子の移行が
適用済みなら真を返す。バージョン番号の自前比較より確実である。

## 7.3 テーブル定義

### ID の方針 [設計判断]

**内部の参照はすべて `Int64`（rowid）。**UUID 文字列は使わない（実測で投入 3 倍・
サイズ 2.8 倍の差）。JSON 入出力の同一性キーはもともと UUID ではなく自然キー
（相対パス + ファイル名 等）なので [JS-04]、外部仕様は変わらない。

**外部から参照されるものだけ**が安定した外部キーを併せ持つ:

| テーブル | 外部キー | 誰が外から参照するか |
|---|---|---|
| `library` / `temporaryFolder` | `uuid TEXT UNIQUE` | フェーズ 1 の `registeredFolders.json` の登録 ID。環境設定の「起動時に開くフォルダ」、`NavigationRoot.registeredFolder(id:)`、ウインドウ状態復元 |
| `libraryType` | `presetKey TEXT UNIQUE`（ユーザー定義は NULL）| アプリ更新をまたいだプリセットの同定 [LT-10] |
| `label` / `labelGroup` | なし。ただし `AUTOINCREMENT` | ウインドウ状態復元がラベルフィルタの選択を保持する [ST-20]。**rowid が再利用されると復元後に別のラベルが選ばれる**ため、この 2 つだけは再利用を禁じる |
| `managedFile` / `fileLabel` | なし | 生存中の参照はすべて外部キー制約（`ON DELETE CASCADE`）。操作履歴・通知は**パスとファイル名を非正規化して持つ**ため、行が消えても意味を保つ |

### 設定を JSON 列で持つ理由 [MT-10][MT-15][設計判断]

`library.settingsJSON` には、**可変長で・件数上限が将来変わりうる**設定
（区切り文字集合、保護文字列、`semanticBindings`、`labelGroupOrder`、
`targetExtensions` / `imageExtensions`、`seriesTitleCompositionFormat` 等）を
まとめて格納する。固定カラムにすると上限の引き上げがスキーマ変更を伴うため
[MT-10]。**ただし SQL で絞り込む必要があるものは列にする**——検索・フィルタ・
ソートの対象になるものを JSON へ入れてはならない。

一方 `filenameFormat` / `volumeFormat` / `folderLevelMapping` /
`protectedToken` / `volumeOutputStyle` は**優先順の並べ替え・個別の有効／無効・
編集画面での一覧**があるため、独立したテーブルにする。

#### `targetExtensions` を空で登録してはならない [AL-11][IF-01]

新規ライブラリには**要件定義書 11.4 節の既定**
（`zip, cbz, rar, cbr, 7z, cb7, pdf, epub`、`AppDefaults.Library.targetExtensions`）
を入れる。テンプレート（`LibraryTypeTemplate`）はこの値を持たないので、
`LibraryRepository.register` が入れるのが正しい場所になる。

**空集合は「既定」ではなく別の意味を持つ。** `LibraryEnumerator` は空を
「拡張子で絞らない＝すべてのファイルが対象」と解釈するため、空のまま登録すると
初回スキャンが `.DS_Store` やメモの `.txt` まで蔵書として取り込む。ブックフォルダ
の判定 [IF-01] も「直下に対象拡張子ファイルが 0 件」を条件にするので、空だと
画像フォルダが 1 冊と見なされなくなる。

以後の変更はライブラリ設定ウインドウ（2-12）が担う。

### 再生成可能性の宣言 [MG-20〜MG-23]

SwiftData 前提の `@Regenerable` プロパティラッパは使わない。**型に宣言させ、
テストで網羅性を検証する**（文字列の走査より確実で、列を足したときに黙って
漏れない）。

```swift
/// 再生成可能な列を宣言する。宣言しなかった列は「再生成不可能」とみなされ、
/// JSON エクスポートに含まれていなければテストが落ちる [MG-22][MG-23][B-13]。
public protocol RegenerabilityDeclaring {
    static var databaseTableName: String { get }
    static var allColumns: Set<String> { get }
    static var regenerableColumns: Set<String> { get }
}
```

| 分類 | 属性 | 根拠 |
|---|---|---|
| **再生成可能** | サムネイル、カバー自動抽出、`label.fileCount`、`normalizedName`、`searchKey`、`isBookFolder`、`volumeNumber`/`volumeKind`/`volumeRaw`、`fileLabel(origin = 'auto')`、**埋め込みメタデータ（`metadataStamp` / `metadataSource` / `metadataJSON` / `hasVolumeConflict`）**、`title(titleOrigin = 'auto')`、`pageCount`、`subfolderCount`、`firstImage*` | [MG-21] |
| **再生成不可能** | `fileLabel(origin = 'manual' / 'manuallyRemoved')`、`rating`、ユーザー指定カバー、手動編集 `title`、`archivedFromPath`、`isPinned`、`label.isArchived`、ラベルグループ名・色、各種設定 | [MG-22] |

## 7.4 索引と性能

| # | 要件 |
|---|---|
| IX-01 | `managedFile` の索引: `(volumeUUID, inode)` **UNIQUE**、`(libraryID, relativePath)`、`(libraryID, state)`、`(libraryID, seriesKey)`、`searchKey` |
| IX-02 | `label` に `(labelGroupID, normalizedName)` の UNIQUE 索引 [LB-01] |
| IX-03 | `label.fileCount` は増分更新する。`fileLabel` の追加・削除、ファイルの `state`/`isArchived` の変化で ±1 する [DB-02]。**実測 0.1 ms** |
| IX-04 | IX-03 の破綻に備え、手動コマンド「ラベル件数を再集計」を提供する [MX 一覧]。**実測 844 ms**（10,530 ラベル）なので、疑わしければ気軽に回してよい |
| IX-05 | 起動時に `managedFile` の総数を数え、`AppLimits.dbRecordWarningThreshold` 超過で警告する [DB-04]。**実測 6.3 ms** |
| IX-06 | `fileLabel` に `labelID` の索引を張る（ラベルフィルタの `INTERSECT` が使う）|

### ラベルフィルタ [PF-12][DB-01][LF-08〜LF-10]

**メモリ上の索引は持たない。**グループごとの `IN` を `INTERSECT` で畳むだけで
「グループ内 OR × グループ間 AND」がそのまま表現できる [T-03 実測]。

```sql
SELECT … FROM managedFile
WHERE libraryID = :lib AND state = 'active' AND isArchived = 0
  AND id IN (
        SELECT fileID FROM fileLabel WHERE labelID IN (:g1…)   -- グループ 1 の OR
  INTERSECT
        SELECT fileID FROM fileLabel WHERE labelID IN (:g2…)   -- グループ 2 の OR
  )
ORDER BY … LIMIT :limit OFFSET :offset
```

| # | 要件 |
|---|---|
| FI-01 | 上記 1 本の SQL で完結させる。フォールバック経路を設けない [DB-01] |
| FI-02 | フィルタ結果から `state = 'trashed'` [TR-02] と `isArchived = 1` [LF-13][FA-05] を除外する |
| FI-03 | 5 万件で 500ms 以内 [PF-03]。**実測 18〜182 ms**（該当件数が多いほど遅い。最悪は全件該当）|
| FI-04 | オフラインのライブラリは対象にしない |
| FI-05 | 一覧は常に `LIMIT` / `OFFSET` でページングする [PF-10]。全件を materialize しない |

#### フォルダ表示モードへ効かせる 2 つの問い合わせ [VM-02][LF-14]（2-8 で追加）

中央ペインは **DB の一覧を描くのではなく、実体の一覧を絞る**（理由は 14章 §14.2）。
そのため「どの行を残してよいか」だけを問う経路が要る。`query` の結果を呼び出し側で
畳む形にはしない——フィルタが緩いとライブラリのほぼ全件を持ち出すことになる [FI-05]。

| API | 何を返すか | いつ使うか |
|---|---|---|
| `matchingChildNames(_:)` | `scope` のフォルダ**直下の子の名前**。深い階層の該当は最初のパス成分（＝直下フォルダ名）へ畳まれる | 通常の一覧。**1 度の問い合わせで「該当ファイル」と「該当を配下に持つフォルダ」が両方**得られる [VM-02] |
| `matchingRelativePaths(_:among:)` | 候補の相対パスのうち該当するもの | 再帰検索の結果 [LF-14]。直下の名前では 1 件ずつ見分けられない |

```sql
-- matchingChildNames: :off は `substr` へ渡す 1 起点の位置（`sqliteOffsetAfter`）
SELECT DISTINCT CASE
    WHEN instr(substr(relativePath, :off), '/') = 0 THEN substr(relativePath, :off)
    ELSE substr(relativePath, :off, instr(substr(relativePath, :off), '/') - 1)
END FROM managedFile WHERE …
```

- `scope` の `recursive` は**無視して必ず配下全体**を見る。直下だけに絞ると「該当を
  配下に持つフォルダ」を落とし、フィルタを掛けた瞬間に下の階層へ掘れなくなる。
- `matchingRelativePaths` は候補を **900 件ずつに分けて**問う。SQLite のホスト変数の
  上限（版により 999 まで下がる）を避けるためだが、**実際に効くのは速度**——
  1,805 件を 1 回で問うと 0.20 秒 → 11.14 秒になる [実測]。

#### ライブラリ表示モードへ効かせる問い合わせ [VM-10〜VM-12]（2-9 で追加）

こちらは向きが逆で、**DB の行そのものを描く**（14章 §14.3）。

| API | 何を返すか |
|---|---|
| `query(_:)` → `FilePage` | 条件に合う行（`LIMIT`/`OFFSET`）と、**絞り込み後の総数** |

- `scope` は `.folder(path:, recursive: true)`。**`recursive` を落とすと
  サブフォルダの本が 1 件も出ない**——ライブラリ表示モードは現在フォルダ
  **配下**をフラットに出すもので、範囲を現在フォルダに限る [VM-11] のは
  `path` のほうが担う。
- `totalCount` は毎ページ読み直す。**走査は一覧を見ている最中にも走る**
  [SY-01] ので、古い総数のままだと「もう無いのに読み続ける」か「まだ
  あるのに止まる」のどちらかになる。行が挿入されて `offset` がずれた
  ときのために、呼び出し側（`LibraryContentModel`）が重複も落とす。
- 並べ替えは `orderClause` が担う。**メモリ上で並べ替え直さない**
  ——ページングと両立しない（読み込んだぶんの中でだけ正しくなる）。

| HP2-02 | 保存は 500 件または 1 秒のバッチ境界で行い、トランザクション境界と一致させる [ST-10][ST-13][SE3-05] |

### 評価の書き込み [RA-01〜RA-08]

`filesInSameSeries(as:)` は**シリーズ名ではなく基準のファイルの `FileID` を取る**。
呼び出し側にシリーズ名を渡させると正規化の責務が UI 側へ移り、表記ゆれのある巻が
黙って対象から漏れる——漏れたことは件数を数えても分からない。基準の行が持つ
正規化済みの `seriesKey`（索引 `mf_lib_series`）でそのまま引けるので、ライブラリの
取り違えも構造的に起きない。返す範囲は `.trashed` **以外**（孤立・オフラインは含む
[ID-08]）。

`setRating` は 900 件ずつに分けて書く（`matchingRelativePaths` と同じ事情）。
**この分割は変異検証では空振りする**——この環境の SQLite はホスト変数の上限が
高いため、外しても結果は正しい。壊れるのは速度のほうなので外さないこと。

決定の全体は 14章 §14.4「評価」が持つ。

### ラベルの付け外し [RL-01〜RL-07][RP-02]

`assignments(fileIDs:)` は**複数ファイルの紐づけを 1 度に読む**。右ペインは
選択が変わるたびに読み直すので、1 件ずつ引くと選択の数だけ読み取りトランザクションが
開く。読み取りも `setRating` と同じ 900 件ずつに分ける（**この分割は変異検証では
空振りする**——壊れるのは速度のほう）。

`applyAssignments(labelID:_:)` は 1 つのラベルの紐づけを、ファイルごとに指定した
状態へ揃える。`origin` が `nil` の項目は行ごと消す。

- **`execute()` と `undo()` がどちらもこれを使う。** 戻すことも「指定した状態へ
  揃える」ことに他ならないので、復元のための別 API を作らない。
- **`origin` を `Optional` で持つのが要点。** `nil`（行が無かった）／`.auto`／
  `.manual`／`.manuallyRemoved` の 4 通りを区別できないと、⌘Z が元と違う状態へ
  戻す（評価で「変更前の値を 1 件ずつ持つ」と決めたのと同じ [RA-06]）。
- **1 トランザクションで書く** [RP2-04]。一括付与 [RP-02] の途中で失敗したときに
  半分だけ付いた状態を残さない。**この原子性は変異検証では空振りする**——失敗を
  注入しない限り、1 件ずつのトランザクションに割っても結果は同じになるため。

外したときに `manuallyRemoved` の印を立てるかは呼び出し側が決める。
**アプリ層は auto でも manual でも立てる**［ユーザー判断、14章 §14.4「決めたこと」］
——`replaceAutoLabels` がその印を見て再計算での復活を止める [RC-04]。

決定の全体は 14章 §14.4「ラベル設定」が持つ。

### タイトルの書き込み [RP-10〜RP-12]

`setFields(_:id:)` は `title` / `titleOrigin` / `seriesName`（＋ `seriesKey`）/
巻数 / `authorName` を**まとめて**書く。手動編集 [RP-10] は最初の 2 つだけを、
「ファイル名から再取得」[RP-12] は全部を書き換える——**書き換える列の数が違う
だけの同じ操作**なので、API を分けない（`SetRatingCommand` を単発と「全巻に
適用」で共有しているのと同じ理由）。

- **`seriesKey` はリポジトリが導出する** [3.8 節]。呼び出し側に正規化させると、
  ライブラリの `caseSensitive` 設定を知らない場所で正規化することになり、
  手で直したシリーズ名では「シリーズ全巻」[RA-04] が引けなくなる——しかも
  件数を見ても気づけない。
- **`titleOrigin` は渡された値をそのまま書く。** `applyParsedFields` のように
  `manual` を守る細工はしない——守る側（走査）と、意図して書き換える側
  （右ペイン）は別の操作である。
- **再スキャンからの保護は `applyParsedFields` の SQL が担う**
  （`title = CASE WHEN titleOrigin = 'manual' THEN title ELSE ? END`）[RP-11]。
  これは v1 の実装から入っており、2-10 では書き手が現れただけ。

決定の全体は 14章 §14.4「タイトル編集」が持つ。

### カバー画像の書き込み [CV-02〜CV-08]

`setCover(_:id:)` は `coverImageSource` と `coverImageRef` を書く。

- **`.userSpecified` 以外では `ref` を消す。** 残ると「自動に戻したのに複製が
  参照されたまま」になり、起動時の掃除 [CV-06] がその複製を永久に捨てられない。
  上位（`CoverEditorModel.revert()`）は常に `ref` が `nil` の割り当てを渡すので
  普段は表に出ない不変条件だが、**変異検証で上位経由のテストだけでは空振りする
  と分かった**ため、リポジトリ層で直に固定してある。
- **サイドカー [IV-02②] は DB に書かない。** 仕様の疑似コード [9章 §9.6] も②で
  DB を見ずに実体を探している。保存すると、あとから `covers/` に画像を置いた・
  消したときに DB が古いまま残り、画面と実体が食い違う。
- **複製そのものの作成・削除はここでしない。** DB は参照だけを持ち [CL-05]、
  実体の管理は `UserCoverStore` の仕事——混ぜると「DB は書けたが複製が無い」
  「複製はあるが誰も参照していない」のどちらへも倒れ得る。
- `userCoverRefs(libraryID:)` が起動時の掃除の入力になる。**ユーザー指定のもの
  だけ**を返す。

**走査は `coverImageSource`/`coverImageRef` に触れない**（`updateInPlace` の SQL に
列が無い）ので、差し替えたカバーが再スキャンで消えることはない。

決定の全体は 14章 §14.4「カバー画像」が持つ。

### ラベルそのものの編集 [LE-07〜LE-11][LB-05〜LB-07][CO-06]

付け外し（上記）が**ファイルとラベルの関係**を書き換えるのに対し、こちらは
**ラベルの行そのもの**を書き換える。決定の全体は 15章 §15.2 が持つ。

| API | 何をするか |
|---|---|
| `deleteLabels(_:)` | 削除 [LE-07]。紐づけは `fileLabel` の `ON DELETE CASCADE` が消す [LE-08][LB-05] |
| `setColor(_:hex:)` | ラベル固有色 [LE-10][CO-06]。`nil` でグループ色の継承へ戻す |
| `merge(_:into:)` | 統合 [LB-07]。`origin` は `LabelOrigin.merging` が決める（下記）|
| `rename(_:to:)` | 改名 [LB-06]。衝突は `LabelEditError.nameAlreadyExists` |
| `snapshot(labelIDs:)` / `restore(_:)` | 削除・統合の Undo 用（下記）|

#### `snapshot` / `restore` は「ちょうどその状態へ揃える」

`applyAssignments` と同じ形にしてある——**戻すことも「ある状態へ揃える」ことに
他ならない**ので、復元専用の別の意味を持つ API を作らない。写しに含まれない
紐づけは消える。

- **`id` を明示して `INSERT` する。** `label.id` は AUTOINCREMENT なので削除された
  ID は再利用されず空いたまま残り、元の ID をそのまま取り戻せる［実測］。
- **`manuallyRemoved` の行も写しに含める。** 落とすと ⌘Z のあと再スキャンで
  ラベルが復活する [RC-04]。
- **相手のファイルが消えていたら飛ばす。** `INSERT OR IGNORE` は外部キー違反を
  無視しない（SQLite は OR IGNORE を UNIQUE / NOT NULL / CHECK にしか効かせない）
  ので、`WHERE EXISTS` で自分で外す——1 件の消失で Undo 全体が失敗しないように。
- **1 トランザクションで書く。** 統合の Undo は 2 件をまとめて戻すので、途中で
  切れると「統合元は戻ったが統合先は統合後のまま」というどちらでもない状態が残る。

#### `merge` は `origin` を突き合わせてから移す

以前は `UPDATE OR IGNORE fileLabel SET labelId = ?` 1 本で移していたが、それだと
移動先の値が無条件に残り、統合元が `manual`・統合先が `manuallyRemoved` の
ファイルで**手動付与が黙って消えていた**。両方が付いているファイルを先に
`LabelOrigin.merging`（manual > auto > manuallyRemoved）で書き換えてから移す。

**グループをまたぐ統合は断る** [LB-07]。ラベルの一意性はグループ内で定義されて
おり [LB-01]、またぐと「グループを移す」という別の操作になる。

#### `labels(groupID:includeArchived:)` は件数を 2 つ返す

`fileCount`（非正規化列、フィルタ用、保管庫を数えない [FA-05]）と
`fileCountIncludingArchived`（バッジ用、保管庫を数える [LE-05]）。
**要件が意図的に食い違うため 1 つの値では両方を満たせない**——詳細は 15章 §15.2。

#### `archivedLabelCounts()` は 1 回でライブラリ全件を返す（2-13 で追加）

ラベル保管庫の整理ウインドウが、左ペインで**保管庫が空のライブラリを
グレーアウトする**ために使う [15章 §15.3]。`GROUP BY labelGroup.libraryId` の
1 問い合わせで全ライブラリぶんを返し、**0 件のライブラリはキーごと現れない**
（呼び出し側は `?? 0` で読む）。

**ライブラリごとに `groups` → `labels` と辿らないのは費用のため**［設計判断］。
そちらは問い合わせが「ライブラリ数 × グループ数」になり、しかもこのウインドウは
`CommandStack.operationHistory.count` を鍵に読み直すので、**⌘Z のたびに**それが走る。

#### 登録は草案を通る [RG-01][LT-02][LS-01]

`register(_:template:)` は **`TemplateInstantiation.draft(from:)` へ委譲する**
だけで、既定値を自分では持たない。有効化ウインドウが見せるのも同じ関数の
結果なので、**利用者が見た内容がそのまま登録される**ことが構造的に保証される。

`register(_:draft:template:)` が本体で、`template` が `nil` なら白紙から
作ったカスタム [LT-02]（専用の非プリセット型を作る）。付随テーブルへの
書き込みは `writeSettingsTables` を `updateSettings` と共有する——別々に書くと
「有効化した直後の設定」と「設定を開いて保存し直した設定」が食い違う。

#### 実装状況（第 1 段、2026-08）— **触る前にこの表を読むこと**

`BackupDocument`／`BackupRepository`（`QooKit`）と `SQLiteBackupRepository`
（`QooPersistence`）、`LibraryServices` の 3 つの口、環境設定「リセット」タブ
（`ResetPreferencesTab`／`LibraryBackupAction`）まで実装済み。**削除機能を

##### 仕様との差異 3 つ（いずれも意図的。戻すなら理由ごと検討すること）

1. **取り込みはライブラリの行を作らない。** ライブラリを作るには
   Security-Scoped Bookmark が要り、**それは環境固有なので JSON に持てない**
   （別マシンでは解決できず、同じマシンでもフォルダを選び直せば別物になる）。
   DB に無いライブラリは `missing` として報告するに留める。したがって
   MG-24 の復旧手順は「新規ストア → インポート → 再スキャン」ではなく
   **「有効化 → 再スキャン → インポート」**になる。UI はこの順序を案内する。
2. **ファイルの行も作らない** [ID-06]。実体を伴わないレコードを増やすと、
   次の走査でそれが孤立として現れ「消えたファイル」の報告に混ざる。
   走査が作った行に、評価・手動ラベル・手動タイトルを載せ直す形にした。
3. **ラベル紐づけの主キーは `groupIndex`**（JS-04 は「グループ名」と書く）。
   グループ名は後から変えられるので、名前だけを頼りにすると改名した瞬間に
   別物になる。名前も併記してあるので、将来ライブラリ間マージを作るときは
   そちらを使える。

##### 書き出さないもの（**再スキャンが作り直せるものは持たない**）

`origin = 'auto'` のラベル紐づけ [RC-04]、`titleOrigin = 'auto'` のタイトル
[RP-11]、`coverImageSource = 'auto'` のカバー参照 [IV-03]、そして
**再生成できる情報しか持たないファイルの行そのもの**。10 万件の蔵書で
JSON が無意味に膨らむのを避けるためで、`FileBackup.carriesUnrecoverableData`
が唯一の判定点になっている（書き出しと取り込みで条件がずれないよう 1 箇所に閉じた）。

**この設計に伴い `ManagedFileRecord.regenerableColumns` へ `fileSize`／
`createdAt`／`modifiedAt` を追加した**——いずれも走査が実体から読み直して
必ず上書きするので、JSON に持つと「古い値で正しい観測を上書きする」危険
だけが残る。網羅性テストがこの分類と DTO の一致を見張っている。

### 自動バックアップ [BK-01〜BK-05]

```swift
public protocol BackupService: Sendable {
    func snapshotOnLaunch() async throws                                      // [BK-01]
    func snapshotBeforeDestructive(_ reason: DestructiveReason) async throws  // [BK-02][MG-10]
    func restore(from url: URL) async throws                                  // [BK-03]
    func exportToUserFolder(_ url: URL) async throws                          // [BK-04]
    func pruneGenerations(keep: Int) async throws
}

public enum DestructiveReason: Sendable {
    case bulkLabelDelete, templateApply, jsonImport, schemaMigration          // [BK-02]
}
```

| # | 要件 |
|---|---|
| BK2-01 | スナップショットは SQLite のオンラインバックアップ（`DatabaseReader.backup(to:progress:)`）で取る。**ファイルを直接コピーしてはならない**——`-wal` に未反映の内容を取りこぼす |
| BK2-02 | バックアップ中も読み書きを止めない。`pagesPerStep` を指定して進捗を出す |
| BK2-03 | 世代管理は `pruneGenerations(keep:)`。既定 5 世代 |
