## 8.1 FileOperationService [FO-01]

**ファイルシステムへの変更はすべてこのサービスを経由する。** 他のレイヤから `FileManager` の変更系 API を呼んではならない。CI の静的検査 B-10 で強制する [FO-02]。

### ゴミ箱を持てないボリューム（1-16b で扱う）

> **ネットワークボリューム全般の事前調査は §8.11 にある。** 本節はそのうち
> ゴミ箱に限った論点で、§8.11.8 の検証計画にも最優先項目として載っている。

ネットワークボリューム（SMB/AFP）など、`.Trashes` を置けない場所では
「ゴミ箱に入れる」がそもそも成立しない。Finder はこの場合「この項目はすぐに
削除されます」と尋ねてから完全削除する。**本アプリは現状その分岐を持たない。**

コードを読んで確定している事実:

| # | 確定していること |
|---|---|
| 1 | `NSWorkspace.recycle` がエラーを返せば `FileOperationService.trash` は throw し、`TrashCommand` → `FolderOperations.run` → `NotificationRouter` とエラーが提示される。**黙って完全削除されることはない** |
| 2 | 一方、`recycle` が成功を返しつつ**ゴミ箱先の URL を返さなかった**場合、`TrashReceipt.trashURL` が `nil` になる。`restoreFromTrash` はその項目を読み飛ばす（`guard let trashURL … else { continue }`）ため、**Undo は復元できない** |
| 3 | しかも `CommandStack.undo()` は `.partial` を**操作履歴に記録するだけ**で `NotificationRouter` へ流さない。つまり 2 の状況では **⌘Z を押しても画面上は何も起きない**（無言で失敗する） |

未確定（1-16b で実測して確定させること）:

- SMB/AFP 上で `NSWorkspace.recycle` が実際に何を返すか（エラーか、成功＋URL 無しか）。
  **[訂正] 「検証に使えるネットワークボリュームが無い」と記録していたが、これは
  もう事実ではない。** 1-16c の名前長・パス長の実測では**実 NAS を SMB 経由で
  使っており**（本節より後の作業）、SMB の検証は可能である。1-16b はこの前提で
  着手できる。
- 読み取り専用のディスクイメージで近似しようとしたが、`NSWorkspace.recycle` の
  完了ハンドラが 5 分待っても呼ばれず（ランループを回した状態でも同様）、
  この経路からは確認できなかった。**「ハングする」と結論づけるには材料が
  足りない**（バンドルを持たない検証プロセスで UI 提示が抑止された可能性が
  ある）ため、事実としては「この方法では確認できなかった」に留める。

1-16b で決めること:

| # | 決めること |
|---|---|
| NV-01 | ゴミ箱を持てる場所かを**事前に**判定する手段（`FileManager.url(for: .trashDirectory, in: .userDomainMask, appropriateFor:)` の可否など）。1-14 で `.trashDirectory` はボリュームによって `code 3328` で失敗すると実測済みで、その失敗自体が判定に使える可能性がある |
| NV-02 | ゴミ箱に入れられない場合、Finder と同じく**完全削除でよいか確認する**。無言で完全削除しない・無言で失敗しないこと |
| NV-03 | 3 の「`.partial` な Undo が画面に出ない」を塞ぐ。ここはネットワークに限らない一般の欠陥で、フェーズ1完了前監査でも記録済み |
| NV-04 | 変更検知は FSEvents が他のマシンの変更を報告しないため、10章 §10.0 のポーリング経路が実際に働くかを実機で確認する（現状**未検証**） |

### 実装上の確定事項（1-14 で実装）

| # | 内容 |
|---|---|
| PD-10 | `deletePermanently` は**最初の失敗で中断しない** [ER-13]。成功・失敗・スキップを `DeletionOutcome` に個別に集めて返し、完了後に結果サマリを提示する [ER-12][ER-14]。他の一括操作（`transfer` 等）が「最初の失敗で例外を投げ、それまでの `OpReceipt` を捨てる」形なのに対し、完全削除だけこの形にする理由は、**「実際にはファイルが消えているのに操作は失敗扱いで記録も残らない」状態が復元不能な事故に直結する**ため |
| PD-11 | PD-06 の「都度尋ねる対象」は**ロック済み項目**とする。ER-11 が定める「ユーザーの選択によって結果が変わるもの」に完全削除で該当するのはこれだけで、Finder も同じくロック項目のみを個別に確認する。「以降すべてに適用」の状態は UI 側が `DeletePermanentlyOptions.lockedItemResolver` に閉じ込めて保持する（`BatchNotificationSession` を待たない）[設計判断] |
| PD-12 | 確認は**操作対象 1 件ごと**に行い、フォルダ配下の個々のロック項目ごとには行わない。フォルダ自身がロックされていなくても**配下にロック項目を含めば尋ねる** — `FileManager.removeItem` はロック済みの子に当たった時点で失敗し、そこまでに消した子だけが失われた中途半端な状態を残すため [設計判断] |
| PD-13 | ロック解除は削除の直前にのみ行い、**削除に失敗したら元に戻す**。シンボリックリンクの先へは入らない（`removeItem` はリンク自体しか消さないため、リンク先のロックを外してはならない）|
| PD-14 | 完全削除で実体を失うライブラリ／テンポラリ登録は**強制的に登録解除する** [ユーザー要望]。対象の照合は削除の**前**（ブックマークが解決できるうち）に行い、解除は削除の**後**に行う（先に解除するとアクセススコープが閉じて削除自体が権限エラーになる）。確認ダイアログにも登録が解除される旨を明示する |
| PD-15 | メニュー配置は Finder と同じく**「ゴミ箱に入れる」[FM-04] の ⌥ 代替**とする（`modifierKeyAlternate(.option)`、13章 §13.7.1）。対にすることで「ゴミ箱を出せない場面で完全削除だけが現れる」経路が構造的に無くなる。**[訂正]** 当初は「SwiftUI では ⌥ による入れ替えを実装できない」との誤った判断から「その他 ▸」サブメニューへ退避していたが、`View.modifierKeyAlternate(_:_:)`（macOS 15.0+）で実装可能と判明したため、サブメニューは廃止した |

### 8.7.1 登録フォルダの縮退状態 [SB-05][FS-08][LP-04][VD-11]

登録フォルダには、本アプリの制御外で操作が加わる——ボリュームのイジェクト、削除、移動、リネーム。
**「ブックマークを解決できたか否か」の二値では、性質のまったく異なる事象が同じ扱いに潰れる。**
ボリューム未接続は「待てば必ず戻る」ので登録を絶対に消してはならず、完全削除は「戻らない」ので
登録の整理をユーザーに促すべきである。この区別を状態として持つ。

#### 実測にもとづく前提

以下は使い捨てのプローブと `hdiutil` のスパースイメージで実測して確定させた事実であり、
設計はこれらを前提にしている。**推測で置き換えないこと。**

| # | 実測結果 |
|---|---|
| BM-1 | 登録フォルダのリネーム・移動、祖先のリネームでは、ブックマークは**追従して解決に成功する**（`isStale = true`）|
| BM-2 | **ゴミ箱へ移動しても解決は失敗しない。**`~/.Trash/…` を指したまま成功する（inode を追跡するため）|
| BM-3 | 完全削除は `NSCocoaErrorDomain` code = 4 |
| BM-4 | **ボリュームのアンマウントも code = 4。**エラーコードだけでは BM-3 と区別できない |
| BM-5 | **`.withoutMounting` を付けない解決は、未マウントのボリュームを実際にマウントする。**ネットワークボリューム（FS-06）ではタイムアウトぶんブロックし得る |
| BM-6 | 未マウント時でも `startAccessingSecurityScopedResource()` は `true` を返す。生存確認には使えない |
| BM-7 | 削除後に同名フォルダを作り直すと、inode が違っても**パスで解決してしまう** |
| BM-8 | セキュリティスコープの保持はアンマウントを妨げない（**サンドボックス下でも実測済み**。1-16 のイジェクト実装時に、実アプリと同じ entitlement でアドホック署名した probe で `startAccessingSecurityScopedResource()` を保持したまま `unmountAndEjectDevice` が成功することを確認。したがってイジェクト前にアクセスを停止する処理は不要）|

#### 状態


#### 判定順序 [設計判断]

**ボリュームのマウント状態を、ブックマークを解決する「前」に見る。**
順序を逆にすると BM-5 を踏む——未接続を判定するはずの処理が、その判定の過程で
ボリュームをマウントしてしまう。

```pseudo
resolveStatuses(folders):
    # ① マウント済みボリュームの UUID → URL マップを 1 回だけ作る。
    #    登録ごとに問い合わせない（性能）
    mounted = mountedVolumeURLs() をUUIDで索引化

    for folder in folders:
        # ② 未マウントならここで打ち切る。解決を一切試みない [BM-5 の回避]
        if folder.volumeUUID != nil && mounted[folder.volumeUUID] == nil:
            yield .offline(folder.volumeUUID); continue

        # ③ マウントは抑止して解決する
        switch bookmarks.resolve(folder.bookmarkData)   # 既定で .withoutMounting
          case .offline: yield .missing; continue       # マウント済みなので削除と断定してよい
          case .resolved(url): break

        # ④ ゴミ箱配下か [BM-2]
        if url.pathComponents contains ".Trash" または ".Trashes":
            yield .inTrash(url); continue

        # ⑤ 実在とディレクトリ種別の確認
        if !isDirectory(url): yield .missing; continue

        yield .online(url)
```

| # | 要件 |
|---|---|
| RG3-01 | `BookmarkResolving.resolve` は既定で `.withoutMounting` を付ける。マウントを許す解決は、ユーザーの明示的な操作からのみ呼ぶ別 API に分ける [BM-5] |
| RG3-02 | `RegisteredFolder` に `volumeUUID: String?` を持つ [VD-02]。`Optional` なので既存 JSON はそのままデコードでき、旧レコードは初回のオンライン解決時に埋める（値が `nil` であること自体が「未移行」を表すため、専用の移行フラグは不要）|
| RG3-03 | ゴミ箱判定は `pathComponents` の照合で行う。**`FileManager.url(for: .trashDirectory, appropriateFor:)` は使わない** — ボリュームによって `code 3328`（未サポート）で失敗することを実測で確認済み（同一マシンで `/` は成功、`/Volumes/T7` は失敗）|
| RG3-04 | いずれの状態でも**登録レコードを自動削除しない** [SB-05][R-01]。登録解除は必ずユーザーの明示的な操作で行う |
| RG3-05 | 入れ子の禁止 [RG-03][RG-04] は外部での移動によって事後に破れる（BM-1）。起動時とオンライン復帰時に再検証し、破れていたら警告する。**自動解除はしない** |
| RG3-06 | 表示中のタブが読み込みに失敗したとき、原因がボリューム未接続なら**祖先へ退避させない**。オフラインのプレースホルダを出し、履歴も破棄しない（破棄すると挿し直しても戻れない）。退避するのは削除・改名の場合のみで、退避先は登録ルートで止める（`NavigationRoot` の境界と揃える）|
| RG3-07 | フェーズ 1 では着脱検知を持たないため、判定はツリー更新時にマウント一覧と突き合わせる受動的なものに留める。2-2 で `NSWorkspace` のボリューム通知に置き換える（10.2 節）。**状態モデルと判定順序は変えず、遷移の駆動方法だけを差し替える** |
| RG3-08 | ゴミ箱を監視する必要はない。`.inTrash` は解決先を見るだけの受動的な判定であり、[TR-07] の「システムのゴミ箱を監視しなくて済むようにする」方針と整合する |

### 8.11.1 対象の分類 [NV-10]

「ネットワークボリューム」は一枚岩ではない。分岐を書く前にどれを指しているかを
決めること。

| 系統 | 実体 | `volumeIsLocal` | 位置 |
|---|---|---|---|
| SMB（`smbfs`）| カーネル VFS。macOS の事実上の標準 | `false` | `/Volumes` |
| NFS（`nfs`）| カーネル VFS | `false` | `/Volumes` |
| WebDAV（`webdav`）| カーネル VFS ＋ `webdavfs_agent` | `false` | `/Volumes` |
| AFP | macOS 11 でクライアント側サポート終了。新規考慮不要 | `false` | — |
| FUSE 系（macFUSE / SSHFS / rclone）| ユーザ空間。capability の申告が実装ごとにばらばら | 実装依存 | `/Volumes` |

### 8.11.2 機能差 — ローカルにあってネットワークに無いもの

| # | 内容 | 一次/二次 |
|---|---|---|
| NV-20 | **変更検知が原理的に存在しない。** FSEvents は各ボリュームのカーネルレベルのイベントログに支えられており、リモート FS はそれを持たない。`kqueue` も ①fd を大量消費し ②開いた fd がアンマウントを `EBUSY` で妨げ ③リモート側の変更がクライアントカーネルに伝わらない。SMB/NFS のプロトコル自体に汎用の変更通知が無い（SMB の `CHANGE_NOTIFY` は VFS 層から FSEvents へ橋渡しされていない）。**ポーリングしか手段が無い** → 10章 §10.0 | 二次 |
| NV-21 | **ファイル同一性の基盤が崩れる。** `volumeUUIDString` は「永続 UUID が利用できない場合は nil」とドキュメントされており、ネットワークでは nil になり得る。IORegistry にもネットワークボリュームの情報が無く、`statfs` からも取れない。inode（`fileResourceIdentifierKey` / `st_ino`）は SMB サーバが File ID を返すか・その安定性がサーバ実装依存。**「volumeUUID ＋ inode」で同定する設計は破綻するか、静かに誤同定する。誤同定は上書き事故に直結する** | 一次（nil 可能性）/ 二次（inode）|
| NV-22 | **アトミック操作が使えない。** `renamex_np(RENAME_EXCL)`／`RENAME_SWAP` は `VOL_CAP_INT_RENAME_EXCL`／`VOL_CAP_INT_RENAME_SWAP` を持つ FS でのみ動き、持たなければ `ENOTSUP`。`exchangedata(2)`・`clonefile(2)`／`COPYFILE_CLONE` も不可。**「存在チェックしてから rename」の 2 段階に退行せざるを得ず、TOCTOU が現実の脅威になる**（共有ストレージでは他クライアントの割り込みが日常）| 一次（man page）|
| NV-23 | **コピーは逆に、専用 API のほうが桁で速い。** 同一サーバ内のコピーは SMB/AFP が**サーバサイドコピー**（`VNOP_COPYFILE`）に対応しデータがネットワークを通らない。Finder はこれを使うが、**`copyfile(3)` も `FileManager.copyItem` も使わない**（進捗報告と `VNOP_COPYFILE` のブロッキング性が両立しないため）。Apple DTS の回答は「非推奨の Carbon File Manager `FSCopyObjectSync()` を使え」。使用条件は ①転送元・先の両方に `VOL_CAP_INT_COPYFILE` ②`ATTR_VOL_FSTYPENAME` が同一（現状 SMB と AFP のみ）③`ATTR_VOL_MOUNTPOINT` 等で同一サーバ。代償は進捗もキャンセルも無く、遅い回線でブロックすること。**サーバ側 Samba に `vfs_fruit` ＋ `fruit:copyfile = yes` が無いと有効にならない — クライアント実装だけでは決まらない** | 一次（DTS 回答）|
| NV-24 | **ハードリンクは SMB で作れない**（macOS SMB クライアントの制限。プロトコル側は対応していても実装が無い）。シンボリックリンクはサーバの Unix 拡張（`vfs_fruit` / POSIX extensions / `mfsymlinks`）次第で、非対応だと普通のファイルとして見えるか作成が失敗する。スパースファイルの穴は転送で埋まる | 二次 |
| NV-25 | **ゴミ箱が成立しない。** → §8.4 NV-01〜NV-04 | 二次 |
| NV-26 | **Unicode 正規化がクライアントとサーバでずれる。** macOS ローカル FS は NFD で扱うことが多いが、**macOS の SMB クライアントは送信前に NFC へ正規化する**。サーバ側（Linux/Samba）が NFD の名前を保持していると、**一覧には見えるのにその名前で開くと「存在しない」**という状態になる（TrueNAS が公式ドキュメントで警告）。日本語の濁点・半濁点で顕在化する。**本アプリは日本語ファイル名が主戦場であり、影響は大きい** | 二次（ベンダー公式文書）|
| NV-27 | **大文字小文字の扱いがずれる。** SMB2 は既定で case-insensitive。サーバ側が case-sensitive でも SMB がそれを申告しないと macOS が case-aware と誤認する。**大文字小文字だけを変えるリネームが黙って無視される**のが典型。case-preserving でない構成もある。`volumeSupportsCaseSensitiveNamesKey` / `volumeSupportsCasePreservedNamesKey` を見る。**リネーム後に実際の名前を読み戻して検証する**防御が要る | 二次 |
| NV-28 | **名前・パス長の上限が違う。** ローカル APFS/HFS+ は NFD 後の UTF-16 単位で 255 に対し、**SMB は UTF-8 バイトで 255**（実装依存）。日本語は 1 文字 3 バイトなので **85 文字程度で上限**。この数値は本プロジェクトが 1-16c で実 NAS に対して実測済み（`PathLimits`／`FileNameValidation` のコメント参照）。パス全体の上限もサーバ側 OS 依存 | **実測済み**（本プロジェクト）|
| NV-29 | **権限モデルが写像で歪む。** SMB マウント時、共有全体がマウントしたユーザの所有・rwx として見えることがあり、表示上の POSIX パーミッションが実際のアクセス可否と一致しない。サーバ側 ACL は macOS からは見えず無視されているように見える。`chmod`／`chown`／`chflags`（`uchg`）が失敗するか、成功したように見えて反映されない。**「読めるかどうかは実際に開いてみるまで分からない」— 事前のパーミッション検査は当てにならない** | 二次 |
| NV-30 | **Spotlight が使えないことがある。** ローカルのインデックスはネットワークを対象にしない。SMB 越しの Spotlight はサーバが `mdssvc` RPC を提供する場合のみ（Samba の `spotlight = yes` 等）で、共有がボリューム全体である必要があるなど条件が厳しい。非対応サーバでは検索がクライアント側の再帰列挙になり往復が爆発する | 二次 |
| NV-31 | **空き容量が当てにならない。** サーバ側 quota 設定・データセット構成次第で 0 が返る／共有ではなくユーザ quota が返る／桁が壊れる、という報告が多数。WebDAV は `DAV:quota-*` 由来でサーバが返さなければ不明。`volumeAvailableCapacityForImportantUsageKey` は purgeable を前提にした値でネットワークでは意味を持たない。**「空きが足りないなら書き始める前に断る」事前検査は、正当な操作を誤って拒否する方向に壊れる。0／取得失敗なら検査を飛ばして通す**（`VolumeCapacity` が既に採っている害の非対称と同じ判断）| 二次 |
| NV-32 | **オープン中ファイルの削除セマンティクスが違う。** SMB は「オープン中のファイルは削除できない」（sharing violation）。macOS は silly rename（`.smbdelete***` へ改名して delete-on-close マーク）で回避しようとする。**Finder のプレビュー生成・アイコン生成がファイルを開いたままにするため、選択しただけで削除・改名・移動が失敗する**という報告がある。**自アプリのサムネイル生成・Quick Look がこれを引き起こす側になる** — ハンドルを開きっぱなしにしないこと | 二次 |

### 8.11.3 性能 — コストの構造がまったく違う

ローカルは 1 操作 ≒ マイクロ秒。ネットワークは **1 往復 ≒ 0.5〜数十ミリ秒**。
**支配要因は帯域ではなく往復回数（chattiness）。**

| # | 内容 |
|---|---|
| NV-33 | 1,000 ファイルに `resourceValues` を 1 件ずつ呼ぶと、それだけで数秒〜数十秒。列挙は**取得する属性を最小化する**（必要な resource key だけ prefetch）ことが効く |
| NV-34 | `getattrlistbulk(2)` はローカルでは劇的に少ないシステムコールで済むが、**ネットワークでは単純に速いとは限らない**（SMB では `opendir` のほうが速い、キャッシュが温まると `contentsOfDirectory` が遅くなる、という計測報告が入り組む）。さらに **macOS 15 Sequoia で SMB 上の `getattrlistbulk` が同じファイルを繰り返し返す不具合報告**がある |
| NV-35 | **macOS SMB クライアントはディレクトリ列挙結果をキャッシュする**（Apple が公式に無効化方法を案内している）。速い代わりに他クライアントの変更が見えず、キャッシュ再構築中に項目が消える。**「読み取ったばかりの内容が最新とは限らない」** — 書き込み後に読み戻して検証するパターンがキャッシュ越しに古い値を読んで誤判定し得る |
| NV-36 | SMB2.1 以降の **lease oplock** でクライアントが read-ahead / write-behind をキャッシュする。他クライアントが開くと lease break が発生しフラッシュするが、**その最中のネットワーク障害でキャッシュ済みの書き込みが失われる**。転送暗号化を有効にすると oplock / lease が無効化されるという報告もあり、キャッシュ挙動そのものが変わる |
| NV-37 | **I/O 増幅を起こす機能を縮退させる。** ネットワークで特に危険なのは、サムネイル生成（**ファイル本体を丸ごと読む**）、Quick Look のカバー生成、フォルダの再帰的な項目数・合計サイズ [DT-05][DT-06]、再帰検索、アーカイブの中身一覧、インスペクタの自動集計。**①ネットワークでは既定でオフ ②明示操作でのみ実行 ③キャンセル可能 ④上限付き**、のいずれかが要る。サムネイルの一括生成は**帯域を飽和させてサーバ全体を巻き込む** → 09章 §9.6（DS-01〜DS-07）の一括制御が既にその器になっている |
| NV-38 | **同時実行数の適正値がローカルと違う。** 並列度を上げるとサーバの接続数上限・スレッドプールを枯渇させる一方、往復レイテンシが支配的なので直列では遅すぎる。ローカル用に決めたスロット数（`AppLimits.Thumbnail.maxConcurrent` 等）をそのまま流用しない |
| NV-39 | プロトコルレベルの要因（**アプリからは制御できないが体感に効く**）: SMB の署名・暗号化が macOS 側で強制されがちで、特に Apple Silicon で顕著な性能低下の報告がある。SMB Multichannel で改善する。調整は `/etc/nsmb.conf`・`sysctl net.smb.fs.*`。**これはユーザ／管理者の領域でありアプリが変えてはならない**が、「遅い原因がアプリではなく環境である」と説明できるとサポートコストが下がる |
| NV-40 | **メインスレッドを絶対に塞がない。** ローカルなら `stat` 1 回はマイクロ秒だが、サーバが応答しないと分単位でブロックする（hard マウントでは無限）。`FileManager`／`URL.resourceValues`／`NSWorkspace` のあらゆる呼び出しがブロックし得る。**描画のついでに属性を読む実装（セル描画中の `resourceValues`、`body` 評価中のファイルアクセス）はビーチボールに直結する。** ローカル前提の同期ヘルパーが 1 つ残っているだけでアプリ全体が固まる |

### 8.11.4 障害 — 切断は例外ではなく通常状態

| # | 内容 |
|---|---|
| NV-41 | macOS の SMB は日常的に切断する（Wi-Fi ローミング、スリープ復帰、サーバ再起動、DHCP 更新、省電力）。しかも **macOS はリンク回復時に自動再接続を試みない**、**Finder はマウントポイントをキャッシュして古いデータを表示し続ける**、マウントポイントは存在し続けるが中身にアクセスすると失敗する（stale mount）、という報告が Yosemite〜Sonoma で一貫している |
| NV-42 | **マウントポイント名を信用しない。** 同名共有を複数マウントすると 2 つ目は `Share-1` に自動改名される。異常終了後の残骸、複数ユーザの同時マウントでも起きる。**保存しておいたパスが別の場所を指す**（Lightroom 等でリンク切れとして知られる）。**永続化はパス文字列ではなく、`NetFSCopyURLForRemountingVolume()` で得たサーバ URL ＋ 共有内相対パスで行い、復元時に現在のマウントポイントへ解決し直す** |
| NV-43 | **マウント／アンマウント通知が来ない可能性がある。** `NSWorkspace` のボリューム通知はネットワークボリュームを対象から除外しているという報告がある。Disk Arbitration も情報が乏しい。代替は Darwin notification（`kNotifyVFSMount`）や Endpoint Security の `NOTIFY_MOUNT`（要 entitlement）。**着脱検知はポーリング（`mountedVolumeURLs` の定期取得）に退行する可能性が高い。要実測** → 2-2（VD-01〜VD-06）の設計に直結する |
| NV-44 | **部分失敗が常態になる。** 100 ファイルのコピー中 47 番目で切断すれば 46 個は転送済み。「最初の失敗で中断し、それまでの結果を破棄する」設計だと**実際には転送済みのファイルが記録に残らない**（取り消せない・二重転送になる）。**`transfer()` の部分成功の保持（2-2、[RB-04][ER-13]）は、ネットワークではイジェクト以上に日常的に踏まれる** |
| NV-45 | **書きかけの宛先が残る。** サイズが同じでも中身が壊れている可能性がある。中断・失敗時に宛先を確実に片付けること。**`.replace` の「退避 → 書き込み → 成功なら退避削除／失敗なら復元」（`withReplaceBackupCleanup`）は、失敗確率が桁違いに高いぶんネットワークでは価値がさらに大きい** |
| NV-46 | **NFS の hard / soft マウントで挙動が根本的に違う。** hard は I/O が無限にリトライしプロセスがハングする（`intr` が無いと `kill` も効かない）。soft は `retrans` 回後に失敗を返すがデータ破損リスクがある。**アプリはこれを制御できない** — 同じコードが「固まる」か「失敗する」かに分かれる。自前のタイムアウト（`Task` の上限時間）が hard 環境での唯一の防衛線だが、**タイムアウトしても下位の I/O は止まらない**（スレッド／スロットが塞がったまま）ことに注意 |
| NV-47 | **期待すべき errno を「不明なエラー」に丸めない。** `ETIMEDOUT`（無応答）／`ENOTCONN`・`ENETDOWN`・`EHOSTDOWN`・`EHOSTUNREACH`（接続喪失）／`ESTALE`（ハンドル無効、NFS で顕著）／`EACCES`・`EPERM`（サーバ側 ACL・read-only 共有）／`ENOSPC`・`EDQUOT`（quota）／**`ENOTSUP`・`EOPNOTSUPP`（capability 検出漏れのサイン）**／`EBUSY`（他クライアントがオープン中）／`EINTR`（soft マウントでの中断）／`ENAMETOOLONG`。`PosixFailure`（1-16c で新設）の翻訳表にこれらを追加すること。Foundation の `NSError` はこれらを丸めて情報を落とすため `NSUnderlyingErrorKey` を掘る必要がある |
| NV-48 | **「静かに失敗する」を作らない。** 見た目は成功で起きること: 大文字小文字だけのリネームが無視される（NV-27）／xattr の設定が失敗しても本体のコピーは成功する（NV-51）／キャッシュのせいで古い内容が読める（NV-35）／上書きのつもりが別の正規化形式で新規作成される（NV-26）。**破壊的操作の後に読み戻して検証する価値がローカルより遥かに高い** |

### 8.11.5 メタデータとファイル属性

| # | 内容 |
|---|---|
| NV-50 | **拡張属性は `._` ファイル（AppleDouble）に落ちる。** macOS は Mac のメタデータを保持できないボリューム（SMB・FAT32・zip 等）で `foo` に対し `._foo` を作る。入るのはリソースフォーク・Finder info（ラベル色・カスタムアイコン）・多くの拡張属性。結果、**ファイル数が 2 倍になり列挙コストも 2 倍**、Windows/Linux からはゴミファイルとして見え、`._` だけ／本体だけが残る不整合が起きる。挙動は Samba の `vfs_fruit` 設定（`fruit:resource`、`fruit:veto_appledouble`）で変わる。**列挙時に `._` を除外する配慮が要る** |
| NV-51 | 属性ごとの可否（いずれも失敗し得る）: 拡張属性 `setxattr`（`ENOTSUP`／`EPERM`、または `._` へ迂回）／`com.apple.quarantine`／Finder タグ（`com.apple.metadata:_kMDItemUserTags` xattr なので同じ）／ロック `isUserImmutable`（`uchg`）／ACL／実行ビット。**作成日はサーバ実装依存、`addedToDirectoryDateKey`（追加日）はローカル FS 固有で取れないと考えるべき** — 1-16 で「追加日」列を足しているため、**ネットワークでは nil になる前提で UI・ソートが破綻しないこと** |
| NV-52 | **`copyfile(3)` の `COPYFILE_ALL` は、宛先が対応していない属性で失敗する。** エラーを無視すると xattr が落ちたまま「成功」する。逆にエラー段階で `COPYFILE_CONTINUE` を返すと**本体の I/O エラーまで握り潰される**（1-16c で実際に踏んだ落とし穴）。ネットワーク相手では「属性の欠落は許容し、本体の失敗は許容しない」という**属性ごとの重要度の区別**が実質必要になる |
| NV-53 | **自分が汚染源にならないこと。** Finder の `.DS_Store` はネットワーク共有を汚し、CIS ベンチマークで抑制が推奨されている（`DSDontWriteNetworkStores`）。**本アプリはネットワークボリューム上にアプリ由来のファイルを一切作らない** [CL-01〜CL-05 の延長]。サムネイルキャッシュ・索引は必ずアプリコンテナ側に置く（現状の `CoverImageCache`／`QuickLookCoverStore` は既にそうなっている）|

### 8.11.6 排他制御とセキュリティ

| # | 内容 |
|---|---|
| NV-60 | **すべてのリモート FS で確実に動くロック方式は存在しない。** `flock(2)` は NFS で動かない、`fcntl(F_SETLK)` は SMB で動かないという報告（古い情報の可能性あり、要実測）。SMB のバイト範囲ロックはプロトコルとしては**強制ロック**で Unix の advisory とは意味が違う。`NSURLVolumeSupportsAdvisoryFileLockingKey` で判定せよ、が Apple の指示 |
| NV-61 | **ロック前提の排他設計は成立しない。** 代替は ①楽観的並行制御（操作直前に mtime／サイズを確認し、変わっていたら中止）②ロックファイル（`O_CREAT|O_EXCL` の原子性に依存 — これも FS 依存）③**多クライアント同時編集を前提にしないと宣言する**。`LockManager` [LK-11〜LK-14] はプロセス内の排他であってこの問題を解かない |
| NV-62 | **「自分だけがこのファイルを触っている」前提が崩れる。** 列挙 → 表示 → 選択 → 操作 の間に他クライアントが削除・改名している。事前検査と実行の間に状態が変わる（TOCTOU）。**自己変更識別（§8.2 の期待変更台帳）は FSEvents が無いため土台を失う** — 4 層構造 [5.4 節] のうち ①FSEvents フラグ ③一括操作中の監視停止 が効かず、②期待変更台帳と ④冪等性検証だけが残る |
| NV-63 | **TCC「ネットワークボリューム」権限。** macOS には「プライバシーとセキュリティ > ファイルとフォルダ > **ネットワークボリューム**」という**単一のスイッチ**（ボリュームごとではない）があり、`Info.plist` に **`NSNetworkVolumesUsageDescription`** が要る。**TCC の許可はバイナリの解決済みパスに紐づくため、アップデートのたびに再許可を求められる**（Claude Code 自身がこの問題を踏んで issue になっている）。**アドホック署名の開発ビルドでは再ビルドのたびに許可が失われる可能性が高い**（Full Disk Access で既に踏んだのと同じ性質。§0「動画サムネイル調査」参照）— 1-16b の検証作業自体がこれに阻まれる |
| NV-64 | **サンドボックス下では `NetFSMountURLSync` によるマウントが動かない**という報告がある（`file-mount` がシステムポリシーで拒否される）。**マウントは OS／ユーザに任せ、アプリは行わない**。アクセス取得は `NSOpenPanel`（既存の「アクセス権」タブ）経由が最も確実 |
| NV-65 | Security-Scoped Bookmark のネットワークでの挙動: ①未マウントだと解決できない ②**解決の副作用でマウントが走る**（BM-5。`.withoutMounting` を付けないとタイムアウトぶんブロックする — 1-17 で対処予定）③macOS のマイナーアップデートでブックマークが一斉に無効化された事例がある（14.7.5）|
| NV-66 | **サーバは信頼できない入力源である。** サーバが `..` を含む名前・`/` を含む名前・極端に長い名前・不正な UTF-8 を返し得る。シンボリックリンクが共有外を指し得る（Samba の `wide links`）。悪意あるサーバは列挙のたびに違う内容を返せる。**列挙結果をそのままパス結合してファイル操作するのは、アーカイブ展開時のパストラバーサル対策 [EX-10〜EX-15] と同等の検証を要する** |

### 8.11.7 File Provider 系クラウドの固有問題 [NV-70]

`volumeIsLocal` が `true` を返すため上記の判定を**すべてすり抜ける**が、実体は
ネットワークである。

| # | 内容 |
|---|---|
| NV-70 | ファイルは **dataless（脱水状態）** で存在し得る。メタデータだけあって中身が無い |
| NV-71 | **読もうとすると materialization（ダウンロード）が走り、数秒〜数分ブロックする。** materialization は `bird`（iCloud）/ `fileproviderd`（サードパーティ）が行い、**ユーザセッション内のプロセスからの要求でないと動かない** |
| NV-72 | **`NSFileCoordinator` を使わないと materialization が起動しない、あるいは File Provider の内部ロックと衝突する**（Claude Code が実際に踏んでいる）。本アプリは現状 `NSFileCoordinator` を一切使っていない |
| NV-73 | **単純に列挙してサムネイルを作る処理が、ユーザのクラウドストレージを全件ダウンロードさせる**（帯域・従量課金・ディスク容量の三重の被害）。NV-37 の縮退が最も切実に効く場所 |
| NV-74 | 判定候補は `URLResourceKey.ubiquitousItemDownloadingStatusKey`／`isUbiquitousItemKey`／`SF_DATALESS` フラグ／パスが `~/Library/CloudStorage/` 配下か。**どれが確実かは要実測** |

### 8.11.8 実測計画 — 推測のまま設計に組み込むと危険な順

**1-16b は本表の上から順に潰すことから始める。**

検証環境について: **1-16c の名前長・パス長の実測で実 NAS を SMB 経由で使った
実績がある**（CLAUDE.md §0「名前とパスの制限は実測で決めた」の表に
「SMB（実 NAS）」の実測値がある）。§8.4 と 10章 §10.0 に残っていた
「検証に使えるネットワークボリュームが無い」という記述は、それより前の時点の
ものでもう成り立たない。**ユーザの実データがある共有には触れず、専用の一時
フォルダだけを作り、最後に必ず消したことを確認する**（1-16c で確立した手順）。
NFS / WebDAV / File Provider 系クラウドについては環境の有無が未確認なので、
着手時にユーザへ確認すること。

| 優先 | 確認項目 | 未確定だと何が壊れるか | 関連 |
|---|---|---|---|
| 最高 | `volumeUUIDString` / inode がネットワークで何を返すか | ファイル同一性の基盤。誤同定は**上書き事故**に直結 | NV-21 / [ID-01] / [FS-03] |
| 最高 | `renamex_np(RENAME_EXCL)` が SMB で通るか（`ENOTSUP` か）| 通らないと**既存ファイルを黙って上書きする**。1-16c で移動をこれに置き換えたばかり | NV-22 |
| 最高 | `NSWorkspace.recycle` の実際の挙動（エラーか、成功＋URL 無しか）| 「ゴミ箱」が無言の完全削除／無言の失敗になる | §8.4 NV-01〜03 |
| 最高 | TCC「ネットワークボリューム」権限の発火条件と、開発ビルドでの再許可頻度 | **検証作業そのものが成立するか** | NV-63 |
| 高 | 大文字小文字のみの改名・NFC/NFD 差異での照合 | 静かに失敗する／別ファイルを潰す | NV-26 / NV-27 |
| 高 | FSEvents が本当に何も届かないか（`/Volumes` のマウント検知は届くか）| 10章 §10.0 のポーリング経路が実際に働くか。設計全体が変わる | NV-20 / NV-43 / §8.4 NV-04 |
| 高 | `NSWorkspace` のマウント／アンマウント通知が来るか | 2-2 の着脱検知（VD-01〜06）の手段が変わる | NV-43 |
| 中 | 空き容量（`...ForImportantUsage` / plain）の値 | 0 を返すと**正当な操作を誤って拒否する**（1-16c の事前検査） | NV-31 |
| 中 | サーバサイドコピーの capability（`VOL_CAP_INT_COPYFILE`）が実 NAS で立つか | 立つなら同一サーバ内コピーの体感が桁で変わる | NV-23 |
| 中 | xattr / 作成日 / **追加日** / ロックの可否 | 列・ソート・機能の縮退範囲が決まる | NV-51 |
| 中 | 切断時の errno と、そこからの回復手順 | エラー文言（`PosixFailure`）の設計に必要 | NV-47 |
| 中 | `flock` / `fcntl` の可否 | 排他設計の前提 | NV-60 |
| 低 | `getattrlistbulk` の Sequoia 不具合が現在も再現するか | 列挙方式の選択 | NV-34 |
| 低 | File Provider 系クラウドの判定手段 | 別タスクに切り出してよい | NV-74 |

### 8.11.9 設計指針（上記から導かれる横断的な方針）

| # | 指針 |
|---|---|
| NV-80 | **capability 検出主義。** 「ネットワークかどうか」ではなく「clone できるか」「`RENAME_EXCL` が使えるか」「advisory lock が使えるか」「ゴミ箱があるか」で分岐する [NV-11] |
| NV-81 | **縮退を明示的に設計する。** 機能が使えない場所では ①項目を出さない ②無効化して理由を示す ③代替に落とす、のどれかを選ぶ。**黙って別の動作に落ちるのが最悪**（ゴミ箱→完全削除、移動→コピー＋削除）|
| NV-82 | **すべてのファイル I/O を非同期・キャンセル可能・タイムアウト付きにする** [NV-40] |
| NV-83 | **部分成功を第一級の概念にする** [NV-44][RB-04][ER-13] |
| NV-84 | **破壊的操作は「退避してから書く」** [NV-45] |
| NV-85 | **場所の永続化はパス文字列に依存しない** [NV-42] |
| NV-86 | **共有上にアプリ由来のファイルを作らない** [NV-53] |
| NV-87 | **ユーザに「ここはネットワークである」ことを伝える。** 遅い・自動更新されない・ゴミ箱が無い・一部機能が使えない、を UI で説明できると不具合報告の大半が消える [FS-06 の警告表示の延長] |
| NV-88 | **サーバ側の実装差を織り込む。** Samba / TrueNAS / Synology / QNAP / Windows Server で挙動が違う。**特定のサーバでの成功を一般化しない** |
