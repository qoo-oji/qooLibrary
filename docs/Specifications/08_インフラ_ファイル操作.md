## 8.1 FileOperationService [FO-01]

### ゴミ箱を持てないボリューム [NV-01〜NV-04]

> **実測で確定した。詳細と決定事項は §8.11.4 にある。** 本節は要約のみ。

**[実測] SMB 3 系統（Samba/QNAP・Apple・Windows）すべてでゴミ箱は存在しない。**

| 経路 | 結果 |
|---|---|
| `FileManager.url(for: .trashDirectory, appropriateFor:)` | `NSCocoaErrorDomain 3328` を **0.01 秒**で返す → **事前判定に使える**（NV-01 の答え）|
| `FileManager.trashItem` | `3328` で失敗し、**ファイルは残る** |
| **`NSWorkspace.recycle`（本アプリが使う経路）** | **macOS がシステム確認ダイアログを出す**（「この項目はすぐに削除されます。取り消せません」）→ 承諾で完全削除・**成功・返却 URL 0 件**／キャンセルで `3072`（`NSUserCancelledError`）・ファイルは残る |
| UI 文脈の無いプロセス | ダイアログを提示できず**完了ハンドラが永久に呼ばれない** |

**したがって、以前ここに書いていた懸念のうち:**

- 「黙って完全削除されることはない」→ **正しい。** OS が必ず確認する
- 「成功しても `trashURL` が nil なら Undo が復元できない」→ **現実に起きる。** 返却 URL は 0 件だった
- 「⌘Z を押しても画面上は何も起きない」→ **現実に起きる**（`CommandStack.undo()` が `.partial` を提示しないため）

**残る問題は「無言の削除」ではなく、次の 4 つ**（決定事項は §8.11.4 の NV4-01〜04）:

1. ユーザーは「ゴミ箱に入れる」を選んだのに**完全削除の確認**が出る。しかもアプリ自身の確認シート（[PD-02] の件数・合計サイズ、[PD-14] の登録フォルダ強制解除）を通らない
2. 成功しても **⌘Z が無言で何もしない**のに、Edit メニューの「取り消す」は有効に見える
3. ダイアログが出ている間 `FileOperationService`（`actor`・直列）が塞がり、**アプリの全ファイル操作が停止する**
4. ユーザー自身のキャンセルに対して**エラーダイアログが出てしまう**（`NSUserCancelledError` を素通しするため）

**[文献] 「常に無い」と決め打ちしてはならない。** AFP 3 は共有ルートの `.Trash` を使う経路を持ち、
**ネットワークホームフォルダ**はプロトコルによらず例外的にゴミ箱が働く。→ **必ず事前判定する。**

**NV-04（変更検知）は §8.11.5 で実測済み** — FSEvents は他マシンの変更を報告しないが、
ディレクトリ mtime のポーリングは 1 秒以内に検知できる。10章 §10.0 の併用設計は妥当だった。

### 実装上の確定事項（1-14 で実装）

| # | 内容 |
|---|---|
| PD-10 | `deletePermanently` は**最初の失敗で中断しない** [ER-13]。成功・失敗・スキップを `DeletionOutcome` に個別に集めて返し、完了後に結果サマリを提示する [ER-12][ER-14]。他の一括操作（`transfer` 等）が「最初の失敗で例外を投げ、それまでの `OpReceipt` を捨てる」形なのに対し、完全削除だけこの形にする理由は、**「実際にはファイルが消えているのに操作は失敗扱いで記録も残らない」状態が復元不能な事故に直結する**ため |
| PD-11 | PD-06 の「都度尋ねる対象」は**ロック済み項目**とする。ER-11 が定める「ユーザーの選択によって結果が変わるもの」に完全削除で該当するのはこれだけで、Finder も同じくロック項目のみを個別に確認する。「以降すべてに適用」の状態は UI 側が `DeletePermanentlyOptions.lockedItemResolver` に閉じ込めて保持する（`BatchNotificationSession` を待たない）[設計判断] |
| PD-12 | 確認は**操作対象 1 件ごと**に行い、フォルダ配下の個々のロック項目ごとには行わない。フォルダ自身がロックされていなくても**配下にロック項目を含めば尋ねる** — `FileManager.removeItem` はロック済みの子に当たった時点で失敗し、そこまでに消した子だけが失われた中途半端な状態を残すため [設計判断] |
| PD-13 | ロック解除は削除の直前にのみ行い、**削除に失敗したら元に戻す**。シンボリックリンクの先へは入らない（`removeItem` はリンク自体しか消さないため、リンク先のロックを外してはならない）|
| PD-14 | 完全削除で実体を失うライブラリ／テンポラリ登録は**強制的に登録解除する** [ユーザー要望]。対象の照合は削除の**前**（ブックマークが解決できるうち）に行い、解除は削除の**後**に行う（先に解除するとアクセススコープが閉じて削除自体が権限エラーになる）。確認ダイアログにも登録が解除される旨を明示する |
| PD-15 | メニュー配置は Finder と同じく**「ゴミ箱に入れる」[FM-04] の ⌥ 代替**とする（`modifierKeyAlternate(.option)`、13章 §13.7.1）。対にすることで「ゴミ箱を出せない場面で完全削除だけが現れる」経路が構造的に無くなる。**[訂正]** 当初は「SwiftUI では ⌥ による入れ替えを実装できない」との誤った判断から「その他 ▸」サブメニューへ退避していたが、`View.modifierKeyAlternate(_:_:)`（macOS 15.0+）で実装可能と判明したため、サブメニューは廃止した |

### 8.7.1 登録フォルダの縮退状態 [SB-05][FS-08][LP-04][VD-11]

登録フォルダには、本アプリの制御外で操作が加わる——ボリュームのイジェクト、削除、移動、リネーム。
**「ブックマークを解決できたか否か」の二値では、性質のまったく異なる事象が同じ扱いに潰れる。**
ボリューム未接続は「待てば必ず戻る」ので登録を絶対に消してはならず、完全削除は「戻らない」ので
登録の整理をユーザーに促すべきである。この区別を状態として持つ。

#### 実測にもとづく前提

以下は使い捨てのプローブと `hdiutil` のスパースイメージで実測して確定させた事実であり、
設計はこれらを前提にしている。**推測で置き換えないこと。**

| # | 実測結果 |
|---|---|
| BM-1 | 登録フォルダのリネーム・移動、祖先のリネームでは、ブックマークは**追従して解決に成功する**（`isStale = true`）|
| BM-2 | **ゴミ箱へ移動しても解決は失敗しない。**`~/.Trash/…` を指したまま成功する（inode を追跡するため）|
| BM-3 | 完全削除は `NSCocoaErrorDomain` code = 4 |
| BM-4 | **ボリュームのアンマウントも code = 4。**エラーコードだけでは BM-3 と区別できない |
| BM-5 | **`.withoutMounting` を付けない解決は、未マウントのボリュームを実際にマウントする。**ネットワークボリューム（FS-06）ではタイムアウトぶんブロックし得る |
| BM-6 | 未マウント時でも `startAccessingSecurityScopedResource()` は `true` を返す。生存確認には使えない |
| BM-7 | 削除後に同名フォルダを作り直すと、inode が違っても**パスで解決してしまう** |
| BM-8 | セキュリティスコープの保持はアンマウントを妨げない（**サンドボックス下でも実測済み**。1-16 のイジェクト実装時に、実アプリと同じ entitlement でアドホック署名した probe で `startAccessingSecurityScopedResource()` を保持したまま `unmountAndEjectDevice` が成功することを確認。したがってイジェクト前にアクセスを停止する処理は不要）|

#### 状態

|---|---|---|---|
| `.online` | 通常 | 制限なし | — |
| `.offline` | グレーアウト＋「ボリュームが接続されていません。接続すると自動的に復帰します」[LP-04][VD-11] | 「登録解除」のみ。**展開しても子を読みに行かない** | マウント検知で自動 [VD-03] |

#### 判定順序 [設計判断]

**ボリュームのマウント状態を、ブックマークを解決する「前」に見る。**
順序を逆にすると BM-5 を踏む——未接続を判定するはずの処理が、その判定の過程で
ボリュームをマウントしてしまう。

```pseudo
resolveStatuses(folders):
    # ① マウント済みボリュームの UUID → URL マップを 1 回だけ作る。
    #    登録ごとに問い合わせない（性能）
    mounted = mountedVolumeURLs() をUUIDで索引化

    for folder in folders:
        # ② 未マウントならここで打ち切る。解決を一切試みない [BM-5 の回避]
        if folder.volumeUUID != nil && mounted[folder.volumeUUID] == nil:
            yield .offline(folder.volumeUUID); continue

        # ③ マウントは抑止して解決する
        switch bookmarks.resolve(folder.bookmarkData)   # 既定で .withoutMounting
          case .offline: yield .missing; continue       # マウント済みなので削除と断定してよい
          case .resolved(url): break

        # ④ ゴミ箱配下か [BM-2]
        if url.pathComponents contains ".Trash" または ".Trashes":
            yield .inTrash(url); continue

        # ⑤ 実在とディレクトリ種別の確認
        if !isDirectory(url): yield .missing; continue

        yield .online(url)
```

| # | 要件 |
|---|---|
| RG3-01 | `BookmarkResolving.resolve` は既定で `.withoutMounting` を付ける。マウントを許す解決は、ユーザーの明示的な操作からのみ呼ぶ別 API に分ける [BM-5]。**[1-16b で範囲を拡大] これは起動経路にも適用する。** `RegisteredFolderStore.loadAndActivateAll()` と `VolumeAccessStore.loadAndActivateAll()` は起動時に全件を解決するが、現在は `.withoutMounting` を付けていない。ネットワーク共有が登録されていてサーバが不在だと、**起動時に接続タイムアウト分ブロックし、ユーザーが何もしていないのに認証ダイアログが出る**（§8.11.11 NV-91）。**上限時間も設ける** |
| RG3-02 | `RegisteredFolder` に `volumeUUID: String?` を持つ [VD-02]。`Optional` なので既存 JSON はそのままデコードでき、旧レコードは初回のオンライン解決時に埋める（値が `nil` であること自体が「未移行」を表すため、専用の移行フラグは不要）|
| RG3-03 | ゴミ箱判定は `pathComponents` の照合で行う。**`FileManager.url(for: .trashDirectory, appropriateFor:)` は使わない** — ボリュームによって `code 3328`（未サポート）で失敗することを実測で確認済み（同一マシンで `/` は成功、`/Volumes/T7` は失敗）|
| RG3-04 | いずれの状態でも**登録レコードを自動削除しない** [SB-05][R-01]。登録解除は必ずユーザーの明示的な操作で行う |
| RG3-05 | 入れ子の禁止 [RG-03][RG-04] は外部での移動によって事後に破れる（BM-1）。起動時とオンライン復帰時に再検証し、破れていたら警告する。**自動解除はしない** |
| RG3-06 | 表示中のタブが読み込みに失敗したとき、原因がボリューム未接続なら**祖先へ退避させない**。オフラインのプレースホルダを出し、履歴も破棄しない（破棄すると挿し直しても戻れない）。退避するのは削除・改名の場合のみで、退避先は登録ルートで止める（`NavigationRoot` の境界と揃える）。**[1-16b へ前倒し] ネットワークでは切断が日常であり、1-17 を待つと現実に踏まれる**（§8.11.11 NV-93）。判定は「マウント一覧に無い」で行い、**解決を試みる前にマウント状態を見る** |
| RG3-07 | フェーズ 1 では着脱検知を持たないため、判定はツリー更新時にマウント一覧と突き合わせる受動的なものに留める。2-2 で `NSWorkspace` のボリューム通知に置き換える（10.2 節）。**状態モデルと判定順序は変えず、遷移の駆動方法だけを差し替える** |
| RG3-08 | ゴミ箱を監視する必要はない。`.inTrash` は解決先を見るだけの受動的な判定であり、[TR-07] の「システムのゴミ箱を監視しなくて済むようにする」方針と整合する |

## 8.11 ネットワークボリュームと File Provider（1-16b）

> **本節の記述には必ず分類札を付ける。**

### 8.11.0 測定環境

| 系統 | 実体 | 位置づけ |

### 8.11.1 「ネットワークかどうか」は判定できない [NV-10][NV-11]

**[実測]** ボリューム種別による分岐は成立しない。`volumeIsLocal` をすり抜ける経路が実在する。

| ケース | `volumeIsLocal` | 実体 |
|---|---|---|
| SMB / NFS / AFP / WebDAV | false | ネットワーク |
| **File Provider（iCloud 等）** | **true** [実測] | ネットワーク。しかも**起動ボリュームと同じ `volumeUUID`・`isInternal=○`・`supportsPersistentIDs=○` を返す** |
| ネットワーク共有上のディスクイメージ（Time Machine のスパースバンドル等）| **true** [文献] | ネットワーク |
| FUSE 各種 | 実装依存 [文献] | — |

**[普遍]** Apple 自身が QA で同じ結論を述べている——
「ローカルとネットワークの区別は近年**曖昧**である。ネットワークボリュームが遅いとも、
ローカルボリュームがロックの問題と無縁とも仮定できない。**一般に、ボリューム種別から
仮定するのではなく、必要な機能が存在するかを検査すべきである。**」

**[文献]** macOS 26 の **FSKit** により第三者がユーザ空間でファイルシステムを実装できる
ようになった。Apple のドキュメントは「内容はローカル・ネットワーク・メモリのいずれから
来てもよい」としており、**判別不能な変種はこれから増える**。本アプリの最小対応 OS は
macOS 26 なので、これは将来の話ではなく現在の前提である。

### 8.11.3 ファイル同一性 — 最も危険な領域 [NV-21][ID-01][FS-03]

**[実測] 能力フラグは両方向に間違う。**

| サーバ | `supportsPersistentIDs` | 実際の同一性 | |
|---|---|---|---|
| Samba | × | **×**（破綻）| 一致 |
| Apple | ○ | ○ | 一致 |
| **Windows** | **×** | **○** | **偽陰性** |

- **Samba [実測]**: `st_ino` は**パス名から合成された値**で、改名・移動で変わり、
  **削除→同名で作り直すと同じ値が再利用される**（＝別ファイルが同一と判定される）。
  `fileResourceIdentifier` はマウントセッション内の連番（既存フォルダが `17,18,19,…`）で、
  セッション内では安定だが**再マウントをまたいでは保証されない**。
- **原因 [一次情報]**: Samba の `vfs_fruit` は `fruit:zero_file_id`（**既定 `yes`**）により、
  AAPL をネゴシエートしたクライアントへ**ゼロの File ID を返す**。man page 曰く
  「Samba の File-ID は inode 番号ベースで作成・削除をまたいで再利用されるため
  Mac クライアントには使えない。ゼロを返すことで **Mac クライアントはサーバの
  ファイル ID を使うことも信用することもやめる**」。**QNAP 固有ではなく Samba 系全般の既定。**
- **Windows [実測]**: NTFS の File Reference Number がそのまま渡る。改名・移動・書換で
  不変。再利用時は sequence number が増えるため誤同定が構造的に起きない
  （`0x0003_…0032` → `0x0004_…0032`）。**フラグは `×` なのに実際は完全に安定。**
- **[普遍] `volumeUUIDString` は 3 系統すべてで nil。** `FileIdentity` は
  volumeUUID ＋ inode の組なので、**SMB では必ず片肺になる**。

| # | 決定事項 |
|---|---|
| NV3-01 | **`FileIdentity` の `volumeUUID` に空文字を入れてはならない。** 現在の実装（`volumeUUIDString ?? ""`）では、**異なる 2 つのネットワーク共有をマウントすると別ファイルが同一と判定され得る**。ネットワーク上のボリュームには別の識別子（マウントポイント＋サーバ URL 等）を割り当てるか、そもそも同一性を扱わないと決める |
| NV3-02 | **`VolumeEligibilityChecker` の `supportsPersistentIDs` による `guard` を撤去し、FS-03 の実測プローブ（作成→移動→ID 再取得）に一本化する。** 実測プローブは 3 系統すべてを正しく分類できたが、フラグは Windows で偽陰性を出し、**実際には使える共有を誤って拒否する** |
| NV3-03 | それでも**ネットワーク上では同一性を当てにしない**。Apple/Windows で成立しても NV3-01 の問題が残り、再マウント後の保証も無い |

### 8.11.4 ゴミ箱 [NV-01〜NV-04]

**[普遍・実測] SMB 3 系統すべてでゴミ箱は存在しない。**

| 経路 | 結果 |
|---|---|
| `FileManager.url(for: .trashDirectory, appropriateFor:)` | `NSCocoaErrorDomain 3328` を **0.01 秒**で返す → **事前判定に使える** |
| `FileManager.trashItem` | `3328` で失敗。**ファイルは残る**。文言も良好 |
| **`NSWorkspace.recycle`（アプリが使う経路）** | **macOS がシステム確認ダイアログを出す**（「This item will be deleted immediately. You can't undo this action.」）→ Delete: 完全削除・**成功・返却 URL 0 件**／Cancel: `NSCocoaErrorDomain 3072`（`NSUserCancelledError`）・ファイルは残る |
| UI 文脈の無いプロセス | ダイアログを提示できず**完了ハンドラが永久に呼ばれない**（40 秒以上で確認）|

**[依存]** QNAP はサーバ側の `@Recycle`（Network Recycle Bin）が削除を受け止めた。
ただし QNAP 公式 FAQ に「**空のフォルダとサイズ 0 のファイルは @Recycle を経由せず
直接削除される**」とあり、この網には穴がある。Windows・Apple サーバには相当機能が無い。

**[文献]** AFP 3 は共有ルートの `.Trash` を使う経路を持ち、**ネットワークホームフォルダ**は
プロトコルによらず例外的にゴミ箱が働く。→ **「常に無い」と決め打ちせず、必ず事前判定する。**

| # | 決定事項 |
|---|---|
| NV4-01 | **`trash` を呼ぶ前に `.trashDirectory` を問い合わせる**（0.01 秒）。取れなければ「ゴミ箱に入れる」を提供しない |
| NV4-02 | ゴミ箱が無い場所では、Finder 同様に**アプリ自身の確認シート**（[PD-02] の件数・合計サイズ・登録フォルダの強制解除 [PD-14] を伴う）を出し、承諾されたら `deletePermanently` を使う。**Undo に積まない** [PD-05]。素のシステムダイアログに任せない |
| NV4-03 | `NSUserCancelledError`（3072）は**エラーとして提示しない**。ユーザー自身のキャンセルにエラーダイアログを出さない |
| NV4-04 | `recycle` の完了を待つ継続には**上限時間**を設ける。UI 文脈が無い経路（テスト・将来のバックグラウンド処理）で `actor` が永久に塞がるのを防ぐ |

### 8.11.5 変更検知 [NV-20][NV-43] → 10章 §10.0

**[実測] §10.0 の「FSEvents はネットワークで使えない」という前提は不正確だった。**

| 変更の出どころ | FSEvents | dir mtime ポーリング |
|---|---|---|
| **同じ Mac の別プロセス**（Finder 等）| **届く** [実測: SMB] | 届く |
| **別マシン**（真のリモート）| **届かない** [実測: Apple サーバで両面から確認] | **1 秒以内に見える** [実測] |

正しくは「**この Mac のカーネルを通らない変更は FSEvents に現れない**」。
ローカル VFS 由来かどうかの問題であり、プロトコルとは無関係 **[普遍]**。

**→ §10.0 の「FSEvents ＋ 2 秒ポーリング」の併用は、両輪とも必要性が実測で裏付けられた。**

**[依存・要注意]** `nsmb.conf` の既定は `dir_cache_min=30s` / `dir_cache_max=60s` で、
ディレクトリ情報は最大 60 秒キャッシュされる。にもかかわらず Apple サーバでは 1 秒で
見えた——SMB2 変更通知（`notify_off` が存在することが使用を示す）がキャッシュを
無効化しているためと考えられる。**変更通知を実装しないサーバでは最大 60 秒遅れ得る。**

### 8.11.6 実行モデル — ハングとスレッド枯渇【最重要】[NV-40][NV-46][NV-82]

**[実測] コア数ぶんの同期ブロッキング I/O で、協調スレッドプールは枯渇する。**
論理コア 10 の機で 10 本ブロックさせたところ、**ごく普通の `Task` が 5 秒間一度も動かなかった**。
`Task.detached` も同じプールを使う **[一次情報]**。

**[依存] 「無限ハングではない」は SMB 限定である。**

| プロトコル | 無応答時 |
|---|---|
| SMB | `nsmb.conf` の `max_resp_timeout` 既定 **30 秒** [一次情報] |
| **NFS（hard マウント＝既定）** | **割り込み不能に無限ハング。`intr` は既定でなく、`kill` も効かないことがある** [文献] |
| **FUSE-T**（macFUSE の後継。rclone/SSHFS/JuiceFS 等が使う）| **NFSv4 ループバックとして実装**されるため NFS と同じ特性。ユーザ空間サーバが死ぬと復帰しない [文献] |

**帰結**: SMB なら 30 秒で解放される（一時的な劣化）ものが、**NFS では
スレッドが永久に失われる**。

| # | 決定事項 |
|---|---|
| NV6-01 | **ブロッキング I/O を協調スレッドプールで行わない。** 専用のスレッド源（`TaskExecutor`、SE-0417）を設け、枯渇しても他を巻き込まない構造にする。`Task.detached` は executor preference を継承しないので明示的に指定する |
| NV6-02 | **メインスレッドで FS に触らない。** `NSWorkspace.icon(forFile:)` は例外（[実測] LaunchServices のみで I/O を伴わず、SMB でも 0.1〜0.4ms） |
| NV6-03 | **タイムアウトとは「待つのをやめる」であって「I/O を止める」ではない。** macOS に中断可能なファイル I/O は無く、`Task.cancel()` はブロック中の syscall を割り込まない。止まったスレッドは戻ってこない前提で設計する |

### 8.11.7 性能と縮退 [NV-33〜NV-39]

**[実測] 列挙の prefetch は本当に効く。** `contentsOfDirectory(at:includingPropertiesForKeys:)`
で prefetch した resource value は URL にキャッシュされ、**実体を削除した後でも読める**。
つまり一覧の読み込みは N 往復ではなく **1 往復**。既存の `reload()`／`enumerateMatches`／
`children(of:)` はいずれも正しく prefetch している。**この性質を壊さないこと**——
prefetch していないキーを後から読むと項目ごとに往復が発生する。

**[実測]** 書き込み先への問い合わせ（`volumeIsReadOnly`／`access(2)`／`pathconf`／
`volumeMaximumFileSize`／名前長の規則／空き容量）は**操作ごとに 1 回にまとめる**。
**1-16b で `transfer` の `preflight` に集約済み**——項目ごとに尋ねるものは残っていない
（`checkFileSizeFits`／`checkNameFits` は走査で拾った「いちばん大きい 1 件」
「いちばん長い 1 件」に対してだけ呼ぶ）。

**[文献]** I/O 増幅を起こす機能（サムネイル生成・Quick Look のカバー生成・
再帰的な集計 [DT-05][DT-06]・再帰検索・アーカイブの中身一覧）は、
ネットワークでは縮退の対象。09章 §9.6（DS-01〜DS-07）の一括制御が既にその器になっている。

### 8.11.8 File Provider（iCloud / OneDrive / Dropbox / Box / Google Drive）[NV-70〜NV-74]

**[文献] macOS 13 以降、4 社ともすべて Apple の File Provider で実装され**、
`~/Library/CloudStorage/<Provider>-<Domain>` に置かれる。iCloud Drive も同じ機構のため、
**個別対応ではなく File Provider として一括で備えれば足りる**。

**[実測: iCloud]**

| 操作 | 実体化するか | 所要 |
|---|---|---|
| 列挙（prefetch 付き）| しない | 1 ms |
| `stat` / `resourceValues` | しない | 0 ms |
| `NSWorkspace.icon(forFile:)` | しない | 3 ms |
| **`Data(contentsOf:)`** | **する** | **1065 ms / 2MB** |

`SF_DATALESS`（`0x40000000`、`SF_SYNTHETIC` の一部）は `lstat` 0ms で確実に判定でき、
`ubiquitousItemDownloadingStatus` とも一致した。**このフラグは File Provider 機構そのものが
立てるため、第三者プロバイダでも同じはず [文献]**（未検証）。

| # | 決定事項 |
|---|---|
| NV8-01 | **`isDataless` は「使う直前」に見る。** ユーザーが触らなくても「ストレージを最適化」で脱水される。「さっき読めたから今も読める」は成り立たない |
| NV8-02 | **自動生成（サムネイル・カバー・集計）は dataless なら行わない。** ユーザーが明示的に頼んだ操作（Quick Look・展開・開く）は従来どおり実体化してよい |
| NV8-03 | **`NSFileCoordinator` の要否は「不要」から「要再評価」へ差し戻す**（下記）|
| NV8-04 | **「同期先の制約」という第 3 の上限を設ける。** これまで ①macOS の上限 ②書き込み先 FS の上限 を検査してきたが、③**同期サービスの上限**は誰も教えてくれない [下記] |

#### `NSFileCoordinator` — 過去の結論の訂正

フェーズ1完了前監査で「協調読み取りは**不要**と実測で判明」と記録したが、
**その測定はロック構造を持たない単発スクリプトで行ったものであり、実アプリには一般化できない。**

**[文献]** File Provider 配下の読み取りで **`EDEADLK`（errno 35, "Resource deadlock avoided"）**
が発生する事例が報告されている。一覧と `stat` は成功し**読み取りだけが失敗**する。目印は
`Blocks: 0`（＝ dataless）。**iCloud・Google Drive・Dropbox・OneDrive・Box すべてで発生**。
原因は「プロセスが同期読み取り中にロックを保持しており、File Provider が同じプロセスへ
コールバックする必要が生じるとデッドロックする」。

実アプリは `FileOperationService`（`actor`・直列）・`ThumbnailService`（`actor` ＋
同時実行スロット）を持ち、**コア数ぶんのブロッキング I/O で協調プールが枯渇する
（8.11.6 の実測）**。**実体化のためのコールバックが枯渇したプールからスレッドを
得られなければ、それは本物のデッドロックである。** NV6-01（専用 executor）を入れれば
構造的に回避できる可能性があるため、**両者は一体で設計する**。

#### 「ファイルシステムは許すのに、同期が黙って失敗する」

**[文献]** これは既存のどの失敗とも異なる種類で、**エラーが出ない**。

| 制約 | 値 | 現在の事前検査 |
|---|---|---|
| **OneDrive/SharePoint のパス長** | **400 文字**（macOS は 1024）| `pathconf` は 1024 を返す → **通過する** |
| 禁止文字 `" * : < > ? / \ |` | Dropbox・OneDrive・Box に共通 | `FileNameValidation` は macOS 基準（`/` と `.` のみ）→ **通過する** |
| ファイルサイズ上限 | プロバイダごと | `volumeMaximumFileSize` は APFS の値 → **通過する** |

コピーも作成も成功し、エラーも出ず、**そのファイルは永久に同期されない**。
本アプリは `(成年コミック) [作者] タイトル 第01巻` のような長く記号を含む名前を
常態的に扱うため、400 文字制限は現実的に踏む。**個別ファイルの同期エラーを
問い合わせる公開 API は見当たらなかった**（`NSURLUbiquitousItem…ErrorKey` は iCloud 専用）。

→ File Provider 配下と分かる場合は**より厳しい既定で警告する**（拒否ではなく警告。
誤って断らない原則に従う）。

#### その他 [文献]

- **競合コピー**が各社の同期で勝手に生成される（`… (conflicted copy).ext` 等）。
  外部からの変更として `DirectoryChangeHub` が正しく扱える
- `~/Library/CloudStorage/` へは `startAccessingSecurityScopedResource()` が要るとの報告。
  既存の `VolumeAccessStore`／`RegisteredFolderStore` の枠組みで足りる
- SDK に **`NSFileProviderThumbnailing`** があり、**実体化せずにサムネイルを得られる
  可能性**がある。`QLThumbnailGenerator` がこれを経由するなら、アーカイブを自前で読む
  現在の経路より遥かに安全。**要検証**

### 8.11.10 設計指針 [NV-80〜NV-88 の改訂]

3 プロトコル・3 サーバ・4 つの破綻を経て、すべてに耐える原則は 1 つに収束した。

> **プロトコルもボリューム種別も判定しない。**
> 依存する機能ごとに、**依存する直前に、実際の振る舞いを測る**。
> そして**測れないもの——応答が返ってくるか——は、測ろうとせず
> 「待つのをやめられる」構造で受ける。**

| # | 指針 |
|---|---|
| NV-80 | **能力フラグを「できる証明」にも「できない証明」にも使わない。** 3 系統で偽陽性・偽陰性の両方を実測した。フラグは「速い経路を試す根拠」までに留め、正しさは実際の呼び出しで担保する（`COPYFILE_EXCL` を必ず自分で指定する、という既存の判断の一般化）。`ENOTSUP`/`EOPNOTSUPP` が返ってきたときに縮退経路へ落ちる |
| NV-81 | **縮退を明示的に設計する。** 黙って別の動作に落ちるのが最悪（ゴミ箱→完全削除、移動→コピー＋削除）|
| NV-82 | **ブロッキング I/O を協調プールとメインスレッドから追い出す** [NV6-01〜03] |
| NV-83 | **部分成功を第一級の概念にする** [RB-04][ER-13] |
| NV-84 | **破壊的操作は「退避してから書く」**（`withReplaceBackupCleanup`）|
| NV-85 | **場所の永続化はパス文字列に依存しない** [NV-42] |
| NV-86 | **共有上にアプリ由来のファイルを作らない** [CL-01〜05 の延長] |
| NV-87 | **ユーザに「ここはネットワークである」ことを伝える** [FS-06]。**現在 `VolumeWarning.networkVolumeFSEventsUnreliable` は生成されているが `RegisteredFolderStore` が捨てている**（`VolumeCapability.isReadOnly` が「計算されていたのに誰も読んでいなかった」のと同型）|
| NV-88 | **特定のサーバでの成功を一般化しない。** 本節の [依存] 札はすべてこの原則の実例である |
| **NV-89** | **書き込み可否は `access(2)` で確かめる。** [実測] Windows 共有で、モードビットは `drwx------`（書ける）、`volumeIsReadOnly` は `×`（読み取り専用でない）と**両方が嘘をつき**、`access(W_OK)` だけが正しく `false` を返した。現在の `checkDestinationIsWritable` は `volumeIsReadOnly` しか見ておらず、**検査を通過してから失敗する** |
| **NV-90** | **SMB では、開いたままのハンドルがあるとフォルダを削除できない** [実測・1-16b の実装時に再測定して訂正]。**「時間が経てば直る」ではない** — 下記 §8.11.12 を参照 |

### 8.11.11 状態遷移で露出する穴 [再チェックで発見]

### 8.11.12 フォルダを削除できない本当の理由 [NV-90 の訂正]

**当初の記述は誤りだった。** 「削除直後のディレクトリ削除が一時的に失敗し、
少し後に別プロセスからは成功した（delete-on-close の反映待ち）」と書いていたが、
1-16b の実装時に測り直したところ**時間とは無関係**だと判明した。

**[実測]** SMB 共有（QNAP／Samba）の使い捨てフォルダで測定:

| 条件 | 親フォルダの `rmdir` |
|---|---|
| 子を消しただけ（ハンドルなし）| **即成功**（0ms、4/4 回）|
| 8MB を書いた直後に消す | **即成功**（0ms、4/4 回）|
| 子ディレクトリを消した直後に親 | **即成功**（0ms、4/4 回）|
| **消した子のハンドルを開いたまま** | **`ENOTEMPTY`(66) のまま。5 秒待っても成功しない** |
| 同上・**ハンドルを閉じた直後** | **即成功** |

**[普遍]** 同じ手順をローカル（APFS）で行うと、ハンドルを開いたままでも
`rmdir` は**成功する**。POSIX では `unlink` が即座にディレクトリ項目を外すのに対し、
SMB は Windows 由来の **delete-on-close** 意味論を持ち、**最後のハンドルが
閉じるまで項目が残り続ける**ため。プロトコルの意味論の違いであって、
サーバ実装やタイミングの問題ではない。

| # | 決定事項 |
|---|---|
| NV90-01 | **待って再試行する設計にしない。** 原因が開いたハンドルである以上、待っても直らない（実測で 5 秒待っても変わらず、閉じた瞬間に成功した）。バックオフを伸ばすのは待ち時間を増やすだけである |
| NV90-02 | **引き金は他のアプリが握っているハンドルであって、本アプリではない** [実測・当初この項目を「自分でハンドルを開いたまま消している疑い」として書いたが誤りだった]。`FileHandle` は**解放時に fd を閉じる**（`throw` で抜けた場合も含めて実測で確認）ため、明示的に閉じ忘れても開いたままにはならない。したがって対処できるのは NV90-03 の**説明のしかた**だけで、Finder・Quick Look・メディアプレイヤー等が掴んでいる場合はユーザーがそれを閉じる以外に手が無い |
| NV90-03 | **`ENOTEMPTY` を「中身を空にしてください」と説明しない。** その案内は、空にしたのに消せないこの状況では**嘘になる**。「この中のファイルを開いているアプリがあるかもしれない」と伝える |
| NV90-04 | 短い再試行を 1 回だけ残すのは、**外部プロセスが偶然その瞬間だけ掴んでいた**場合に効くことがあるため。それ以上は伸ばさない |
