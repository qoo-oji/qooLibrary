## 1.2 ビルド構成

| 構成 | 内容 |
|---|---|
| `Debug` | ログレベル `debug`、アサーション有効 |
| `Release` | 既定ビルド。UnRAR を含む [LC-10][LC-11] |
| `Release-Permissive` | `PERMISSIVE_ONLY_BUILD` 有効。UnRAR を除外し libarchive の RAR リーダを使用 [LC-12] |

```swift
// Package.swift（抜粋）
.target(
    name: "QooInfrastructure",
    dependencies: ["QooKit", "CLibarchive"] + (permissive ? [] : ["CUnrar"]),
    swiftSettings: permissive ? [.define("PERMISSIVE_ONLY_BUILD")] : []
)
```

| # | 要件 |
|---|---|
| B-01 | `PERMISSIVE_ONLY_BUILD` の有無は `BuildConfiguration.rarBackendName` として実行時に取得でき、アバウト画面・診断情報に表示する [LC-13][LG2-05] |
| B-02 | libarchive は `Scripts/build-libarchive.sh` で `arm64` / `x86_64` の xcframework を生成し、アプリへ同梱する。システムの `libarchive.dylib` にリンクしない [LC-15] |
| B-03 | UnRAR は C++ のため Objective-C++ ラッパー（`QooUnrarBridge.mm`）経由で Swift から呼ぶ。C++ interop の直接利用は行わない [設計判断: ビルド安定性を優先。T-13 の検証結果で見直す] |
| B-04 | UnRAR 呼び出しラッパーの先頭コメントに、RAR 互換アーカイバの開発に使用してはならない旨を記す [LC-26] |
| B-05 | 依存追加時は `THIRD-PARTY-NOTICES.md` の更新を PR チェックリストの必須項目とする [LC-05] |

### 標準の場所への到達性 [B-24〜B-27、実測]

実アプリと同じ entitlement でアドホック署名した最小アプリ（許可は 1 件も無い
状態）で実測した結果。**推測ではなく、この表を根拠に
`StandardLocation.accessRequirement` を決めている。**

| 場所 | 素のサンドボックス | 上の entitlement 追加後 | 必要な手段 |
|---|---|---|---|
| `~/Downloads` | ✗ (NSCocoaError 257) | **○** | entitlement のみ |
| `~/Pictures` `~/Music` `~/Movies` | ✗ | **○** | entitlement のみ |
| `/Applications` `/Applications/Utilities` `/Volumes` | **○** | ○ | 何も要らない |
| `~`（実ホーム） `~/Library` `/Users/Shared` | ✗ | ✗ | 自身または**祖先**への許可 |
| `~/Documents` `~/Desktop` | ✗ | ✗ | **その場所そのもの**への許可 |

| # | 要件 |
|---|---|
| B-24 | デスクトップ・書類には対応する entitlement が**存在しない**（`/System/Library/Sandbox/Profiles/application.sb` を直接引いて確認。`com.apple.security.files.downloads.*` はあるが desktop/documents は無い）。`NSOpenPanel` でユーザーに選ばせ、Security-Scoped Bookmark を `VolumeAccessStore` に永続化する経路で扱う [ユーザー判断] |
| B-25 | **`/` への許可はサンドボックス層を通すだけで TCC 層は通さない。** 書類・デスクトップは `/` を許可していても毎回 TCC のダイアログが出る。したがって「祖先への許可で足りる場所」と「その場所そのものへの許可が要る場所」を区別する [実測] |
| B-26 | **TCC の許可はコード署名の同一性（アドホック署名では CDHash）に紐づくため、開発ビルドでは再ビルドのたびに失効する。** Security-Scoped Bookmark はコンテナに紐づいて再ビルドを越えて生き残るのとは対照的で、パネル＋ブックマーク経路に寄せる実利がここにある [実測。ユーザー報告「許可されても記憶されない」の真因] |
| B-27 | サンドボックス下でも `getpwuid(getuid())->pw_dir` は実ホーム（`/Users/<name>`）を返す。`FileManager.homeDirectoryForCurrentUser` / `NSHomeDirectory()` はコンテナを返す [実測] |

| # | 要件 |
|---|---|
| B-20 | フルディスクアクセスは entitlement では取得できない。**しかも付与しても App Sandbox のカーネルレベルの制限は回避されない**ため、アクセスの付与導線は環境設定「アクセス権」タブ（`VolumeAccessStore`）が担う [実測による訂正、CLAUDE.md 1-4 節参照] |
| B-21 | 付与状態の判定は「TCC 保護領域（`~/Library/Application Support/com.apple.TCC` 等）への読み取り試行」で行う。API での照会手段がないため [設計判断] |
| B-22 | 未付与でもブックマーク済みフォルダの範囲で動作すること。未アクセス領域はツリー上で「アクセス権がありません」と表示し、付与導線を出す [SB-04] |
| B-23 | ブックマーク解決は `BookmarkResolver` に集約する。解決失敗時は例外を投げず `.offline` を返す [SB-05] |

```swift
public protocol BookmarkResolving: Sendable {
    /// 登録時にブックマークを生成する。FS-02/FS-03 の検証を通過していることが前提。
    func makeBookmark(for url: URL) throws -> Data                      // [RG-07]
    /// 起動時・マウント時に解決する。失敗は throw せず .offline を返す。 [SB-05]
    func resolve(_ data: Data) -> BookmarkResolution
    /// 解決した URL に対する startAccessing/stopAccessing をスコープ管理する。
    func withAccess<T>(_ data: Data, _ body: (URL) async throws -> T) async throws -> T
}

public enum BookmarkResolution: Sendable {
    case resolved(url: URL, isStale: Bool)
    case offline(reason: OfflineReason)   // .volumeNotMounted / .permissionDenied / .invalidBookmark
}
```

## 1.5 ファイルシステム適合検証

要件 FS-01〜FS-09 の実装。フォルダ登録の前段で必ず通す。

```swift
public struct VolumeCapability: Sendable {
    public let volumeUUID: String            // .volumeUUIDStringKey [VD-02]
    public let fileSystemName: String        // .volumeLocalizedFormatDescriptionKey
    public let supportsPersistentIDs: Bool   // .volumeSupportsPersistentIDsKey [FS-02]
    public let isNetworkVolume: Bool         // .volumeIsLocalKey == false [FS-06]
    public let isReadOnly: Bool
}

public enum VolumeEligibility: Sendable {
    case eligible(warnings: [VolumeWarning])       // 例: .networkVolumeFSEventsUnreliable [FS-06]
    case rejected(reason: VolumeRejection)         // 理由 + fileSystemName を保持 [FS-04]
}

public protocol VolumeEligibilityChecking: Sendable {
    func capability(of url: URL) throws -> VolumeCapability
    /// FS-02 の宣言値に加え、FS-03 の実測（作成→移動→ID 再取得）を行う。
    func evaluate(_ url: URL) async throws -> VolumeEligibility
}
```

```pseudo
evaluate(url):
    cap = capability(of: url)
    if cap.supportsPersistentIDs == false:
        return .rejected(.noPersistentFileID(fileSystem: cap.fileSystemName))   # [FS-01][FS-04]

    # FS-03 実測
    tmpA = url / ".qoo-fsprobe-<uuid>"
    create tmpA (0 byte)
    idA = fileID(tmpA)                       # .fileResourceIdentifierKey + st_ino
    tmpB = url / ".qoo-fsprobe-<uuid>-moved"
    move tmpA -> tmpB                        # FileOperationService は使わない（登録前のため）
    idB = fileID(tmpB)
    delete tmpB
    if idA != idB:
        return .rejected(.persistentIDNotPreserved(fileSystem: cap.fileSystemName))

    warnings = []
    if cap.isNetworkVolume: warnings.append(.fsEventsMayNotWork)                 # [FS-06]
    return .eligible(warnings)
```

| # | 要件 |
|---|---|
| B-30 | 実測用の一時ファイルは処理終了時に必ず削除する。異常終了で残った場合は次回起動時のクリーンアップ（RB-07 と同じ経路）で除去する |
| B-31 | ドラッグ＆ドロップ登録（DD-04）でも `evaluate` を通す。非同期のため、ドロップ受理後に検証し、失敗ならロールバックして理由を提示する [FS-05] |
| B-32 | 起動時に登録済みボリューム全件の `capability` を再取得し、`supportsPersistentIDs` が `false` に変わっていたらライブラリを読み取り専用に遷移させ、警告する [FS-08] |
| B-33 | 非サポートボリュームでもファイルマネージャー機能は制限しない。制限するのは登録のみ [FS-07] |
