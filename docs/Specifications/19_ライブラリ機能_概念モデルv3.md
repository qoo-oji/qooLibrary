# 19. ライブラリ機能 概念モデル v3

対応要件: 本章が定める処分表（§19.8）に基づき、要件定義書は v2.12 として段階的に改訂する

> **この文書の位置づけ**: フェーズ 2 で積み上げたライブラリ機能の**ユーザーに見える概念と導線を再設計する**ための基準文書。エンジン（パーサ・走査・GRDB 永続化・FSEvents 追従）は資産として維持し、変えるのは概念・導線・ウインドウ構成である。**本章と既存章（14・15 章等）が食い違う間は、本章が目標を、既存章が現状を表す。**各ステージの実装と同時に既存章を改訂する。実装ステージの分割は本章 §19.10、**再設計後のユーザー体験の要約は §19.11**（この要約が簡潔に書けることを、設計がシンプルであることの検収条件とする）。

## 19.1 目的と設計原則

**目的**: ユーザーが快適かつシンプルに自身のコミックライブラリを管理・運用できるようにする。

| # | 原則 | 意味 |
|---|---|---|
| P1 | **操作は 1 つずつシンプルに、組み合わせで多様に** | ユーザーからの操作は 1 つずつは極力シンプルにする。それを組み合わせると多種多様な使い方が実現できる方向で要件を整理する |
| P2 | **見えない複雑さは構わない** | ユーザーに見えないところで複雑・高度な処理をすることは妨げない（パーサ・同一性追跡・差分走査・ヒューリスティック解析などはエンジン内部に閉じ、カスタマイズ項目も設けない） |
| P3 | **高度な機能は「高度な設定」に隔離** | 正規表現などの複雑な機能は「高度な設定」としてまとめ、特定のボタンから呼び出さない限り既定のまま。高度な使い方の余地（正規表現等）は必ず残す |
| P4 | **登録と解除以外はフルオート** | ライブラリフォルダの操作はフルオートで機能提供する。ユーザーの明示操作は「登録」「解除」と、必要に応じての設定変更だけ |
| P5 | **シンプルに見せて、高度に使える** | 多すぎる情報と複雑すぎる UI はユーザー体験を損なう（保管庫機能が必要と判断した理由と同根——見たくないものを隠せることが価値）。どの画面も既定で見せる情報・操作は最小限にし、高度な情報・操作は求めたときにだけ現れる（段階的開示）。P3 はこの原則の設定画面への適用である |
| P6 | **状態より導出（実体が真実）** | ユーザーが管理する状態を増やさない。実体から導出できるものは導出し、実体の変化に自動で追随させる（自動で入り、自動で戻る）——ユーザーの邪魔にならず、しかしユーザーが把握・管理できる仕組みへの一元化。§19.12 のラベルの非表示・`FileSnapshot.isArchived` の計算プロパティ・§19.13 の件数導出はすべてこの原則の適用である |

> **P5 と P6 は対で読む**［ユーザー恒常指示］: **不要な情報がユーザーのノイズにならないように、でも仕組みとしてはシンプルに。** ノイズを消すために状態・区画・イベントを増やさない——導出で隠れるものは導出で隠す（§19.12 の非表示モデルが実例）。

**自動抽出の情報源と優先順位**［ユーザー指示］: **埋め込みメタデータ（ComicInfo・EPUB・PDF）が最も強く、次がフォルダ名、最後がファイル名**。登録ウィザードの説明もこの順で言う（メタデータ > ファイル名は実装済み [EM-03]。フォルダ名 > ファイル名の優先はエンジン側の現状を Stage 4 で確認・整合させる）。

参照モデル: [StackNest](https://github.com/shelfsmith/stacknest)（カタログ＋フィールド＋ブラウズ／フィルタ＋シェルフ）。そこに qooLibrary の固有資産——ファイルマネージャー連携・保管庫・埋め込みメタデータ・ファイル名／フォルダ名の解析エンジン——を載せる。

## 19.2 概念モデル（ユーザーに見えるもの）

| 概念 | 内容 | 現行からの変化 |
|---|---|---|
| **ライブラリ** | 登録したフォルダ。**登録した瞬間にライブラリとして機能し始める**（§19.3） | 「登録」と「有効化」の 2 段階を 1 段階に統合 |
| **ライブラリタイプ** | 本の種別（一般コミック／同人誌／同人CG…）。ライブラリ単位で、**登録時に自動判定**。StackNest の bookType 相当 | 手動選択 → 自動判定（設定から変更可） |
| **本** | 蔵書 1 件。タイトル・シリーズ・巻・評価・カバーを持つ | 変更なし（構造化列のまま） |
| **フィールド** | 本を分類する軸。**既定 5 種（著者・サークル・ジャンル・イベント・キーワード）を全ライブラリに保証**し、表示名の変更と追加ができる。値は多値で、自動抽出（ファイル名解析・埋め込みメタデータ）と手動編集の両方 | 旧「ラベルグループ」。可変スキーマ＋予約語割り当て → 既定＋追加可 |
| **ラベル** | フィールドの値 1 つ（例: 著者フィールドの「著者値A」）。**生きている実体を失うと自動的に隠れ、実体の復活・新規作成で自動的に戻る**——「見つからないファイル」と同型で、整理はフィールド編集の一覧から（§19.12） | 呼称維持。「ラベルの保管庫」という概念は廃止［ユーザー判断］。origin は表示専用（✨ の印）に格下げし、保護の判定には使わない（§19.4）。0 件ラベルの赤字・削除促し [LE-04][RC-07] も廃止 |
| **保護** | 「この部分は自動更新しないで」という印。ファイル全体、またはファイル×フィールド単位（§19.4） | 新設。origin 3 状態・manuallyRemoved・titleOrigin による個別の保護機構を置き換える |
| **シリーズスタック** | ライブラリ表示モードで、同一シリーズの本を 1 つの仮想的な集合（スタック）にまとめて表示する（Kindle のコレクション相当、§19.5b） | 新設［ユーザー指示。ライブラリ表示モードのみ］ |
| **シェルフ** | 保存した絞り込み（フィールド選択＋評価＋検索語）。左ペインに並び、ワンクリックで復元 | 新設（StackNest のスマートシェルフの簡易形） |
| **保管庫** | 蔵書から外すが捨てない場所（`.qooarchive`） | 変更なし |
| **未整理のファイル** | フォーマットに一致せず、タイトル・ラベルを自動で付けられなかったファイル。**左ペインから 1 クリック**で中央ペインに一覧され、通常のファイル操作＋救済アクションで片付ける（§19.6） | 旧「フォーマットに一致しないファイル」ウインドウを置き換え。「不一致」という否定形の枠付けをやめる［ユーザー指示］ |
| **メンテナンス** | ライブラリの片付けごとを 1 か所に集めたウインドウ（§19.6） | 整理ウインドウ 2 種＋重複の入口＋シリーズの提案を統合 |

### 用語の整理（フィールド名の意味）

StackNest の「ジャンル」は内容ジャンル（萌え・日常）を指すが、qooLibrary では同人イベント文化の呼称に揃える［ユーザー判断］:

| 概念 | qooLibrary での呼び方 |
|---|---|
| 本の種別（一般コミック／同人誌…） | **ライブラリタイプ**（フィールドにはしない。フォーマットがライブラリ単位である登録モデルの中核） |
| 二次創作の原作・オリジナル | フィールド**「ジャンル」**（値: 東方Project・オリジナル…）。予約語は `@genre`。設定画面の説明文で「二次創作の原作／オリジナルを指します」と補足 |
| 内容ジャンル（百合／SF…） | 既定フィールドには**置かない**。キーワードで代用し、必要ならユーザーがフィールドを追加 |

既定フィールド 5 種 = **著者・サークル・ジャンル・イベント・キーワード**（すべてライブラリごとに表示名変更可）。

## 19.3 導線モデル — 登録と解除以外はフルオート [P4]

### 登録（＝ライブラリ化、ウィザード形式）[RG3-20〜RG3-28、新設 ID]

登録は**ウィザード**で行う［ユーザー指示］。フルオート [P4] が適用されるのは**登録後の運用**（走査・追従・再解析）であり、登録そのものは「初めてでも仕組みを理解した上で迷わず終えられる」教育的な導線にする。**「ライブラリとして有効にする」という登録と別の操作は存在しない**（登録ウィザードの完了＝ライブラリ化）。

| # | 要件 |
|---|---|
| RG3-20 | ライブラリフォルダの「＋」は登録ウィザードを開く。ウィザードの完了と同時にライブラリとして機能し始める |
| RG3-21 | **ステップ 1「ライブラリフォルダとは」**: なるべくグラフィカルに（図解・SF Symbols・色分け）次を伝える——①実ファイルとフォルダはそのまま（読み取りだけ。移動も書き換えもしない。解除しても無傷）②ファイル名・フォルダ名から自動でメタデータを抽出してカタログ化する ③前提: 対象は zip/cbz/rar/cbr/7z/cb7/pdf/epub、ファイル名が情報源 ④ユーザーの自由: フォルダ構成は自由・命名規則はテンプレートから選べて調整できる・以後の追従は全自動 |
| RG3-22 | **ステップ 2「フォルダの選択」**: FS 適合検証 [RG-08]・入れ子禁止 [RG-03][RG-04] はここで検査し、理由付きで断る |
| RG3-23 | **ステップ 3「テンプレートの選択」**: **(A)/(B) の変種は 1 行に統合する**［ユーザー指摘。実差はフォルダ階層を使うかどうかだけで、それは RG3-24 の独立した選択にする］。実ファイル名をサンプリング（`previewSampleLimit` 件まで）して全テンプレートの適合率を計算し（`LibraryPreview` を流用）、**最も適合するものを推奨として選択済みにする**——判定はフォルダを使わない側で行う（使う側は `@title` 万能フォーマットを持ち種別を判別できない）。各行に適合件数・命名規則の例を添え、右側に実ファイルの分解プレビューを出す。全テンプレート 0 件一致でもそのまま進める（一致しない分は「未整理のファイル」に残る旨を表示） |
| RG3-24 | **ステップ 4「カスタマイズ」**: 並びは ①フィールド（追加・削除・改名・色）②**フォルダ名によるラベル分類**（分類しない／分類する の 2 択。サンプルのサブフォルダ比率から既定を推定し根拠も示す。「分類する」では階層割り当てエディタをその場に出す）③**ファイル名によるラベル分類**（フォーマット一覧と編集。高度な機能ではない）④**本を開くアプリ**（フォルダに実際に含まれる形式＋画像フォルダだけを並べ、形式ごとに既定アプリを選ぶ。選ばなかった形式はシステムの既定のまま）⑤高度な設定のカタログ（何が調整できるかの予告）と**「高度な設定をいま編集…」ボタン**（設定ウインドウと同じエディタを入れ子で開く）。セクションは区切り線で整理する［いずれもユーザー指示］ |
| RG3-25 | **ステップ 5「確認」**: カスタマイズの結果、**具体的にどうなるのかをグラフィカルにプレビューする**——実ファイル名のサンプルが登録後のライブラリでどう見えるか（タイトル・シリーズ・巻・フィールド値チップ付きの一覧モック）、フィールドごとに付く値の集計（著者 8 種・サークル 12 種…）、一致した件数と、一致せず「未整理のファイル」に残る件数。**納得できたら「登録」を押して初めて登録が成立する**（それまで DB には何も書かない）。納得できなければ前のステップへ戻って調整できる |
| RG3-26 | 登録 → 初回走査・ラベル自動付与を自動で開始し、ウィザードは閉じる。結果は通知で知らせる（例: 「「X」を 同人誌(A) として取り込みました。211 件中 209 件が一致」）。以後の追従（FSEvents・定期フルスキャン）も自動。「今すぐ再スキャン」はメニューに残す [SY-05] |
| RG3-27 | タイプ・設定の変更は設定ウインドウから行い、保存 → 確認 → 自動再スキャンで反映する（現行の settingsRevision 経路のまま） |
| RG3-28 | 初回セットアップウィザード [OB-01〜10、2-17] は、この登録ウィザードのステップ 1〜5 を部品として使う（同じ画面を 2 つ作らない） |

### 解除

| # | 要件 |
|---|---|
| RG3-30 | 解除は「登録解除」の 1 操作だけ。**「ライブラリ機能を無効にする」は廃止**（登録解除に一本化）。ラベル・評価が失われることの確認は現行どおり登録解除時に出す |
| RG3-33 | **フォルダツリー上のテンポラリフォルダ・ライブラリフォルダの並びは、ドラッグ＆ドロップで並べ替えられる**［ユーザー指示］。順序は登録の保存（`RegisteredFolderStore`）に永続化し、全ウインドウで共有する（ラベルグループの表示順 [LG-07][ST-23] と同じ扱い）。並べ替えはそれぞれのグループ（テンポラリ／ライブラリ）の中で閉じる |
| RG3-32 | **走査の進捗表示は止まって見えてはならない**［ユーザー指摘: 表示されるファイル名があまり更新されず、処理が止まっているように見えて不安になる］。現行の実装は 500 件のバッチ境界 [SE3-05] でしか名前を報告しないため、埋め込みメタデータの読み取り等で 1 バッチが長引くと表示が凍って見える。**報告はファイル単位で行い、表示側の間引き（10 回/秒・leading edge 付きの既存 `ProgressThrottle`）に任せる**。列挙・メタデータ読み取りなど時間のかかる局面でも、名前か件数のどちらかが動き続けること |
| RG3-31 | **ライブラリの表示名という概念は持たない。フォルダ名＝表示名**［ユーザー指示］。登録ウィザードに名前欄は無く、「表示名を変更…」もライブラリには出さない（名前を変えたければフォルダ自体をリネームする。テンポラリの表示名は現行のまま）。フォルダのリネームへの表示の追随は Stage 2 でエンジン側（解決時の同期）まで含めて行う。**同名のライブラリが複数できうる**ため、ライブラリを列挙する画面（設定・メンテナンス・シェルフ等）は必要に応じてパスを併記して区別する |

### 既存ユーザーの移行

- 登録済みで有効なライブラリ: そのまま動く（DB 行は既にある）。
- 登録済みだが未有効の登録: **起動時に登録と同一の自動経路で拾う**（コード経路を 2 つ作らない）。一度登録解除して再登録しても同じ結果になる［ユーザー明言: 解除→再登録の前提で構わない］。
- 「有効化は 1 件ずつ明示的に」という過去のユーザー判断（CLAUDE.md §0）は、**本章で明示的に反転された**。走査は読み取りのみで実ファイルに触れないため、推測したタイプで自動走査しても失うものは無い。

## 19.4 メタデータの保護 — 自動更新とロック [PR-01〜PR-09、新設 ID]

ラベルの扱いを簡素化する［ユーザー指示］。現行の origin 3 状態（auto／manual／manuallyRemoved）と titleOrigin による暗黙の保護をやめ、**「保護」という 1 つの見える概念**に置き換える。保護されていないものはすべて自動更新の対象。

| # | 要件 |
|---|---|
| PR-01 | 本のメタデータ（ラベル・タイトル・シリーズ・巻）は**既定で自動更新の対象**。走査は保護されていないスコープを毎回まるごと再導出してよい（手動追加の残存を個別には保証しない——PR-03 により編集は同時に保護されるため、実際には守られる） |
| PR-02 | 保護の単位は 2 つ: **ファイル全体**と**ファイル×スコープ**。スコープ = 基本情報（タイトル・シリーズ・巻を 1 つとして扱う）＋各フィールド。ファイル全体の保護 = 全スコープの保護 |
| PR-03 | **手動編集は該当スコープに自動で保護を付ける**（ラベルの付け外し → そのフィールドのスコープ、タイトル／シリーズ／巻の編集 → 基本情報スコープ）。保護の印（鍵アイコン）が表示される［ユーザー判断: 自動でロックが付く］ |
| PR-04 | **保護の解除 = 手動編集の破棄**。解除したスコープは次の走査（解除時に即時再導出してよい）で自動値へ戻る。解除時は確認を出す（旧 RC-06 はこれとして実現される） |
| PR-05 | 保護の付け外しはインスペクタとコンテキストメニューから行える。ファイル全体の保護はワンクリック。複数選択にも効く |
| PR-06 | 評価・ユーザー指定カバー・保管庫状態は元々自動上書きされないため保護の対象外（常に保たれる） |
| PR-07 | 呼称は**「保護」**とする（Finder のファイルロック [FM 系、`.isUserImmutableKey`] と「ロック」の語が衝突するため） |
| PR-08 | 移行: `fileLabel.origin` が manual／manuallyRemoved のフィールド → そのファイル×フィールドを保護に変換し、manuallyRemoved 行は削除。`titleOrigin = manual` → 基本情報スコープを保護に変換。以後 origin は ✨ 表示専用（auto／manual の 2 値）、manuallyRemoved と titleOrigin の保護機能は廃止 |
| PR-09 | 保護スコープは再生成不可能データとして JSON バックアップに含める [MG-22] |

**エンジンへの効果**: `replaceAutoLabels` の「manual／manuallyRemoved を守る」条件分岐 [RC-04] は「保護スコープに触れない」に置き換わり、単純化される。リネーム起点の再計算 [RC-10〜16] は**ダイアログなしで黙って行う**（未保護は再導出・保護済みは不変。結果は通知履歴に記録するだけ）——フルオート原則 [P4] の帰結。

## 19.5 シリーズのヒューリスティック検出（提案）[SS-01〜SS-08、新設 ID]

シリーズ名の抽出はユーザー定義のフォーマット（正規表現）に頼っており、**どうやっても漏れが出る**。特に同人誌では、当初シリーズ化予定のなかった作品が続編でシリーズ化され、1 冊目にだけナンバリングが無い・ナンバリング無しで固有のサブタイトルが付く、という形が頻出する。これを救済するヒューリスティックな解析を提供する［ユーザー指示］。**カスタマイズ項目は設けない** [P2]。

| # | 要件 |
|---|---|
| SS-01 | シリーズ名が設定されていない本を対象に、ヒューリスティックにシリーズ名を検出して**ユーザーに提案する**（勝手には設定しない） |
| SS-02 | 候補の条件: 同じライブラリ（＝同じライブラリタイプ）・**同一フォルダ内**・著者（またはサークル）が一致・タイトル先頭の共通接頭辞が既定長以上（定数は `AppLimits`、設定 UI は無し） |
| SS-03 | 接頭辞の境界をヒューリスティックに判定する: 不一致部分の先頭が数字である／共通部分の末尾が記号・空白文字である、等。提案するシリーズ名からは末尾の記号・空白を取り除く。照合は `TextNormalizer` の正規化（NFC・幅畳み込み）を通し、表示は元の綴りを使う |
| SS-04 | 2 冊以上が揃ったグループだけを提案する |
| SS-05 | 提案はメンテナンスの「シリーズの提案」タブに一覧され、**グループ単位で適用／無視**できる。無視は記憶され、同じ提案を繰り返さない（ファイル単位の除外印。名前が変われば解除——unresolvedFile.isIgnored [UR2-04] と同じ考え方） |
| SS-06 | 適用はメンバーの `seriesName` を設定し、**基本情報スコープを保護する** [PR-03 に準ずる]（次の走査に上書きされないため）。1 つの Undo 単位 [UD-04] |
| SS-07 | 巻数は、不一致部分が素の数字として読める場合にだけ併せて提案する。**番号の無い 1 冊目に 1 を推測して割り当てない**（提案一覧では「巻なし」と表示） |
| SS-08 | 検出は、シリーズ設定済み・基本情報を保護済み・保管庫内の本には触れない |

検出はエンジン（`QooKit` の純粋関数）に置き、ゴールデンテストの流儀（合成名の正例・負例）で固定する。**フォーマットによる解析の代替ではなく救済**——先にフォーマット解析が走り、その取りこぼしだけがこの対象になる。

## 19.5b シリーズスタック（ライブラリ表示モードのみ）[VM3-01〜VM3-06、新設 ID]

同一シリーズの複数の本を 1 つの仮想的な集合にまとめる（Kindle のコレクション機能のイメージ）［ユーザー指示］。**ライブラリ表示モードのみの機能**で、フォルダ表示モードには適用しない［ユーザー指定］。

| # | 要件 |
|---|---|
| VM3-01 | ライブラリ表示モードで、同一シリーズ（`seriesKey`）の本を 1 つのスタックにまとめて表示できる |
| VM3-02 | スタックは代表カバー（巻数順の先頭）＋シリーズ名＋冊数バッジで描く（重複の畳み表示 [DU-04〜06] と同じ視覚部品を流用） |
| VM3-03 | スタックを開くとそのシリーズの巻一覧になり、「戻る」で全体一覧へ復帰する（ライブラリ表示モード内のナビゲーション。既存の戻る／進む履歴に乗せる） |
| VM3-04 | 2 冊以上が揃ったシリーズだけをまとめる。シリーズ名の無い本・1 冊だけのシリーズは単体のまま並ぶ。並び順はシリーズ名と単体タイトルの混在ソート |

| VM3-06 | 検索・ラベルフィルタで絞り込んでいる間は、一致した本を直接（スタックに畳まずに）出す——絞り込みの結果がスタックの中に隠れないため |

シリーズの提案（§19.5）が適用されると、その本は自動的にスタックへ合流する。実装は重複グループ化と同じ SQL 窓関数のパターン（`PARTITION BY seriesKey`、索引 `mf_lib_series` は v1 から存在）。

## 19.11 ユーザー体験の要約（シチュエーション別）

> 本節は検収条件を兼ねる: **本当にシンプルなユーザー体験になっているなら、この要約自体が簡潔で分かりやすいはず**［ユーザー指示］。各ステージ完了時、この要約が実機の振る舞いと一致していることを確かめる。

| シチュエーション | ユーザーに見えるもの |
|---|---|
| **登録** | 「＋」でウィザードが開く: ライブラリとは何か（図解）→ フォルダを選ぶ → テンプレートを選ぶ（自分のファイル名での分解と適合率を見ながら。最適なものが推奨済み）→ カスタマイズ → **登録後の姿をプレビューで確かめて、納得したら「登録」**。取り込みが自動で始まり、「211 件中 209 件が一致」と通知。**以後は放っておいても実体に追随する** |
| **探す** | ライブラリを開き、ツールバーでライブラリ表示に切り替えると、**シリーズは 1 つのスタックにまとまって**カバー・冊数付きで並ぶ（開くと巻一覧）。⌘F でタイトル検索、左ペインでフィールドの値をクリックして絞り込み。よく使う絞り込みは「シェルフとして保存」→ 次からワンクリック |
| **新しいファイルを置く** | Finder でも qooLibrary でも、コピーすれば数秒で一覧に現れ、タイトル・シリーズ・ラベルが付いている。名前がフォーマットに合わなければタイトル＝ファイル名のまま並び、左ペインの「未整理のファイル」に入るだけ。**何も聞かれない** |
| **リネーム・移動** | 移動しても記録・ラベル・評価は付いてくる。リネームすると新しい名前で自動再解析される——ただし**保護（鍵印）を付けた本は変わらない**。ダイアログは出ない |
| **削除・差し替え** | 削除すると一覧から消え、記録はメンテナンスの「見つからないファイル」に残る（同名で戻せば復活）。同名ファイルで差し替えれば黙って引き継がれ、評価・ラベルは保たれる |
| **手で直す** | インスペクタで星・ラベル・タイトルを直すだけ。**触った部分に鍵印が付き、以後の自動更新から守られる**。鍵を外せば自動値に戻る |

## 19.12 ラベルの非表示 — 実体からの導出 [LA3-01〜LA3-05、新設 ID]

**「ラベルの保管庫」という概念は持たない**［ユーザー判断: ファイルの扱いに合わせ、単に非表示にして一覧から整理できるだけでよい］。「見つからないファイル」と同型——実体を失ったら一覧から消えるだけ、整理は一覧画面で、戻れば自動復帰。移動イベントも区画も持たない [P6]。

| # | 要件 |
|---|---|
| LA3-01 | **生きている実体（state = active かつファイル保管庫の外）に 1 件も紐づいていないラベルは、自動的に非表示になる**。これは状態ではなく導出であり、移動イベントを持たない。実体の復活・新規作成・同名の値を持つファイルの追加で、件数が 1 以上になった瞬間に自動的に表示へ戻る |
| LA3-02 | **手動の「非表示にする」印**は残す［ユーザー判断］——実体があるのにフィルタから消したいラベル（うるさい自動ラベル等）の唯一の手段（削除しても次の走査で復活するため）。手動で非表示にしたラベルは実体が何件あっても隠れたままで、自動復帰の対象にしない（現行 `isArchived` の再解釈。「保管庫」の語は使わない） |
| LA3-03 | 整理は**フィールド編集ウインドウの一覧**で行う——実体 0 件・手動非表示のラベルはそこでは控えめな表示（グレー等）で見えて、削除・非表示の切り替えができる。専用ウインドウ・区画は作らない（LAW-01〜03 は撤回） |
| LA3-04 | 0 件ラベルの赤字表示・削除促し [LE-04][RC-07] は**廃止**。「消してよさそう」と急かす表示は不要——放っておいても邪魔にならず、実体が戻れば生き返るのだから |
| LA3-05 | ラベルフィルタには非表示のラベル（実体 0 件・手動非表示とも）を出さない（前者は導出により自然に満たされる——生きている件数 0 のラベルは元々フィルタに出ない） |

なお「見つからないファイル」（実体を失った**記録**）には自動掃除を**適用しない**［ユーザー判断: 手動のまま］——記録にはそのファイル固有の評価・手動タイトルが載っており、勝手に消えてよいものではない。ラベルは LA3-01 が守るので、記録は静かに残り続け、消すのはユーザーの操作だけとする。

## 19.13 状態管理の簡素化（内部の複雑さの棚卸し）
