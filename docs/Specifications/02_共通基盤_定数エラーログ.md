## 2.2 エラー型

```swift
public protocol UserPresentableError: Error, Sendable {
    /// 何が起きたか（1 文） [ER-03]
    var whatHappened: String { get }
    /// なぜ起きたか [ER-03]
    var whyItHappened: String { get }
    /// 次に何ができるか（0..n 個の提案） [ER-03]
    var recoverySuggestions: [RecoveryAction] { get }
    /// 折りたたんで表示する技術詳細 [ER-03]
    var technicalDetail: String? { get }
    /// 提示強度 [13.1 節]
    var severity: NotificationSeverity { get }
}

public enum NotificationSeverity: Int, Sendable, Comparable {
    case logOnly = 5        // 強度 5: ログのみ [ER-01]
    case transient = 4      // 強度 4: 一時通知（ステータスバー／トースト）
    case inline = 3         // 強度 3: インライン
    case sheet = 2          // 強度 2: シート（判断が必要）
    case appModal = 1       // 強度 1: アプリモーダル（続行不可のみ） [ER-02]

public struct RecoveryAction: Sendable, Identifiable {
    public let id: String
    public let title: String
    public let kind: Kind
    public enum Kind: Sendable {
        case openWindow(WindowRoute)     // 例: 孤立ファイル整理へ [NT-05]
        case runCommand(ManualCommandID) // 例: 再スキャン [MX-xx]
        case openSystemSettings(String)
        case retry
        case dismiss
    }
}
```

## 2.3 通知の提示ルーティング [ER-01]

エラー／通知の提示方法を機能ごとに決めさせない。すべて `NotificationRouter` を通す。

```swift
@MainActor
public final class NotificationRouter {
    public func present(_ item: NotificationItem, in scene: SceneContext?) async -> RecoveryAction?
    /// 一括処理向け。判断が必要なものだけを都度尋ね、残りは集約する [ER-10]
    public func beginBatch(title: String) -> BatchNotificationSession
}

public struct NotificationItem: Sendable, Identifiable {
    public let id: UUID
    public let date: Date
    public let category: Category          // .error / .warning / .info [NT-03]
    public let severity: NotificationSeverity
    public let target: NotificationTarget? // ライブラリ / ファイル / 処理名 [NT-04]
    public let title: String
    public let body: String
    public let technicalDetail: String?
    public let actions: [RecoveryAction]
    public let operationLogID: UUID?       // 操作履歴へのリンク [NT-04]
}

public final class BatchNotificationSession {
    /// 判断が必要なものだけシートで尋ねる。"以降すべてに適用" を必ず持つ [ER-11][FM-12]
    public func ask(_ decision: PendingDecision) async -> DecisionOutcome
    /// 判断不要な失敗は記録のみ。処理は中断しない [ER-12][ER-13]
    public func record(failure: UserPresentableError, item: String)
    public func record(skip reason: String, item: String)
    public func record(success item: String)
    /// 完了後に "成功 N / 失敗 N / スキップ N" と理由別内訳を提示 [ER-14]
    public func finish() async -> BatchSummary
}

public struct BatchSummary: Sendable {
    public let succeeded: Int
    public let failed: [(item: String, error: any UserPresentableError)]
    public let skipped: [(item: String, reason: String)]
    public var failureBreakdown: [String: Int]      // 理由別件数 [ER-14]
    public var retryableItems: [String]             // [ER-15]
}
```

| # | 要件 |
|---|---|
| CB-10 | `present` は `severity` に応じて提示手段を自動選択する。呼び出し側が提示手段を指定できない API 設計とする [ER-01] |
| CB-11 | **すべての強度**を `NotificationHistoryStore` に記録し、**未読に数えるのは `severity >= .transient`（強度 4 以上）だけ**とする [ER-05][NT-01、2026-08 改訂] |
| CB-12 | 同種のエラーが連続する場合、`(category, code, target.libraryID)` をキーに 5 秒窓で集約し、件数付き 1 件として扱う [ER-22] |
| CB-13 | 部分成功はロールバックしない。`BatchSummary` を返して終わる [ER-16][MV-12][CW-35] |

## 2.4 通知履歴ストア [13.2 節]

**実装済み**（`NotificationHistoryStore`＝`QooKit`、`SQLiteNotificationHistoryStore`＝`QooPersistence`）。

```swift
public protocol NotificationHistoryStore: Sendable {
    @discardableResult
    func append(_ item: NotificationItem) async throws -> NotificationID
    func query(_ filter: NotificationHistoryFilter) async throws -> [StoredNotification]  // [NW-05]
    func unreadCount() async throws -> Int                       // [NT-02]
    func markRead(_ ids: [NotificationID]) async throws
    func markAllRead() async throws                              // [NW-03]
    func delete(_ ids: [NotificationID]) async throws
    func deleteAll() async throws
    func purgeExpired(retentionDays: Int, maxCount: Int) async throws  // [NT-07]
}
```

- 実体は `notificationRecord` テーブル（07 章 §7.3）。**新しい移行は不要**——列は v1 から揃っていた。
- ステータスバーのバッジは**この未読件数のみ**を表示する。孤立ファイル [OR-05]、ペンディング [PW-14]、再スキャン警告 [MX-10] の個別バッジは持たない [NT-06]。

### 実装で仕様から変えた点（2026-08）

| # | 仕様 | 実装 | 理由 |
|---|---|---|---|
| 1 | 記録は強度 4 以上 [CB-11][NT-01] | **全強度を記録し、未読だけ強度 4 以上** | 実測: `.sheet` が 70 箇所超に対し `.transient` は 3 箇所。旧定義では履歴が常に空になる［ユーザー承認済み、要件定義書 NT-01 も改訂］|
| 2 | `ids: [UUID]` | **`ids: [NotificationID]`（`Int64` の rowid）** | 永続化が SwiftData → GRDB へ移った際の決定（T-03 ②）に揃える。`notificationRecord` も `autoIncrementedPrimaryKey` なので UUID 列を別に持つ理由が無い |
| 3 | `exportCSV()` をストアが持つ | **`NotificationCSV.encode`（`QooKit` の純粋関数）** | 書き出すのは「いま一覧に出ているもの」であって DB 全件ではない [NW-07 の用途]。ストアに置くと絞り込み条件を渡し直すことになり、一覧と食い違う余地が生まれる |
| 4 | `query` は絞り込みを全部担う | **区分と期間は SQL、対象ライブラリとキーワードは Swift** | 対象は `targetJSON` の中にあり、SQL で引くには JSON1 拡張に頼ることになる。キーワードは `NameFilter`（**全角で打っても半角に当たる** [1-16 の実測]）を通す必要があり `LIKE` では表せない。SQL 側には `AppLimits.Notifications.queryLimit`（2,000＝既定の保持件数の 2 倍）を置いて読み出しを有界にしてある |

### まだ実装していないもの

- **CB-12（5 秒窓での集約）**。同種のエラーが連続する場合の `(category, code, target.libraryID)` による集約 [ER-22]。自動走査の繰り返しは `ScanFindingsDigest`（`QooApplication`）が別の形で抑えている（**前回**の観測と同じ内容なら記録しない）ので、当面の実害は無い。
- **`BatchNotificationSession`（ER-10〜16）**、**`SystemNotificationGate`（ER-30〜34）**［ユーザー判断で今回の範囲外、2026-08］。
- `NotificationItem.operationLogID`（操作履歴へのリンク [NT-04]）。列はあるが `operationLog` に書き手が無く、操作履歴は `CommandStack.operationHistory`（メモリのみ）に留まる——**リンク先の実体が無いものへの参照を先に作らない。**

| # | 要件 |
|---|---|
| CB-20 | 出力先 `Application Support/qooLibrary/Logs/`、1 ファイル 10MB、5 世代（`qoo-0.log` … `qoo-4.log`、0 が現行）[LG2-02][LG2-04] |
| CB-21 | 書き込みは専用 `actor` で直列化し、`OSLog` への出力と同時に行う。UI スレッドをブロックしない |

| CB-26 | 絶対パスを持たないユーザー由来の名前（解決できない登録フォルダの表示名、アーカイブ内のエントリ名など）は `Log.redactable(_:)` で `⟨名前⟩` の形に印を付け、匿名化の対象に含める [LG2-06] |
| CB-27 | 自由文（`error.localizedDescription`、`NotificationItem` の本文）は構造化できないため、匿名化時に**引用符・鉤括弧（`「」`『』“” ‘’）の中身**も置換する（安全網）。名前でない固定文言も伏せられるが、匿名化は共有時の opt-in 設定なので取りこぼすより安全側に倒す [設計判断、ユーザー判断] |
| CB-28 | 診断ログに書く操作の説明は、ユーザー向けの `Command.displayName` ではなく `Command.logDescription`（対象を**絶対パス**で表す）を使う [LG2-06] |
| CB-24 | ログのネットワーク送信機構を実装しない [LG2-08][SC-01] |
| CB-25 | 通知履歴と診断ログは別ストアとし、相互参照しない [NT-08][LG2-07] |

**「どこがパスか」はログ本文から推測しない** [CB-26、1-15 の実機確認で 2 度の取りこぼしを経て確立]。macOS のファイル名には **`/` と NUL 以外のあらゆる文字**が入る——空白も、括弧も、引用符も、矢印も、タブすら合法である。したがって「この文字が来たらパスの終わり」という区切り文字は原理的に存在しない。実際、推測方式では次の順で取りこぼした:

1. 空白で打ち切っていたため `/Volumes/<hash>/My Sample/作品名.cbz` と、途中までしか匿名化されなかった。
2. 区切りに括弧を加えたところ、`(成年コミック) [98765架空社] …` という**この分野ではもっとも普通の**ファイル名がまるごと素通しになった（括弧で走査が止まるため）。

どちらも取りこぼしより質が悪い（匿名化したつもりで漏れている）。そこで**パーサを賢くするのではなく、書く側が範囲を明示する**方式に改めた。`Log.path(_:)` がパスを `⟪…⟫` で囲み、匿名化はその範囲をそのまま信じて置換する。ファイル名に印そのものが含まれていても書き込み時に二重化してエスケープされるため曖昧さは残らない。印は書き出し時に取り除かれるので、読む人には見えない。

推測に頼るのは、**こちらが書式を決められないテキスト**（`Foundation` の `localizedDescription` が埋め込むパスなど）に限り、そこでは「余分に伏せる」側へ倒す。あわせて、**ログの書式側も曖昧さの無い形に揃える**: パスの直後に注釈を続けない（`展開開始（zip / 201 エントリ）: <パス> → <パス>` のように注釈を前へ置く）。

**CB-23 は 1-15 で対象を広げた** [設計判断]。当初は「ホームディレクトリ以下を `~/…/<sha256 先頭 8 桁>` に置換」だったが、サンドボックスアプリである qooLibrary が実際に扱うパスの大半はホーム外（外部ボリューム上のライブラリ／テンポラリフォルダ、`/Volumes/…`）であり、ホーム配下だけを対象にすると匿名化の目的をほとんど果たさない。また、パス全体を 1 つのトークンへ畳むと「同じフォルダにある別のファイル」「移動元と移動先が同じ親を持つ」といった関係が失われ、診断に使えないログになる。トークンは**その成分までのパス接頭辞**から導出するため、別の場所にある同名フォルダが同じトークンになって誤った関連付けを生むこともない。ハッシュにはインストールごとに一度だけ生成するソルトを混ぜる（書き出したバンドルには含めない。`/Users/<よくある名前>` のような推測しやすいパスの逆引きを防ぐ）。
