対応要件: SY-01〜SY-12 / VD-01〜VD-11 / ID-01〜ID-08 / SB-05 / FS-08 / T-01 / T-02

## 10.0 表示中のフォルダの追随（フェーズ 1）

> **10.1 以降との関係.** 10.1 の `FSEventsWatcher` は「登録フォルダを DB と
> 突き合わせて収束させる」ためのもの（フェーズ 2、2-2）。本節は
> **「今画面に映っているものを実体に合わせる」**ためだけの、DB に依存しない
> 別の関心事で、フェーズ 1 で実装した。置き換え関係にはなく、2-2 は
> `FileSystemEventStream` を土台として再利用できる。

ファイルマネージャーとして、表示している内容が実体と食い違ったままなのは
致命的である。1-16 まではアプリ自身の操作を全ウインドウへ一斉に知らせるだけで、
Finder や他アプリがアプリの外で加えた変更には一切追随できなかった。

### 構成

| 型 | 役割 |
|---|---|
| `FileSystemEventStream` | FSEvents の薄いラッパ。ルート集合を受け取り、変更をそのまま流す |
| `DirectoryChangeHub` | 「誰がどのフォルダに関心を持っているか」を持ち、変更を振り分ける中枢 |
| `DirectoryObservation` | 1 つの表示が 1 つのフォルダを見張る取っ手。`generation` が増える |

### 3 つの入口を 1 つの出口へ束ねる

| 入口 | 何を拾うか | 遅延 |
|---|---|---|
| FSEvents | ローカルボリュームで**他プロセス**が加えた変更 | `AppLimits.Watch.coalescingLatency`（0.25 秒）|
| `DirectoryChangeHub.noteLocalChanges(at:)` | **自プロセス**が加えた変更。FSEvents は `IgnoreSelf` で自分の変更を落とすため明示的に伝える | 即時 |
| ディレクトリ更新日時のポーリング | ネットワークボリューム上の変更。FSEvents は他のマシンが加えた変更を報告しない | `AppLimits.Watch.remotePollInterval`（2 秒、前面時のみ）|
| `NSApplication.didBecomeActive` | 上記いずれでも取りこぼした変更 [MX-10 と同じ考え方] | アプリが前面に戻ったとき |

出口はどれも `DirectoryObservation.generation` の加算で、購読側から見れば区別が
無い。**差分を適用するのではなく「読み直せ」とだけ伝える**［設計判断］ —
10.3 の「実ファイルの状態と突き合わせて収束させる」[FO-20][SY-12] と同じ考え方で、
同じ変更を 2 回伝えても結果が変わらない。

| # | 要件 |
|---|---|
| DW-01 | 自分が加えた変更は **`FileOperationService` の 1 箇所**から通知する [FO-01]。FS を変更する経路はすべてそこを通ることが静的検査 [FO-02][B-10] で強制されているため、通知の書き忘れが構造的に起こらない |
| DW-02 | 関心は「直下だけ（`.shallow`）」と「配下すべて（`.deep`）」の 2 種類。一覧・ツリーの行は前者、再帰検索は後者 |
| DW-03 | FSEvents に渡すルートは関心の集合から**祖先に含まれるものを剪定**して作る。辞書順で直前の要素だけを見る実装にしてはならない（`/a`・`/a b`・`/a/b` の順に並ぶため）|
| DW-04 | ルート集合の差し替えは `FSEventStreamGetLatestEventId` を `sinceWhen` に渡して行い、停止から再開までの空白を埋める [SY-02][SY-03 と同じ機構] |
| DW-05 | 照合するパスは、画面が扱う表記と**物理パス**（`realpath(3)`）の両方を索引に載せる。FSEvents は実体のパスを返すため |
| DW-06 | 高価な再計算（再帰検索・再帰集計）は、走っている間に届いた変更を溜め、終わってから 1 回だけやり直す。打ち切って始め直すことを繰り返すと結果がいつまでも出ない |
| DW-07 | 表示していないフォルダは見張らない（たたんだツリーの行を含む）|

### 実測に基づく設計判断

サンドボックス下の最小アプリ（実アプリと同一 entitlement）で計測した。

| 検証項目 | 実測結果 |
|---|---|
| App Sandbox 下で動くか | 動く。追加 entitlement 不要 |
| 読み取り権限の無いパスのイベント | **届く**（`contentsOfDirectory` が拒否される外部ボリュームでも全件到達）|
| `/` を監視したときの量 | 待機時 約 2 件/秒。外部プロセスが 4,000 ファイルを作る最悪ケースで約 4,000 件/10 秒 |
| `IgnoreSelf` | 自プロセスの変更は抑止され、別プロセスの変更は届く |
| 存在しないパスを含めた生成 | **成功する**。パスが出現した時点で `RootChanged` から配送が始まる |
| 監視中のフォルダ自身の削除・改名 | `RootChanged` が届く。パスが復活するとストリームは自動的に再武装する |
| アンマウントの阻害 | しない（ファイル記述子を保持しないため）— 1-16 のイジェクトに影響しない |
| ボリューム着脱 | `/Volumes` を監視すると `Mount`/`Unmount` フラグが届く [WA-07][VD-07] |

**`kqueue`/`DispatchSource` を採らなかった理由**: ディレクトリごとにファイル
記述子を開くことになり、そのボリュームのアンマウントが `EBUSY` で失敗する。

### 既知の限界

- ネットワークボリュームは、ディレクトリ自身の更新日時が変わる変更（項目の
  増減・改名）しか検知しない。子ファイルの中身だけが変わった場合は、アプリが
  前面に戻ったときの再同期に委ねる。**実機での検証は未了**（検証に使える
  ネットワークボリュームが無いため）。
- インスペクタの再帰集計 [DT-05][DT-06] は直下の変更でのみ更新する。孫以下の
  変更は選び直したときとアプリが前面に戻ったときに反映される。

## 10.2 ボリューム着脱検知 [8.6.1 節]

> **フェーズ 1（1-17）との関係.** 登録フォルダの縮退状態（オフライン／ゴミ箱／消失の区別）と
> その判定順序は、DB 導入前に確定させるため 8.7.1 節でフェーズ 1 に前倒ししてある。
> ただし 1-17 は着脱**検知**を持たず、ツリー更新時にマウント一覧と突き合わせる受動的な判定に留める。
> 2-2 の役割は、その遷移を下記の `VolumeMonitor`（VD-01〜VD-06）で駆動するよう差し替えることであり、
> **状態モデルと判定順序そのものは変えない**。特に、未マウントと判定した時点で
> ブックマークの解決を試みない規則（RG3-01、`.withoutMounting`）は 2-2 でも維持する
> ——解決がマウントを誘発するため、ネットワークボリューム切断時に UI をブロックし得る。

```swift
public actor VolumeMonitor {
    public var events: AsyncStream<VolumeEvent> { get }
    public func start() async
    /// 起動時のボリューム列挙。起動前の着脱はこの経路でのみ検出できる [VD-08]
    public func reconcileWithMountedVolumes() async
    /// 手動コマンド「ボリュームを再検証」 [VD-09]
    public func revalidateAll() async
}

public enum VolumeEvent: Sendable {
    case mounted(volumeUUID: String, url: URL)
    case willUnmount(volumeUUID: String)
    case didUnmount(volumeUUID: String)
    case renamed(volumeUUID: String, oldURL: URL, newURL: URL)
}
```

### 検知手段の優先順位

| 順 | 手段 | 役割 |
|---|---|---|
| 1 | `NSWorkspace.shared.notificationCenter` の `didMount` / `willUnmount` / `didUnmount` / `didRenameVolume` | 主たる検知手段 [VD-01] |
| 2 | `FileManager.mountedVolumeURLs` の起動時列挙 | 起動前の着脱 [VD-08] |
| 3 | FSEvents の Mount / Unmount フラグ | 取りこぼしへの備え [VD-07] |
| 4 | DiskArbitration | 補助。サンドボックス下の可否は T-09 で検証 |

```pseudo
onMounted(uuid, url):
    for folder in registeredFolders where folder.volumeUUID == uuid:
        folder.isOnline = true                                 # [VD-03]
        resolved = bookmarks.resolve(folder.bookmarkData)      # 再解決 [VD-03]
        folder.resolvedPath = resolved.url.path
        startWatching(resolved.url, since: folder.lastFSEventID)
        enqueueIncrementalScan(folder)                         # [SY-03][VD-03]
    recordHistory(.volumeOnline)                               # [VD-10]

onWillUnmount(uuid):
    for folder in registeredFolders where folder.volumeUUID == uuid:
        cancelRunningOperations(folder, safely: true)          # [VD-04][RB-04]
        folder.lastFSEventID = await stopWatching(folder)      # [VD-04]
        stopAccessingSecurityScopedResource(folder)            # アンマウントを妨げない

onDidUnmount(uuid):
    for folder in … : folder.isOnline = false                  # [VD-05]
    # 孤立判定を停止する [SB-05][ID-08]

onRenamed(uuid, old, new):
    for folder in … : folder.resolvedPath = new.path           # [VD-06]
    # volumeUUID は不変なので紐づけは維持される
```

| # | 要件 |
|---|---|
| VM3-01 | ボリューム識別にはマウントパスではなく `volumeUUIDString` を使う [VD-02] |
| VM3-02 | `willUnmount` ではアンマウントを妨げない。処理の中断とストリーム停止を素早く行う [VD-04] |
| VM3-03 | 状態遷移（オンライン／オフライン／再接続）を操作履歴に記録する [VD-10] |
| VM3-04 | オフラインのライブラリを操作しようとしたら「ボリュームが接続されていません」と明示し、接続後に自動復帰する旨を案内する [VD-11] |
| VM3-05 | 起動時に `mountedVolumeURLs` と DB のオンライン状態を突き合わせる [VD-08] |
| VM3-06 | 再フォーマット等でサポート外になった場合、警告のうえ読み取り専用（ラベル更新停止）にする。オフライン扱いとは区別する [FS-08] |

## 10.3 スキャンエンジン [FO-20][SY-12]

**差分イベントに反応するのではなく、実ファイルの状態と DB を突き合わせて収束させる。** 同じイベントを 2 回処理しても結果が変わらないこと。

```swift
@ModelActor
public actor ScanEngine {
    public enum Mode: Sendable {
        case incremental(paths: [String])   // FSEvents 差分 [SY-03]
        case full(libraryID: UUID)          // [SY-05][AT-02]
        case folder(libraryID: UUID, relativePath: String, recursive: Bool)  // [SY-06]
    }

    public func scan(_ mode: Mode, progress: ProgressReporter?) async throws -> ScanSummary
}

public struct ScanSummary: Sendable {
    public var added: Int
    public var updated: Int
    public var reidentified: Int      // ID-04
    public var orphaned: Int          // ID-06
    public var candidatesForReview: Int  // ID-05
    public var unresolvedNames: Int   // AL-31
    public var bookFoldersDetected: Int
}
```

```pseudo
scan(mode):
    library = …
    if !library.isOnline: return .skipped              # [SB-05][ID-08] 孤立判定を一切行わない
    if library.isReadOnlyDueToFS: 読み取りのみ          # [FS-08]

    # ① 実ファイルの列挙
    enumerator = FileManager.enumerator(
        at: root,
        includingPropertiesForKeys: [.fileResourceIdentifierKey, .fileSizeKey,
                                     .contentModificationDateKey, .creationDateKey,
                                     .isDirectoryKey, .isSymbolicLinkKey, .isAliasFileKey],
        options: [.skipsPackageDescendants])            # [PF-13]
    # シンボリックリンク・エイリアスは除外 [SL-03]
    # .qooarchive 配下も列挙対象に含める [SY-10]

    seen: Set<PersistentIdentifier> = []
    for url in enumerator:
        if isSymlinkOrAlias(url): continue              # [SL-03]
        if isDirectory(url):
            if BookFolderDetector.isBookFolder(url, …): # [IF-01]
                pid = reconcile(url, asBookFolder: true)
                seen.insert(pid); enumerator.skipDescendants()
            continue
        if url.pathExtension not in library.targetExtensions: continue
        pid = reconcile(url, asBookFolder: false)
        seen.insert(pid)

    # ② DB 側の突き合わせ（full / folder スコープのときのみ）
    if mode is .full or .folder:
        for record in dbRecords(inScope) where record.id not in seen:
            if record.state == .trashed: continue        # 期限まで保持 [TR-01]
            record.state = .orphaned                     # 即削除しない [ID-06]

    # ③ ラベル再計算（自動ラベルのみ）は ApplyAutoLabelsUseCase へ委譲
```

| # | 要件 |
|---|---|
| SE3-01 | 列挙は `includingPropertiesForKeys` でまとめて属性を取得し、個別 `stat` を避ける [PF-13] |
| SE3-02 | 1 万ファイルのフルスキャンを 60 秒以内。バックグラウンド実行で操作をブロックしない [PF-05][LK-01] |
| SE3-03 | 進捗はステータスバーに表示、キャンセル可能 [SY-09] |
| SE3-04 | 一覧は逐次埋まる。空の一覧を見続ける状態を作らない [ST-15] |
| SE3-05 | 保存は 500 件または 1 秒のバッチ境界で行い、トランザクション境界と一致させる [ST-10][ST-13] |
| SE3-06 | スキャンは非排他処理。実行中もユーザー操作を許す [LK-01][LK-02] |
| SE3-07 | フルスキャンは既定 7 日間隔で起動時にバックグラウンド実行。環境設定で無効化可 [SY-05] |
| SE3-08 | 手動再スキャン（差分／フル）をライブラリ単位・フォルダ単位で提供 [SY-06][MX-01] |

## 10.4 同一性判定 [6.3 節]

```swift
public enum IdentityResolver {
    public enum Resolution: Sendable {
        case matchedByIdentity(PersistentIdentifier)                 // [ID-02]
        case matchedByPathAndSize(PersistentIdentifier)              // [ID-03]①
        case matchedByNameAndSize(PersistentIdentifier)              // [ID-03]②
        case candidateByNameOnly([PersistentIdentifier])             // [ID-03]③ → [ID-05]
        case new
    }
    public static func resolve(_ fs: FileSnapshot,
                               repo: ManagedFileRepository) async throws -> Resolution
}
```

```pseudo
reconcile(url, library):
    fs = FileSnapshot(identity: (volumeUUID, inode), relativePath, filename, size, dates)

    switch await IdentityResolver.resolve(fs):
      case .matchedByIdentity(pid):
          # パス・ファイル名の変化を追従更新 [ID-02]
          update(pid, path: fs.relativePath, name: fs.filename, size: fs.fileSize)
          if pathOrNameChanged: markForLabelRecalculation(pid)     # [RC-01]
          if record.state == .trashed and 元の場所に戻った: record.state = .active  # [TR-04]
          return pid

      case .matchedByPathAndSize(pid), .matchedByNameAndSize(pid):
          # inode を更新して既存レコードとみなす（ラベル維持）[ID-04]
          update(pid, inode: fs.identity.inode, volumeUUID: fs.identity.volumeUUID)
          if record.state in [.orphaned, .trashed]: record.state = .active   # [TR-05]
          return pid

      case .candidateByNameOnly(candidates):
          # 自動では紐づけず、孤立ファイル一覧に「候補あり」として提示 [ID-05]
          createNewRecord(fs)
          registerReidentificationCandidates(newRecord, candidates)
          return newPid

      case .new:
          return createNewRecord(fs)
```

| # | 要件 |
|---|---|
| ID3-01 | 主キーは `(volumeUUID, inode)`。代替キーは用意しない [ID-01][T-08] |
| ID3-02 | 再照合の優先順は ① 同一相対パス + 同一サイズ、② 同一ファイル名 + 同一サイズ、③ 同一ファイル名のみ [ID-03] |
| ID3-03 | ③のみの一致は自動紐づけしない [ID-05] |
| ID3-04 | いずれにも一致しない DB レコードは即削除せず `.orphaned` へ。ラベル紐づけは保持 [ID-06] |
| ID3-05 | 「孤立ファイルの整理」画面で一覧・手動再紐づけ・一括削除を提供 [ID-07] |
| ID3-06 | **オフライン時は孤立判定を一切行わない** [ID-08][SB-05][R-01] |
| ID3-07 | 別ボリュームへの移動（テンポラリ → ライブラリ）では inode が変わる。移動元・移動先の対応を記録して引き継ぐ [FS-09][MV-10] |

## 10.5 イベント処理のパイプライン

```
FSChangeBatch
   │ ①台帳照合（自己変更を除外）[FO-12]
   │ ②パスをライブラリ／テンポラリへ振り分け
   │ ③.qooarchive / covers / 隠しファイルの扱いを決定
   │ ④テンポラリ → 自動リネーム判定 [AR2-02]（suppressAutoRename でなければ）
   │ ⑤ライブラリ → 差分スキャン [SY-01]
   │ ⑥ラベル再計算（自動のみ）[RC-01]
   └─→ バッチ保存 + UI 反映 [ST-10]
```

```pseudo
handle(batch):
    for change in batch.changes:
        if let entry = await ledger.consume(vol, change.inode, change.path, kind):
            if entry.suppressAutoRename: markSuppressed(change.path)   # [CR-63][PW-15]
            continue                                                   # [FO-12] スキップ
        externalChanges.append(change)

    if batch.needsFullScan: enqueueFullScan(folder)                    # [SY-04]
    else: enqueueIncrementalScan(folder, paths: externalChanges.paths)
    folder.lastFSEventID = batch.lastEventID
```

| # | 要件 |
|---|---|
| EV-01 | 台帳に一致したイベントは処理をスキップする [FO-12] |
| EV-02 | 排他処理中はイベントを保留し、完了後に差分照合を 1 回だけ実行する [LK-31][FO-14] |
| EV-03 | 処理は冪等。2 回処理しても結果が変わらない [FO-20][SY-12] |
| EV-04 | 自動処理が長時間実行されていない、または取りこぼしが疑われる場合、通知履歴に警告を記録し手動コマンドへの導線を示す [MX-10] |

### 取りこぼし検出のヒューリスティック [MX-10]
