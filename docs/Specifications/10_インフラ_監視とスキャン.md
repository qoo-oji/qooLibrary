## 10.0 表示中のフォルダの追随（フェーズ 1）

> **10.1 以降との関係.** 10.1 の `FSEventsWatcher` は「登録フォルダを DB と
> 突き合わせて収束させる」ためのもの（フェーズ 2、2-2）。本節は
> **「今画面に映っているものを実体に合わせる」**ためだけの、DB に依存しない
> 別の関心事で、フェーズ 1 で実装した。置き換え関係にはなく、2-2 は
> `FileSystemEventStream` を土台として再利用できる。

ファイルマネージャーとして、表示している内容が実体と食い違ったままなのは
致命的である。1-16 まではアプリ自身の操作を全ウインドウへ一斉に知らせるだけで、
Finder や他アプリがアプリの外で加えた変更には一切追随できなかった。

### 構成

| 型 | 役割 |
|---|---|
| `FileSystemEventStream` | FSEvents の薄いラッパ。ルート集合を受け取り、変更をそのまま流す |
| `DirectoryChangeHub` | 「誰がどのフォルダに関心を持っているか」を持ち、変更を振り分ける中枢 |
| `DirectoryObservation` | 1 つの表示が 1 つのフォルダを見張る取っ手。`generation` が増える |

### 3 つの入口を 1 つの出口へ束ねる

| 入口 | 何を拾うか | 遅延 |
|---|---|---|
| FSEvents | **この Mac のカーネルを通った**他プロセスの変更（ネットワークボリューム上でも届く。8章 §8.11.5 で実測）| `AppLimits.Watch.coalescingLatency`（0.25 秒）|
| `DirectoryChangeHub.noteLocalChanges(at:)` | **自プロセス**が加えた変更。FSEvents は `IgnoreSelf` で自分の変更を落とすため明示的に伝える | 即時 |
| ディレクトリ更新日時のポーリング | **別マシン**が加えた変更。FSEvents はこの Mac のカーネルを通らない変更を報告しない | `AppLimits.Watch.remotePollInterval`（2 秒、前面時のみ）|
| `NSApplication.didBecomeActive` | 上記いずれでも取りこぼした変更 [MX-10 と同じ考え方] | アプリが前面に戻ったとき |

出口はどれも `DirectoryObservation.generation` の加算で、購読側から見れば区別が
無い。**差分を適用するのではなく「読み直せ」とだけ伝える**［設計判断］ —
10.3 の「実ファイルの状態と突き合わせて収束させる」[FO-20][SY-12] と同じ考え方で、
同じ変更を 2 回伝えても結果が変わらない。

| # | 要件 |
|---|---|
| DW-01 | 自分が加えた変更は **`FileOperationService` の 1 箇所**から通知する [FO-01]。FS を変更する経路はすべてそこを通ることが静的検査 [FO-02][B-10] で強制されているため、通知の書き忘れが構造的に起こらない |
| DW-02 | 関心は「直下だけ（`.shallow`）」と「配下すべて（`.deep`）」の 2 種類。一覧・ツリーの行は前者、再帰検索は後者 |
| DW-03 | FSEvents に渡すルートは関心の集合から**祖先に含まれるものを剪定**して作る。辞書順で直前の要素だけを見る実装にしてはならない（`/a`・`/a b`・`/a/b` の順に並ぶため）|
| DW-04 | ルート集合の差し替えは `FSEventStreamGetLatestEventId` を `sinceWhen` に渡して行い、停止から再開までの空白を埋める [SY-02][SY-03 と同じ機構] |
| DW-05 | 照合するパスは、画面が扱う表記と**物理パス**（`realpath(3)`）の両方を索引に載せる。FSEvents は実体のパスを返すため |
| DW-06 | 高価な再計算（再帰検索・再帰集計）は、走っている間に届いた変更を溜め、終わってから 1 回だけやり直す。打ち切って始め直すことを繰り返すと結果がいつまでも出ない |
| DW-07 | 表示していないフォルダは見張らない（たたんだツリーの行を含む）|

### 実測に基づく設計判断

サンドボックス下の最小アプリ（実アプリと同一 entitlement）で計測した。

| 検証項目 | 実測結果 |
|---|---|
| App Sandbox 下で動くか | 動く。追加 entitlement 不要 |
| 読み取り権限の無いパスのイベント | **届く**（`contentsOfDirectory` が拒否される外部ボリュームでも全件到達）|
| `/` を監視したときの量 | 待機時 約 2 件/秒。外部プロセスが 4,000 ファイルを作る最悪ケースで約 4,000 件/10 秒 |
| `IgnoreSelf` | 自プロセスの変更は抑止され、別プロセスの変更は届く |
| 存在しないパスを含めた生成 | **成功する**。パスが出現した時点で `RootChanged` から配送が始まる |
| 監視中のフォルダ自身の削除・改名 | `RootChanged` が届く。パスが復活するとストリームは自動的に再武装する |
| アンマウントの阻害 | しない（ファイル記述子を保持しないため）— 1-16 のイジェクトに影響しない |
| ボリューム着脱 | `/Volumes` を監視すると `Mount`/`Unmount` フラグが届く [WA-07][VD-07] |

**`kqueue`/`DispatchSource` を採らなかった理由**: ディレクトリごとにファイル
記述子を開くことになり、そのボリュームのアンマウントが `EBUSY` で失敗する。

### 既知の限界

- **[訂正・実測済み]** かつてここには「FSEvents はネットワークボリュームで機能しない」
  「ポーリング経路が実際に働くか未確認」と書いていたが、**どちらも 1-16b で実測し、
  前者は不正確、後者は妥当と確定した**（8章 §8.11.5）。

  | 変更の出どころ | FSEvents | dir mtime ポーリング |
  |---|---|---|
  | **同じ Mac の別プロセス**（Finder 等）| **届く**（SMB 上でも実測）| 届く |
  | **別マシン**（真のリモート）| **届かない** | **1 秒以内に見える**（実測）|

  正しい理解は「ネットワークだから届かない」ではなく「**この Mac のカーネルを
  通らない変更は FSEvents に現れない**」である。ローカル VFS 由来かどうかの問題で、
  プロトコルとは無関係。**したがって本節の「FSEvents ＋ ポーリング」の併用は、
  両輪とも必要性が実測で裏付けられた。**

- ディレクトリ自身の更新日時が変わらない変更（子ファイルの中身だけの書き換え）は
  検知しない。アプリが前面に戻ったときの再同期に委ねる。
- **[依存・要注意]** `nsmb.conf` の既定は `dir_cache_min=30s` / `dir_cache_max=60s` で
  ディレクトリ情報が最大 60 秒キャッシュされる。それでも Apple の SMB サーバでは
  1 秒で見えた——SMB2 変更通知がキャッシュを無効化しているためと考えられる。
  **変更通知を実装しないサーバでは最大 60 秒遅れ得る**（未実測）。
- インスペクタの再帰集計 [DT-05][DT-06] は直下の変更でのみ更新する。孫以下の
  変更は選び直したときとアプリが前面に戻ったときに反映される。

## 10.1 FSEvents 監視 [8.6 節]

### 10.1.0 実測 — 履歴の再生は「使えるかどうか」を確かめてからでないと嘘になる [T-02][SY-03][SY-04]

**2-2 の着手時に実測して確定させた。** SDK の `FSEvents.h` は、保存した
`sinceWhen` について次のように定めている（原文の要旨）:

> 保存したイベント ID は、**`FSEventsCopyUUIDForDevice()` が返す UUID と
> セットで**保存し、UUID が一致するときにだけ渡してよい。UUID が変われば
> 履歴は別物である（消去・purge・カウンタの巻き戻り）。**NULL が返る場合は
> 履歴が利用できないので、`kFSEventStreamEventIdSinceNow` 以外を渡しては
> ならない。**

この機の実ボリュームで測った結果 [実測]:

| ボリューム | FSEvents デバイス UUID | 履歴の再生 | `HistoryDone` | 開始後の変更 |
|---|---|---|---|---|
| 起動ボリューム（`/private/tmp`）| `4867A295-…` | **6/6 件** | true | 届く |
| 使い捨てディスクイメージ（APFS）| `C6FAB5BD-…` | **6/6 件** | true | 届く |
| **ネットワーク（SMB、実 NAS）** | **NULL** | **0 件** | **true** | 届く |
| Time Machine 用ボリューム | NULL（`.fseventsd` が無い）| 未測定 | — | — |

**この表から出る結論は 2 つあり、どちらも設計を決める。**

1. **ネットワークボリューム上のライブラリでは履歴が 1 件も再生されない。**
   アプリを閉じている間の変更が**黙って全部失われる**。1-16b が扱った
   ネットワーク上のライブラリは実運用でありうる形なので、これは例外ケース
   ではない。
2. **`HistoryDone` は 0 件でも届く。**したがって失敗の検出には使えない。
   **`FSEventsCopyUUIDForDevice` が NULL を返すかどうかが唯一の検出手段**で
   ある——エラーもフラグも出ず、ただ何も来ないという最悪の壊れ方をする。

> **`FSEventsCopyUUIDForDevice` は存在するパスに対して呼ぶこと。** 存在しない
> パスへの `stat` は失敗するので、その戻り値を「NULL＝履歴なし」と読むと
> **測定そのものが嘘になる**（この実測で一度やった。両ボリュームとも
> 「UUID は NULL なのに履歴は再生される」というヘッダの記述と矛盾する結果に
> なり、それが手がかりで気づいた）。

| # | 要件 | 実装 |
|---|---|---|
| WA-10 | 保存する差分の起点は `(eventID, デバイス UUID)` の**組**とする [SY-02] | `FSEventsCheckpoint` |
| WA-11 | 起動時、ライブラリごとに現在のデバイス UUID を引き、**保存した UUID と一致するときだけ**履歴を要求する | `FSEventsHistory.deviceUUID(for:)` |
| WA-12 | 一致しない・NULL・未保存のライブラリは、履歴を要求せず**フルスキャンへ落とす** [SY-04] | `LibrarySyncCoordinator` |
| WA-13 | `kFSEventStreamCreateFlagFullHistory`（10.15+）を指定する。異常終了の直前に起きた変更を取りこぼさないため、`sinceWhen` を含むチャンクを丸ごと再生させる。スキャンは冪等なので余分な再生は無害 [FO-20] | `FileSystemEventStream` |

## 10.2 ボリューム着脱検知 [8.6.1 節]

> **フェーズ 1（1-17）との関係.** 登録フォルダの縮退状態（オフライン／ゴミ箱／消失の区別）と
> その判定順序は、DB 導入前に確定させるため 8.7.1 節でフェーズ 1 に前倒ししてある。
> ただし 1-17 は着脱**検知**を持たず、ツリー更新時にマウント一覧と突き合わせる受動的な判定に留める。
> 2-2 の役割は、その遷移を下記の `VolumeMonitor`（VD-01〜VD-06）で駆動するよう差し替えることであり、
> **状態モデルと判定順序そのものは変えない**。特に、未マウントと判定した時点で
> ブックマークの解決を試みない規則（RG3-01、`.withoutMounting`）は 2-2 でも維持する
> ——解決がマウントを誘発するため、ネットワークボリューム切断時に UI をブロックし得る。

```swift
public actor VolumeMonitor {
    public var events: AsyncStream<VolumeEvent> { get }
    public func start() async
    /// 起動時のボリューム列挙。起動前の着脱はこの経路でのみ検出できる [VD-08]
    public func reconcileWithMountedVolumes() async
    /// 手動コマンド「ボリュームを再検証」 [VD-09]
    public func revalidateAll() async
}

public enum VolumeEvent: Sendable {
    case mounted(volumeUUID: String, url: URL)
    case willUnmount(volumeUUID: String)
    case didUnmount(volumeUUID: String)
    case renamed(volumeUUID: String, oldURL: URL, newURL: URL)
}
```

### 10.2.0 実測 — 着脱通知はどの経路で届くか [T-09][NV-43]

**仕様書は NV-43（`NSWorkspace` のボリューム通知がネットワークを対象外にするか）
を「2-2 着手時に確かめること」として残していた。実測で決着した。**

実アプリと同一の entitlement でアドホック署名した `.app`（`sandbox=true` を
自己申告させて確認）で、`NSWorkspace` の 4 通知と Darwin 通知
（`kNotifyVFSMount` / `kNotifyVFSUnmount`、`notify_keys.h`）を同時に購読し、
使い捨てディスクイメージと**実 NAS（SMB）**を着脱して測った [実測]:

| 事象 | Darwin 通知 | `NSWorkspace` |
|---|---|---|
| ローカル マウント | ○（8 ms 早い）| ○ |
| ローカル **willUnmount** | **×（対応する通知が無い）** | **○** |
| ローカル アンマウント | ○ | ○ |
| ローカル **改名** | **×** | **○（old / new の両方が付く）** |
| **SMB マウント** | ○ | **○** |
| **SMB willUnmount** | × | **○** |
| **SMB アンマウント** | ○ | **○** |

**結論: `NSWorkspace` はネットワークボリュームでも届く。** NV-43 の懸念
（「`NSWorkspace` はネットワークボリュームを通知の対象から外す」という
二次情報が複数ある）は、この macOS では当てはまらなかった。

**したがって Darwin 通知は採らない**［設計判断］。8 ms 早いだけで固有の情報が
無く、`willUnmount` [VD-04] と改名 [VD-06] はむしろ `NSWorkspace` にしかない。
経路を増やせばそのぶん壊れ方も増える。

- **サンドボックス下で `notify_register_dispatch` 自体は成功する**ことも
  確認した。将来 `NSWorkspace` の取りこぼしが実際に見つかったときは、
  `kNotifyVFSMount` ＋ `MountTable` の差分が**測定済みの代替手段**として使える。
- **未検証**: サーバが突然落ちた場合（クリーンなアンマウントではない形）に
  通知が届くか。`Scripts/network-disconnect-probe.sh` と同じ pf 遮断（要 sudo）
  が要る。**この経路の安全網は `reconcileWithMountedVolumes()`**（`MountTable`
  ベース、切断時も 0 ms）で、起動時・スリープ復帰時・手動の「ボリュームを
  再検証」[VD-09] から回す。

### 検知手段の優先順位

| 順 | 手段 | 役割 |
|---|---|---|
| 1 | `NSWorkspace.shared.notificationCenter` の `didMount` / `willUnmount` / `didUnmount` / `didRenameVolume` | 主たる検知手段 [VD-01] |
| 2 | `FileManager.mountedVolumeURLs` の起動時列挙 | 起動前の着脱 [VD-08] |
| 3 | FSEvents の Mount / Unmount フラグ | 取りこぼしへの備え [VD-07] |
| 4 | DiskArbitration | 補助。サンドボックス下の可否は T-09 で検証 |

```pseudo
onMounted(uuid, url):
    for folder in registeredFolders where folder.volumeUUID == uuid:
        folder.isOnline = true                                 # [VD-03]
        resolved = bookmarks.resolve(folder.bookmarkData)      # 再解決 [VD-03]
        folder.resolvedPath = resolved.url.path
        startWatching(resolved.url, since: folder.lastFSEventID)
        enqueueIncrementalScan(folder)                         # [SY-03][VD-03]
    recordHistory(.volumeOnline)                               # [VD-10]

onWillUnmount(uuid):
    for folder in registeredFolders where folder.volumeUUID == uuid:
        cancelRunningOperations(folder, safely: true)          # [VD-04][RB-04]
        folder.lastFSEventID = await stopWatching(folder)      # [VD-04]
        stopAccessingSecurityScopedResource(folder)            # アンマウントを妨げない

onDidUnmount(uuid):
    for folder in … : folder.isOnline = false                  # [VD-05]
    # 孤立判定を停止する [SB-05][ID-08]

onRenamed(uuid, old, new):
    for folder in … : folder.resolvedPath = new.path           # [VD-06]
    # volumeUUID は不変なので紐づけは維持される
```

| # | 要件 |
|---|---|
| VM3-01 | ボリューム識別にはマウントパスではなく `volumeUUIDString` を使う [VD-02] |
| VM3-02 | `willUnmount` ではアンマウントを妨げない。処理の中断とストリーム停止を素早く行う [VD-04] |
| VM3-03 | 状態遷移（オンライン／オフライン／再接続）を操作履歴に記録する [VD-10] |
| VM3-04 | オフラインのライブラリを操作しようとしたら「ボリュームが接続されていません」と明示し、接続後に自動復帰する旨を案内する [VD-11] |
| VM3-05 | 起動時に `mountedVolumeURLs` と DB のオンライン状態を突き合わせる [VD-08] |
| VM3-06 | 再フォーマット等でサポート外になった場合、警告のうえ読み取り専用（ラベル更新停止）にする。オフライン扱いとは区別する [FS-08] |

## 10.3 スキャンエンジン [FO-20][SY-12]

**差分イベントに反応するのではなく、実ファイルの状態と DB を突き合わせて収束させる。** 同じイベントを 2 回処理しても結果が変わらないこと。

```swift
public actor ScanEngine {
    public enum Mode: Sendable {
        case incremental(paths: [String])   // FSEvents 差分 [SY-03]
        case full(libraryID: UUID)          // [SY-05][AT-02]
        case folder(libraryID: UUID, relativePath: String, recursive: Bool)  // [SY-06]
    }

    public func scan(_ mode: Mode, progress: ProgressReporter?) async throws -> ScanSummary
}

public struct ScanSummary: Sendable {
    public var added: Int
    public var updated: Int
    public var reidentified: Int      // ID-04
    public var orphaned: Int          // ID-06
    public var candidatesForReview: Int  // ID-05
    public var unresolvedNames: Int   // AL-31
    public var bookFoldersDetected: Int
    public var volumeConflicts: Int   // EM-26（巻数の判断待ち）
}
```

### 走査の砦 — 根の同一性を確かめる [R-01][SB-05][ID-08]

**`isOnline` だけに頼ってはならない**［2026-08、アプリ結線時に追加］。

疑似コードの `if !library.isOnline: return .skipped` が「唯一の砦」だが、
**その値を更新する経路（VD-01〜06）が入るまでは常に真で素通りする**。しかも
根の解決は保存済みのパス文字列から `URL` を組み立てるだけで、実体の有無も
ボリュームの同一性も見ていない。実際に事故を防いでいたのは「列挙が
`contentsOfDirectory` で throw すること」——偶然に頼った安全だった。

最も危ないのは**同じマウントポイントに別のボリュームが載る**場合である。
macOS は `/Volumes/<名前>` を使い回すので、外付けを抜いて別のディスクを挿すと
パスは同じまま中身だけが別物になる。**列挙は成功し、観測されなかった＝
ライブラリ全件が孤立**になる——外部ボリュームを抜き差ししただけでラベル
紐づけを一括で失う、まさに R-01 が禁じている事故そのもの。

```pseudo
    # ①の前に根を確かめる
    if !exists(rootURL) or !isDirectory(rootURL): return .skipped
    current = VolumeIdentity.identifier(for: rootURL)
    if current != nil and current != library.volumeUUID: return .skipped
```

|---|---|

| SE3-13 | `VolumeMonitor` で `isOnline` が駆動されるようになっても**この検査は外さない**。両者は独立した砦である |

### 埋め込みメタデータの読み取り [EM-07][EM-09]

### 10.4.0 生きている行を横取りしない [ID3-08]（2026-08 追加）

**同じファイル名は複数のフォルダにふつうに存在する**（`第01巻.cbz` など。
本仕様書自身が「複数シリーズに存在しうる名前」として挙げている）。
引き継ぎは常に自動 [ID-05] なので、**「その行がまだ生きているファイルを
担っていないか」という歯止め**が無いと、片方を触っただけでもう片方の
記録が消える。**ステージ 1（§19.10）で確認ダイアログが撤去されて以降、
この歯止めが唯一の防壁である。**

#### 何が起きていたか（実測で再現）

| 経路 | 操作 | 結果 |
|---|---|---|
| ① `reconcile` | `新/名前.cbz` を消して**旧側と同じ大きさで**作り直す | `旧` の行が横取りされ、`旧` は新しい行に作り直された |
| ② 走査末尾の後始末 | `新/名前.cbz` を**消すだけ**（旧側には触れない）| `旧` の行が孤立側に吸収されて**消えた** |
| ③ `reconcile` | `旧/名前.cbz` を `新/` へ**移動**し、`旧/` に別の新しいファイルを作る | 移動先で inode により正しく引けている行を、元の場所の新しいファイルがパスの一致で奪う |

②では利用者が触れてすらいないファイルの評価（★4）が失われ、走査は
`added=0 / orphaned=0` と報告した——**画面からは何も起きていないように見える。**

原因は 2 つとも同じ思い違いで、**確度の並び**がそれを踏ませる:
`.nameAndSize`（同名・同サイズ・別の場所）は `.pathOnly`（同じ場所・サイズ違い）
より**上**なので、同名ファイルを作り直しただけで別フォルダの生きている行が
先頭に来る。

#### 歯止め（`ScanEngine.unclaimedCandidates`）

`reconcile` は 2 つを候補から外す:

1. 記録上の場所に**いま別のファイルが居る**行——まだ現役なので触らない。
2. **この走査で inode により引けた行**——名前やパスの一致はより弱い証拠
   なので、強い証拠で確定した行を奪ってはならない（③がこれに当たる）。

差し替え（同じ場所に別の実体）と移動（元の場所は空）はどちらも通る。

> **［2026-08 ステージ 1 での変更 §19.8］** かつてはこの歯止めに加えて
> 「走査が疑った組を `identityPending`（v7）へ記録し、一括の確認ダイアログ
> [ID-09] で問い合わせる」という第二の機構があった。確認そのものの撤回
> [ID-09〜ID-15 撤回] に伴い、`identityPending`／`identityRejection` は
> v8 で DROP し、機構ごと消した。歯止め 1・2 は残る——確認が無くなった今、
> これが唯一の防壁なので**外してはならない**（`IdentityRowTheftTests` が
> 3 経路とも固定している）。

#### 実機で確かめたこと（2026-08）

使い捨てボリュームに**同じファイル名を 2 つの別フォルダ**へ置いて確認した。
①同じ大きさで作り直す ②片方を消すだけ ③移動しつつ元の場所に別ファイルを作る
——**3 通りとも、触れていない側の評価・ラベル・行 ID が保たれた。**
（当時はあわせて確認ダイアログ [ID-09] と設定 [ID-14] も検証したが、
どちらもステージ 1 で撤回済み。）

### 10.4.1 引き継ぎは常に自動（確度は並べ替えにだけ使う）

**［2026-08 ステージ 1 で改訂 §19.8］** かつてここには
`IdentityMatchPolicy`（3 段階設定）と確度の 3 × 4 対応表があったが、
設定ごと撤回した [ID-13〜ID-15 撤回]。現在の仕様:

- `ReidentificationCandidate.Confidence`（4 段。①`pathAndSize`
  ②`nameAndSize` ③a `pathOnly` ③b `nameOnly`）は**候補の並べ替え**
  （最も確からしい 1 件を選ぶ）にだけ使い、どの確度でも自動で引き継ぐ。
- 引き継ぎは `reconcile` の中（チャンクごと）だけで完結する。
  **新しい行を作らない**ので、「作る → 孤立にする → 併合する」往復も
  起きない（回帰テストは `added == 0` でこれを見張っている）。
- 危険な取り違えの防壁は §10.4.0 のガードのみ。誤って引き継いだ場合は
  右ペインで直せる。

## 10.6 調整役 — 3 つの部品を結ぶ [2-2 の結線]

`LibraryWatcher`（FSEvents）・`VolumeMonitor`（着脱）・`ScanEngine`（収束）は
**互いを知らない**。どれをどう繋ぐかという方針だけを `LibrarySyncCoordinator`
（`QooApplication`）に置く。`QooPersistence` と `QooInfrastructure` の両方に
依存してよい唯一の層だから [A-01][A-02]。

```
VolumeMonitor ──着脱──┐
                      ├─→ LibrarySyncCoordinator ──→ ScanEngine ──→ DB
LibraryWatcher ─変更──┘         │
   ↑ FSEvents                   └─→ isOnline / resolvedPath / 差分の起点
   ↑ FileOperationService（自プロセスの変更 [FO-01]）
```

### 突き合わせ（`resync`）

起動時・着脱時・ライブラリの増減時・スリープ復帰時に走る。**冪等**で、何度
呼んでも同じ状態へ収束する（`ScanEngine` と同じ考え方 [FO-20]）。

| 順 | すること | 要件 |
|---|---|---|
| ① | `watchStates()` で DB 側の状態を読む | — |
| ② | `LibraryRootLocating` で根の所在を得る。**1-17 の縮退状態をそのまま借りる**（判定を作り直さない）| RG3-01〜08 |
| ③ | オンライン／オフラインの遷移を DB へ書く | VD-03 / VD-05 |
| ④ | 根が動いていれば `resolvedPath` を書き直す | VD-06 |
| ⑤ | 差分の起点を**その場で検証**して監視対象を組み直す | WA-11 / WA-12 |
| ⑥ | 起動時のみ、走らせるべき走査を予約する | SY-03 / SY-04 / SY-05 |

**ゴミ箱の中・実体消失・ファイルシステム非対応も「走査しない」に畳む**が、
理由は保つ——「接続すれば戻る」と「実体が見つからない」は案内が違う [VD-11]。

### 起動時に何を走らせるか

| 状況 | 走らせるもの | 要件 |
|---|---|---|
| 差分の起点が検証できる | **何もしない**。非起動中の変更は FSEvents の履歴再生が `ScanRequest` として運ぶ | SY-03 |
| 起点が検証できない（**ネットワークは常にここ**）| フルスキャン | SY-04 |
| 前回のフルスキャンから間隔を超えた | フルスキャン | SY-05 |

### 差分でも「列挙が到達しない場所」は見ない [実機検証で発見]

`LibraryEnumerator` は隠し項目と `covers` を飛ばすが、**差分の走査単位は
その場所を起点に直接列挙する**ので、飛ばす規則が効かない。実機で
`/Volumes/<ライブラリ>/` の隠しフォルダに置いたファイルが蔵書として DB に
載った——**フルスキャンなら決して現れない行**なので、次のフルスキャンで
孤立になり、差分で戻り、を繰り返す。

走査単位を決める段（`ScanUnitPlanner`）で同じ規則を適用する。
**列挙の規則を 2 か所に持たない**——片方だけ直すと、差分とフルで DB の
中身が食い違う。

なお、**走査対象外の変更しか届かなかった場合はフルスキャンへ落とさない。**
「絞れない」と「見るべき場所が無い」は別の意味で、後者で全体を列挙し直すのは
明らかに過剰。

### 「今から」の番兵を起点として保存しない [実機検証で発見]

`FSEventStreamGetLatestEventId` は、**ストリームが 1 件もイベントを処理して
いないと `kFSEventStreamEventIdSinceNow`（`UInt64.max`）を返す。** それを
起点として保存すると、次回は「使える起点」と判定されたうえで「今から」を
意味する値が `sinceWhen` に渡り、**非起動中の変更が黙って落ちる**——
§10.1.0 が塞ごうとしている穴そのものになる。実機では
`lastFSEventID = -1`（`Int64` として見た `UInt64.max`）という形で現れた。

`0`（未保存）と同じく明示的に弾く。**通る場所すべてで確かめる**
（`FSEventsCheckpoint.isUsable` / `LibraryWatcher.latestEventID` /
保存の直前）——番兵を実在の値と同じ型で持つ以上、型では防げない。

### 走査の待ち行列

**1 本ずつ流す。** 同じライブラリの重なりは `ScanEngine` が弾くので待つだけ
無駄で、別のライブラリでも走査は I/O を独占するため同時に走らせると全部が
遅くなる（特にネットワーク）。同じライブラリへの要求は畳んで 1 回にまとめる。

### 差分の起点を進めてよいのはいつか [SY-02]

**起点の意味は「この ID までは DB へ反映済み」であって「この ID まで受け取った」
ではない。** 受け取っただけで進めると、走査せずに終了したときにその変更が
黙って失われる（次のフルスキャン [SY-05] まで最長 7 日）。

| 場面 | 進めてよいか |
|---|---|
| 走査が成功した | ○（走査を**始める前**に控えた ID を保存する。走っている間の変更は次回に再生されるほうが、取りこぼすより安い）|
| 終了時・アンマウント時で、待ち行列も実行中も空 | ○ |
| **待ち行列に残っている／走査の最中** | **×** |
| 走査が取り消された・見送られた | × |

### 状態の変化は上位へ知らせる（DB を直すだけでは届かない）[VD-03][VD-05]

調整役は 2 つのコールバックを持つ。**どちらも「DB を書き換えた」ことを上位へ
伝えるためのもの**で、無いと画面が古い状態を見続ける。

| コールバック | いつ | なぜ要るか |
|---|---|---|
| `onScanFinished` | 自動走査が終わったとき | 自動走査は `ScanEngine` を直に呼ぶので `LibraryServices.scan(libraryID:)` を通らない。拾わないと**外部でファイルが増えてもライブラリ表示モードの一覧が古いまま**になる（2-9） |
| `onOnlineStateChanged` | `isOnline` が切り替わったとき | `LibraryServices.libraries` は**問い合わせた時点の写し**なので、DB を直しても上位に届かない。**「見つからないファイル」の整理ウインドウが取り出しに追随せず、見えないボリュームの記録を削除できてしまった**（2-14 の実機検証で発見、15章 §15.7） |

**変化があったときだけ呼ぶ。** 突き合わせ（`resync`）は定期的に走るので、
毎回知らせると `libraries` の読み直し（DB への往復）がそのぶん増える。

> **教訓: キャッシュを挟む設計では、書き手が知らせるところまでが 1 組。**
> `LibraryServices.libraries` を見ている画面はすべて着脱後に古い `isOnline` を
> 見ていたが、ラベル保管庫はオフラインでも動いてよいので実害が無く、
> **オフラインを禁じる画面（§15.7）を作って初めて表面化した。**

### 自動走査ではダイアログを出さない — ただし判断が要るものは別［設計判断］

利用者が Finder で自分で消したファイルに対して「N 件が見つからなくなりました」
と出るのは純粋な雑音で、**本当に見てほしい 1 枚まで読み飛ばされるようになる**
[ER-11 の精神]。要約は診断ログに残り、どのファイルかは整理ウインドウ
[OR-01〜05、2-14] で見る。手動の再スキャンは従来どおり結果を提示する。

> **［2026-08 の例外］差し替えの確認 [ID-05] だけは自動走査でも知らせる**
> ［ユーザー判断］。孤立・未解決の件数は「知らせるだけ」なので黙ってよいが、
> **差し替えの確認は放置すると記録（ラベル・評価・編集したタイトル）が失われた
> ままになる**ので性質が違う。しかも FSEvents の自動追随が先に拾ってしまうため、
> **この経路が無いと通知が実質出ない**——手動で再スキャンしても `.nameOnly` の
> 経路を通らない（既に新しい行が同一性で引ける）。受け口は
> `LibraryServices.onAutomaticScanFinished`、判定は
> `LibraryEnableAction.notifyAutomaticScan`（`candidatesForReview > 0` のときだけ）。

### 取りこぼし検出のヒューリスティック [MX-10]

```pseudo
detectStaleness():
    for library in libraries where isOnline:
        if now - library.lastEventReceivedAt > 24h and 実ファイル数 != DB 件数:
            notify(.warning, "変更の検知が働いていない可能性があります",
                   actions: [.runCommand(.rescanFull(library))])
```
