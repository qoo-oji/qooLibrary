# 04. ドメイン層 — ファイル名フォーマットパーサ

対応要件: FF-01〜FF-19 / WS-01〜WS-07 / TY-01〜TY-06 / PT-01〜PT-11 / DL-01〜DL-16 / RW-01〜RW-17 / MT-12 / T-05 / T-10

本アプリの中核。**正規表現の連結では実装しない** [FF-12]。字句解析 → 構文木 → バックトラッキング照合の 3 段構成とする。

---

## 4.1 全体パイプライン

```
フォーマット文字列
   │ ①Lexer          → [FormatToken]
   │ ②Parser         → FormatAST（ネスト構造を保持）
   │ ③Validator      → FormatCompileError / CompiledFormat
   └─→ CompiledFormat（キャッシュ対象）

ファイル名（拡張子除去済み）
   │ ④ProtectedTokenMasker  → MaskedInput（保護文字列を PUA へ退避）
   │ ⑤Matcher（両端アンカー + バックトラッキング + メモ化）
   │ ⑥Unmasker              → 保護文字列を復元
   └─→ ParseResult?
```

```swift
public struct DelimiterSet: Sendable, Hashable, Codable {
```

## 4.3 字句解析（Lexer）

```swift
enum FormatToken: Sendable, Equatable {
    case reservedWord(FieldRef, sourceRange: Range<String.Index>)
    case pairOpen(PairDelimiter)
    case pairClose(PairDelimiter)
    case separator(SeparatorDelimiter)
    case whitespace                      // 弾力的空白 [WS-01]
    case literal(String)                 // 上記以外の連続文字列
}
```

```pseudo
lex(format, delimiters):
    i = format.startIndex
    while i < end:
        if format[i] == '@':
            word = 最長一致する予約語（@labelgroup + 1桁以上の数字 も含む） [MT-12]
            if word == nil: error(.unknownReservedWord)
            emit .reservedWord
        else if format[i] は有効なペア型の open:
            emit .pairOpen
        else if format[i] は有効なペア型の close:
            emit .pairClose
        else if 位置 i から有効なセパレータ型 variant に前方一致:
            emit .separator（最長一致）
        else if isWhitespace(format[i]):
            連続する空白をまとめて emit .whitespace 1 個
        else:
            リテラル文字を蓄積 → 次のトークン境界で emit .literal
```

| # | 要件 |
|---|---|
| LX-01 | 予約語は最長一致で読む。`@labelgroup12` は `@labelgroup1` + `2` ではなく `@labelgroup12` として読む [MT-12] |
| LX-02 | `@labelgroup#` の `#` は 1 桁固定にしない。任意桁の 10 進数を受け付け、範囲チェックは Validator で行う [MT-12] |
| LX-03 | `@ignore` は出現順に連番を振り `FieldRef.ignore(n)` とする [RW-03] |
| LX-04 | 連続する空白は 1 つの `.whitespace` に畳む。保存時にも半角 1 個へ正規化 [WS-03] |

## 4.4 構文木（AST）

```swift
public indirect enum FormatNode: Sendable, Equatable {
    case literal(String)
    case whitespace                                     // 0 個以上の空白 [WS-01]
    case separator(SeparatorDelimiter)
    case field(FieldRef, kind: FieldKind)
    case group(PairDelimiter, children: [FormatNode])   // ネスト可 [FF-11]
}

public enum FieldKind: Sendable, Equatable {
    case free           // @title / @series / @labelgroup# / @ignore / @author [9.2.2]
    case volume         // @volume: 数字または巻数フォーマット [TY-01]
    case enumerated([String])  // @booktype の照合語彙 [TY-01]
}

public struct CompiledFormat: Sendable, Identifiable {
    public let id: UUID
    public let source: String            // 正規化済みフォーマット文字列 [WS-03]
    public let nodes: [FormatNode]
    public let isEnabled: Bool           // [FF-05]
    public let priority: Int             // [FF-03][FF-04]
    public let usedFields: Set<FieldRef>
    /// 出現順に並べたフィールド。CW-16 のフィールド分解表示に使う。
    public let fieldOrder: [FieldRef]
}
```

`FieldKind` は**コンパイル時にライブラリ設定から決定する**。`@volume` の照合には巻数フォーマット集合が必要なため、`CompiledFormat` は `LibrarySettingsSnapshot` の revision に紐づく [TY-06]。

## 4.5 検証（Validator）[FF-15〜FF-19][TY-05]

```swift
public enum FormatCompileError: UserPresentableError, Equatable {
    case unbalancedDelimiter(at: Int)                  // 括弧の不一致
    case duplicateTitle                                // @title の重複
    case duplicateLabelGroup(index: Int)               // [FF-16]
    case labelGroupOutOfRange(index: Int, max: Int)    // [LG-01][MT-11]
    case semanticConflict(keyword: SemanticKeyword, labelGroup: Int) // [RW-15]
    case adjacentFreeFields(first: FieldRef, second: FieldRef)       // [FF-18][TY-05]
    case unknownReservedWord(String)
    case emptyFormat
    case noFieldAtAll                                  // 照合しても何も抽出できない
}
```

```pseudo
validate(nodes, settings):
    # ① 括弧の対応は Parser 段階で検出済み
    # ② フィールドの重複
    seen = {}
    for f in flatten(nodes).fields:
        if f == .title and seen.contains(.title): error(.duplicateTitle)
        if f == .labelGroup(n):
            if seen.contains(.labelGroup(n)): error(.duplicateLabelGroup(n))   # [FF-16]
            if n < 1 or n > AppLimits.maxLabelGroups: error(.labelGroupOutOfRange)
        # @ignore は重複チェック対象外 [RW-03]
        if f != .ignore(_): seen.insert(f)

    # ③ セマンティック予約語と @labelgroup# の衝突 [RW-15]
    for (kw, groupID) in settings.semanticBindings:
        if nodes に kw と、その groupID を指す .labelGroup(n) の両方が存在:
            error(.semanticConflict)

    # ④ 自由文字列フィールドの隣接 [FF-18][TY-05]
    #    flatten して「区切りにならないノード」を挟まずに free 同士が並ぶ場合を検出。
    #    group の境界（open/close）は区切りとみなす。whitespace は区切りとみなさない
    #    （elastic のため境界を決められない）。
    seq = flattenWithBoundaries(nodes)
    for i in 0..<seq.count-1:
        if seq[i].isFreeField and nextSignificant(seq, i).isFreeField:
            error(.adjacentFreeFields)

    # ⑤ @title 省略の許容 [FF-19][RW-09]
    #    @series または @volume が直接書かれていれば @title は不要
```

| # | 要件 |
|---|---|
| VD-01 | 検証エラーは**保存を拒否**する [FF-15]。編集画面では該当位置に下線とメッセージを表示する [HP-04] |
| VD-02 | `whitespace` は境界にならない。`@title @labelgroup1` は `.adjacentFreeFields` として拒否する [設計判断: elastic 空白では境界が決まらないため。TY-05 の趣旨に一致] |
| VD-03 | `.enumerated` フィールドと `.volume` フィールドは境界になりうる（型条件で終端が決まる）ため、自由文字列と隣接してよい [TY-02] |
| VD-04 | FF-16 の制限はフォーマット文字列の内部に限る。**異なるフォルダ階層に同じラベルグループを割り当てることは許容する** [FF-17] |

## 4.6 保護文字列 [9.2.3]

**記法は正規表現**（2026-08 の仕様変更）。

> **[要件の撤回、2026-08]** 要件 `PT-11` と本節の `PTI-04` は
> 「**完全一致のみ。前方一致・正規表現は提供しない**」と定めていた。
> ユーザー要望によりこれを撤回する——リテラルでは `(1999)`〜`(2024)` のような
> 「括弧の中の年号」を 1 本で書けず、20 件以上を登録するしかなかった。
> 要件定義書側も同時に改訂している。

```swift
public struct ProtectedToken: Sendable, Hashable, Codable, Identifiable {
    public let id: UUID
    public var pattern: String                    // 正規表現。`\((19[0-9]{2})\)` など
    public var position: Position                 // [PT-05]
    public enum Position: String, Sendable, Codable { case anywhere, prefix, suffix }
    public var isEnabled: Bool
}

public struct CompiledProtectedToken: Sendable {
    public let id: UUID
    public let pattern: String
    public let position: ProtectedToken.Position
    let regex: SafeRegex                          // 時間の上限つき（05章 §5.6）
    let health: RegexPatternHealth
}
```

照合は巻数フォーマットと**同じ射影**（`FoldedSubject`＝全角を半角へ畳み NFC へ
合成したもの）に対して行う。**大文字小文字は正規表現の option で無視する**——
被検査文字列を小文字化するのではなく option にするので、ユーザーが書いた `[A-Z]`
が壊れない [PT-04 の趣旨を保つ]。

```pseudo
mask(input, tokens):
    subject = FoldedSubject(input)

    # 1. 各パターンの一致を**全部集める**。位置ごとに全パターンを試すより桁で速い。
    candidates = []
    for t in tokens:
        if t.health.isAbandoned(t.id): continue
        (matches, abandoned) = t.regex.allMatches(subject, budget)
        if abandoned: t.health.markAbandoned(t.id); continue
        for m in matches:
            if t.position == .prefix and m.lowerBound != 0: continue
            if t.position == .suffix and m.upperBound != input.count: continue
            candidates.append((m, t の登録順))

    # 2. 左端優先 → 長い方 → 登録順 で、重ならないように選ぶ [PT-06]
    candidates.sortBy(lowerBound asc, length desc, order asc)
    selected = greedyNonOverlapping(candidates)

    # 3. 選んだ範囲を PUA 1 文字へ
    …
```

| # | 要件 |
|---|---|
| PTI-01 | マスクは**パース前**に行う。マスク後の PUA 文字は区切り文字にもフィールド境界にもならないため、自由文字列フィールドに自然に吸収される [PT-02] |
| PTI-02 | 復元はフィールド値の確定後に行う。`FieldValue.text` / `spans` の両方を復元する [PT-03] |
| PTI-03 | 巻数フォーマットとの競合では保護文字列が優先される。マスク済みの範囲は巻数照合の対象にならないため、この優先順位は自動的に成立する [PT-07] |
| PTI-04 | **正規表現で書く**（`PT-11` の撤回。上の注記を参照）。旧いリテラル指定は `LegacyVolumeNotation.regex(fromProtectedLiteral:)` が変換する——**空白の連なりは `\s+` にする**ので、旧実装の弾力的な空白照合 [PT-04][WS-01] の性質が保たれる |
| PTI-05 | PUA 使用領域は U+E000〜U+E0FF（256 個）。保護文字列の出現がこれを超える入力は、超過分をマスクせずログに警告を出す [設計判断] |
| PTI-06 | 保護文字列はライブラリ設定とテンポラリ設定の両方に持ち、相互コピーできる [PT-08]。テンプレートにも含める [PT-09] |
| PTI-07 | **長さ 0 の一致は無視する。** `x*` のようなパターンが至る所で空に一致し、PUA を食い潰すのを防ぐ [設計判断] |
| PTI-08 | 既定で `\((19[0-9]{2})\)` / `\((20[0-9]{2})\)` / `\((結\|終\|完\|完結\|完全版)\)` の 3 本が入る（`AppDefaults.Library.protectedTokenPatterns`）［2026-08 のユーザー要望］。**実蔵書 2,346 件で結果が 1 件も変わらないことを実測してから採用した** |

## 4.7 マッチャ [TY-03][TY-04][FF-13]

### 4.7.1 アルゴリズム概要

**メモ化付きのバックトラッキング。**

> **[実装との差異、2026-08]** 当初この節は「前方アンカー → 後方アンカー → 中央の
> バックトラッキング」の 3 段構成としていた。実装では**段を分けていない**。
> 検証器が「自由文字列フィールドの隣は必ず境界」を保証している [FF-18][VD-02] ため、
> 素直な再帰でも自由文字列の走査は「次の境界を探す」だけになり、探索量は
> O(ノード数 × 入力長) に収まる、という読みによる。
>
> **実測（T-05、`Spikes/README.md`）で裏付けた**: プリセット由来の 50 フォーマット
> （万能フォールバックの `@title` を除く）× 実ファイル名 1 万件で
> **1 件あたり 0.078 ms**（目標 1 ms [MT2-01]）。全 50 本を試して全滅する
> ケースを 8.5% 含む。病的な入力（括弧を多数含む 99 文字）でも 0.121 ms。
>
> 段を分けるのは最適化であって正しさの要件ではないため、**測ってから足す**方針を
> 採った。将来フォーマットの表現力を広げて自由文字列が境界なしに並べられるように
> なった場合は、この前提が崩れるので測り直すこと。

以下は当初案の擬似コード（3 段構成）。実装は Phase C 相当のみを持つ。

```pseudo
match(nodes, input) -> ParseResult?:
    # Phase A: 前方アンカー
    #   nodes の先頭から「決定的ノード」（literal / whitespace / separator /
    #   volume field / enumerated field / group）を消費し、入力の開始位置を確定する。
    #   free field に到達したら停止。
    (frontIdx, inputStart) = consumeDeterministicPrefix(nodes, input, 0, 0)
    if 失敗: return nil

    # Phase B: 後方アンカー
    #   nodes の末尾から同様に逆方向へ消費し、入力の終了位置を確定する。
    (backIdx, inputEnd) = consumeDeterministicSuffix(nodes, input, nodes.count, input.count)
    if 失敗: return nil
    if frontIdx > backIdx: return nil

    # Phase C: 中央部
    #   nodes[frontIdx..<backIdx] を input[inputStart..<inputEnd] に割り当てる。
    #   free field は非貪欲（最短優先）、決定的ノードは位置を探索する。
    bindings = matchMiddle(nodes[frontIdx..<backIdx], input[inputStart..<inputEnd])
    if bindings == nil: return nil
    return assemble(bindings)
```

### 4.7.2 中央部のバックトラッキング

```pseudo
# memo: Set<(nodeIndex, inputIndex)> — 失敗した組を記録し再探索を避ける [T-05 対策]
matchMiddle(nodes, input, ni, ii, memo, out) -> Bool:
    if ni == nodes.count:
        return ii == input.count
    if memo.contains((ni, ii)): return false

    node = nodes[ni]
    switch node:
      case .literal(s):
        if input[ii...] hasPrefix s (幅正規化後で比較):
            return matchMiddle(nodes, input, ni+1, ii+len(s), memo, out)
        break
      case .whitespace:
        # 0 個以上。貪欲に取ったのち減らしながら試す [WS-01]
        for k in maxWhitespaceRun(input, ii) downTo 0:
            if matchMiddle(nodes, input, ni+1, ii+k, memo, out): return true
        break
      case .separator(sep):
        # elastic空白 + variant + elastic空白 [DL-14]
        for (consumed) in separatorMatches(input, ii, sep):
            if matchMiddle(nodes, input, ni+1, ii+consumed, memo, out): return true
        break
      case .group(pair, children):
        if input[ii] != pair.open: break
        # ネストを数えて対応する close を探す [FF-11]
        closeIdx = findMatchingClose(input, ii, pair)
        if closeIdx == nil: break
        inner = input[ii+1 ..< closeIdx]
        if not matchAll(children, inner): break        # 子は完全一致を要求
        return matchMiddle(nodes, input, closeIdx+1, memo, out)
      case .field(ref, .volume):
        # 型付き照合: 巻数フォーマットにマッチする最長の範囲を候補にする [TY-01][SE-24]
        for cand in volumeCandidates(input, ii) sortedByLengthDesc:
            out[ref] = cand
            if matchMiddle(nodes, input, ni+1, ii+cand.length, memo, out): return true
            out[ref] = nil
        break
      case .field(ref, .enumerated(values)):
        for v in values sortedByLengthDesc:
            if input[ii...] hasPrefix v (正規化比較):
                out[ref] = v
                if matchMiddle(nodes, input, ni+1, ii+len(v), memo, out): return true
                out[ref] = nil
        break
      case .field(ref, .free):
        # 非貪欲: 短い方から伸ばす [FF-13]
        # 空マッチは許さない（少なくとも 1 文字）。ただし @ignore は空を許す。
        lower = (ref is .ignore) ? 0 : 1
        for len in lower ... (input.count - ii):
            out[ref] = input[ii ..< ii+len]
            if matchMiddle(nodes, input, ni+1, ii+len, memo, out): return true
            out[ref] = nil
        break

    memo.insert((ni, ii))
    return false
```

| # | 要件 |
|---|---|
| MT2-01 | 計算量は最悪 O(nodes × input²) だが、メモ化と「自由文字列の隣は必ず境界」の保証により、**実測 0.078 ms／件**（50 フォーマット、実ファイル名 1 万件）。目標 1ms 未満を大きく下回る [PF-05][T-05 実施済] |
| MT2-02 | 探索ノード数に上限（既定 20,000）を設け、超過した場合は「照合不能」として次のフォーマットへ進み、警告をログに出す [設計判断: 病的なフォーマットでの停止を防ぐ] |
| MT2-03 | 自由文字列フィールドの内部に区切り文字が含まれていても、両端アンカーと非貪欲探索により正しく解釈できる [TY-04] |
| MT2-04 | `.group` の子は「完全一致」を要求する。`[@labelgroup1 (@labelgroup2)]` のように入れ子になったフィールドを扱える [FF-11][FF-12] |
| MT2-05 | リテラル比較は正準形（NFC + 全角半角 + 小文字化。`CharacterCanonicalization.canonical`）を通した文字同士で行う。大文字・小文字は常に同一視する [N-02][N-04 撤回 §19.8] |

### 4.7.3 TY-02 の検証例

入力 `事件記者コナン (仮) (01) - 著者`、フォーマット `@series (@volume) - @labelgroup1`、保護文字列 `(仮)` 登録済み。

```
① マスク    → "事件記者コナン  (01) - 著者"
② 後方アンカー: " - @labelgroup1" を末尾から消費 → @labelgroup1 = "著者"
③ 後方継続: "(@volume)" を消費 → 候補 "(01)" → volume = numeric 1
④ 残り "事件記者コナン  " が @series に割り当てられる（trim 後）
⑤ 復元      → @series = "事件記者コナン (仮)"
```

保護文字列を登録していない場合でも、`(仮)` は `@volume` の型条件を満たさないため `@volume` には吸収されない [TY-01][TY-02]。ただし `@series` が自由文字列であるため `(仮)` は `@series` の一部として取り込まれ、結果は同じになる。**保護文字列が必要になるのは、`(仮)` の位置に別の自由文字列フィールドがある場合**である [9.2.3 の対比表]。

## 4.8 フォーマット群の評価 [FF-03]


**`ParsePurpose` は撤去した**（2026-09-04）。3 つの用途を分けていた唯一の理由は
`@booktype` の第 2 層——「切り出した値が**このライブラリの型名**と一致するか」の
判定——だったが、本の種別をライブラリ固有の設定から外した [TY-01] ことで
その判定ごと無くなった。**効かない引数を残すと次に読む人を誤らせる。**

```pseudo
parse(name, settings):
    masked = mask(name, settings.protectedTokens)
    for fmt in settings.filenameFormats where fmt.isEnabled sortedBy priority:
        r = match(fmt.nodes, masked.masked)
        if r == nil: continue          # 型条件を満たさない @booktype もここで落ちる
        return unmask(r, masked)
    return nil
```

### `@booktype` の照合は「語彙」で行う [TY-01、2026-09-04]

**候補はライブラリ固有の 1 値ではない。**

```
語彙 = プリセットが持つ本の種別の和集合   （library-types.json から導出）
     ∪ そのライブラリの「本の種別」フィールドに既にあるラベル
```

後者があるおかげで**利用者独自の種別も育つ**——プリセットが知らない `(自炊)` は
最初は拾えないが、そのフィールドへ手でラベルを 1 件足せば次の走査から自動で
拾える。ライブラリ固有の型名という設定を無くした代わりの逃げ道である。

**型条件そのものは残す。** 外して自由文字列にすると、プリセットの
`(@booktype) [@circle (@author)] @title …` が
`(@event) [@circle (@author)] @title …` と**先頭以外まったく同じ形**になり、
優先順位が上の前者が `(C99)` のようなイベント名まで吸う——public ゴールデン
352 件のうち **48 件でイベントが取れなくなる**ことを実測で確かめた［2026-09-04］。
フォーマットの順序では解けない（2 本が同型のため）。

```pseudo
labelsFromPath(relativePath, settings) -> [Int: [String]]:
    components = relativePath のディレクトリ部分を分解
    # ブックフォルダは階層としてカウントしない [IF-13]
    if 末尾のフォルダが isBookFolder: components.removeLast()

    out = [:]
    for (level, name) in components.enumerated(start: 1):
        switch settings.folderLevelFormats[level]:
          case .none:            continue                       # [AL-03]
          case .singleLabelGroup(g):  out[g].append(name)
          case .format(fmt):
              r = match(fmt.nodes, mask(name))
              if r == nil:
                  # AL-23: 想定した階層にフォルダがない配置ではエラーにしない。
                  #        その階層の割り当てを適用せず、素通しする
                  continue
              for (ref, v) in r.fields where ref is .labelGroup(g):
                  out[g].append(v.text)
    return out
```

### 埋め込みメタデータとの優先解決 [EM-03〜EM-05]

ファイル自身が持つメタデータ（§9.9）は**フォルダ名・ファイル名のどちらより優先する**
[EM-03]。読み取りは `QooInfrastructure` が行い、ここには結果の値型

```pseudo

    resolved = resolveLabels(file, settings)          # 上の 2 層（フォルダ名 → ファイル名）

    if metadata == nil: return resolved

    # ── フィールド単位で上書きする [EM-04]。メタデータが持たない
    #    フィールドは、下の層で得た値をそのまま残す。
    if metadata.title  is not empty: resolved.title  = metadata.title
    if metadata.series is not empty: resolved.series = metadata.series
    if metadata.volume is not nil:   resolved.volume = numeric(metadata.volume, metadata.volumeRaw)
    if metadata.authors is not empty: resolved.author = metadata.authors.joined(", ")

    # ── 意味束縛のラベルを差し替える [RW-13]。
    #    著者やシリーズをラベルグループへ流している設定では、
    #    ラベル側もメタデータ由来の値に揃わなければ食い違う。
    if settings.semanticBindings[.author] is g and metadata.authors is not empty:
        resolved.labels[g] = metadata.authors          # 複数ならその数だけラベルが付く
    if settings.semanticBindings[.series] is g and metadata.series is not empty:
        resolved.labels[g] = [metadata.series]

    return resolved
```

### 実装状況（2026-08）

**UR2-01・UR2-03・UR2-04 は実装済み**（UI は 15章 §15.6）。

- 記録は `ScanEngine.reconcile` の 1 箇所から `ManagedFileRepository.syncUnresolved`
  へ。**判定（`EmbeddedMetadataMerge.isUnresolved`）は走査と再マッチングで
  共有する** `ScanEngine.applyResolution` の中にある。
- 再マッチング [AL-34] は `ScanEngine.rematchUnresolved(libraryID:)`。
  **実ファイルを列挙し直さない**——DB の相対パスとファイル名からパースし直し、
  埋め込みメタデータは読み取り済みのキャッシュ [EM-07] を使う。フォーマットを
  1 本足すたびにライブラリ全体を歩き直すのは、ネットワーク上のライブラリでは
  費用が釣り合わない（§9.9 の実測で 5 万件が 10 分）。実体を見直したいときは
  通常の再スキャンを使う。
- UR2-02 の**通知履歴への記録**は**済**（2026-08）。自動走査では強度 4 で履歴へ落ち（割り込まない）、手動の再スキャンでは従来どおりシートに出る。導線は走査結果の
  シートに出している [15章 §15.6「入口」]。

### UR2-05「最も近いフォーマット」の推定（2026-09-01、v3 ステージ 9）

**実装済み。** `FilenameParser.attempt(_:settings:purpose:)` が `ParseAttempt`
（結果 ＋ 一致しなかったときの `NearestFormat`）を返し、`parse` と
`nearestFormat` はその上の薄い包み。走査 [AL-31] と再マッチング [AL-34] が
`unresolvedFile.nearestFormatSource` / `nearestFormatReach` へ書き、
表示は右ペイン [UR3-04]。

**推定は `parse` の副産物として求める。** 別の呼び出しにすると、未解決の多い
ライブラリ——この機能がいちばん効く場面——でパースが 2 倍になる。`parse` は
一致しなければ全フォーマットを試し終えているので、そこで拾えば追加の走査は要らない。

#### 比較は「要素数 → 位置」の順［ユーザー判断］

要件の当初の文言は「照合が最も進んだ入力位置が最大のもの」だったが、
**実測するとその指標は飽和する**（2026-09-01）——自由文字列フィールドに
入った時点で走査位置が入力の末尾へ届くため、`@title (@genre)` と
`[@circle] @title @volume` がどちらも「16/16 文字まで到達」で同点になり、
登録順で前者が勝つ（構造的には後者のほうが近い）。実質「最初の自由文字列より
前の構造が合ったか」という粗い信号にしかならない。

| キー | 何 | 備考 |
|---|---|---|
| 第一 | **満たした要素の数**（`MatchOutcome.satisfiedNodes`）| **括弧の中は数えない**（グループ全体で 1 要素）——入れ子の添字を最上位の添字と混ぜると、深い括弧を持つフォーマットが不当に有利になる。`nodes.count` と等しければ「全要素を満たしたが入力が余った」|
| 第二 | 照合が最も進んだ**原文**の位置 | マスクを原文へ写してから返す [PT-03]。保存先と表示側がマスクを知らずに使えるようにするため |
| 同点 | 登録順で先勝ち | 照合そのもの [FF-03] と同じ規則 |

#### 候補にしないもの（2 つのガード）

- **1 文字も進んでいないもの。** 「先頭のリテラルすら合わなかった」フォーマットを
  「最も近い」と名指しするのは案内ではなく雑音で、しかも全部が 0 なら登録順の
  先頭が無条件に選ばれる。**要素数だけを見てはいけない**［code-review の指摘、
  実測で確認］——先頭が弾力的空白 [WS-01] のフォーマットは、入力を 1 文字も
  消費しないまま要素数が 1 進む（`" [@circle] @title"` で `satisfiedNodes = 1,
  furthestIndex = 0`）。そのようなフォーマットが 1 本あるだけで、それが全部の
  未整理ファイルの「最も近い」になってしまう。
- **探索を打ち切ったもの** [MT2-02]。途中で止めた走査の到達点は「どこまで筋が
  通ったか」を表さない。

#### 位置は保存するが、画面には出さない［ユーザー判断］

`nearestFormatReach` は列に書くが `UnresolvedFile` には載せない——上のとおり
指標は飽和しうるので、「ここまで一致しました」と見せると**ファイル名の全部が
一致したと嘘をつく**場面がある。将来のリネーム候補提示 [PW-02] のために記録
だけしておく。

#### ゴールデンは 1 件も動いていない

パーサ本体（ゴールデンテストで固めてある中核）に手を入れたが、追加したのは
**診断情報の記録だけ**で照合の判断は変えていない。public 352 件・private
2,346 件とも変化なし、実蔵書の適合率も 成年コミック 100%（396/396）／
同人誌 99.9%（1803/1804）／同人CG 100%（146/146）で不変（2026-09-01 に測り直した）。
