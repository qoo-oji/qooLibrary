### フェーズ 1 の完了条件（DoD）

- Finder の代替として日常的に使える。ラベル機能は未実装 [20.1 完了条件]
- `FileOperationService` 以外から `FileManager` の変更系 API を呼ぶ箇所が **0**（静的検査 B-10 が緑）[FO-02][DP-05]
- Undo / Redo がすべてのファイル操作で動作する [DP-01][R-08]
- `mainContext` 共有 + バックグラウンドコンテキストの構成が確定している [DP-07]
- エラー・通知が `NotificationRouter` に一本化されている [DP-08]
- 状態の 3 分類が実装上分離されている [ST-20]
- 登録フォルダの状態がオフライン／ゴミ箱／消失を区別し、**いずれの場合も登録レコードを自動削除しない** [SB-05][R-01]（§8.7.1）
- 展開セキュリティのテストが全件パス [EX-10〜EX-24]
- `LICENSE` / `README` / `THIRD-PARTY-NOTICES.md` が LC-20〜LC-27 を満たす

### フェーズ 2 の順序に関する注意

| # | 注意点 |
|---|---|
| DP-06 | **2-1 の最初に `VersionedSchema` を導入する**。データが溜まってからの後付けは移行そのものがリスク [MG-01][MG-02][R-14] |
| DP-03 | 2-3 のパーサは UI から独立した純粋関数として早期に実装し、ゴールデンテストで固めてから UI に接続する |
| — | 2-3 / 2-4 は 2-1 / 2-2 と並行できる（`QooKit` は永続化に依存しないため）。並行実装を推奨する |
| — | 2-16 は 2-1 完了後すぐ着手してよい。MG-23 の網羅性検証を早く回すほど後戻りが小さい |
| — | **2-2 は 1-17 で確定した縮退状態（§8.7.1）を土台にする。** 1-17 は着脱検知を持たないため「ツリー更新時にマウント一覧と突き合わせる」受動的な判定に留めており、2-2 で `NSWorkspace` のボリューム通知（VD-01〜VD-06）に置き換える。状態モデルと判定順序は変えず、遷移の駆動方法だけを差し替えること |
| — | **2-2 に `transfer()` の部分成功の保持を含める。** 一括操作の途中で失敗すると、それまでに成功した `OpReceipt` を丸ごと捨てるため、実際にはファイルが移動しているのに Undo にも操作履歴にも残らない。イジェクトがこれを日常的に踏ませるため、着脱検知と同時に直す [RB-04][ER-13] |

## 17.7 推奨する実装の進め方

1. **フェーズ 0 の 0-3（サンプル収集）を今日から始める。** パーサの品質はサンプル量に比例する [MT-27]。
2. フェーズ 1 では**制約 4 つ（DP-01 / DP-05 / DP-07 / DP-08）を最優先**で入れる。機能を増やす前に骨格を正しくする。
3. フェーズ 2 は `QooKit`（2-3 / 2-4）と永続化（2-1 / 2-2）を並行させる。前者は UI なしでテストできるため、着手が早いほど検証が進む。
4. 各フェーズの DoD をチェックリストとして PR テンプレートに埋め込み、部分的な達成で次へ進まない。
5. 技術検証（T-xx）は該当フェーズの**開始時**に片付ける。設計判断が覆ると手戻りが大きい項目（T-03 / T-05 / T-13）は特に前倒しする。
