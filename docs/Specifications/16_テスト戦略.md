## 16.8 GUI を介さない実機検証 — 制御口 [MT-33]

**実機検証は GUI の自動操作（合成イベント）に頼っており、3 つの費用を払って
いた**: ①利用者の画面を数十分奪う ②人が同じマシンを触ると前提が崩れ、
崩れ方が実装の欠陥とまったく同じ形で現れる（クリックが効かない・キーが
届かない）③道具（AX ダンプ・伏字・クリック）が毎回 scratchpad で作り直しに
なる。制御口はこの 3 つとも払わずに、**本物のプロセス・本物のサンドボックス・
本物の DB・本物の配線**のまま検証するための入口。

### 成立する根拠（実測、2026-09-08）

| 測ったこと | 結果 |
|---|---|
| サンドボックスアプリがコンテナ内に Unix domain socket を作れるか | **作れる**（`bind`/`listen` とも成功、権限 0600）|
| 外部プロセスからそこへ繋げるか | **繋げる。TCC の許可は要らない** |
| ウインドウを 1 枚も開かずに起動できるか | **できる**（`defaultLaunchBehavior(.suppressed)`、macOS 15+）|
| ヘッドレスでもメニューバーが組まれるか | **組まれる。**有効/無効まで実装どおりに読める |
| プロセス内から自分へ AX で問い合わせられるか | **できる。**外部 AX と同じ品質（役割・題・値・有効/無効・選択）|
| SwiftUI のビューを `NSAccessibilityProtocol` で直に読めるか | **読めない** — 役割が `Unknown`・題が空。解決しているのは AX サーバー層なので、そこを通るしかない |

### 決めたこと

| # | 決定 | 理由 |
|---|---|---|
| CT-01 | **二重の関門**: `#if DEBUG` でリリースから丸ごと消え、さらに起動引数 `--qoo-control` が無ければ socket を 1 つも開かない | 破壊的な操作まで叩ける口なので、開いたままにしない。Release 構成に `DEBUG` が定義されないことを確認済み |
| CT-02 | **socket のパスは固定**（コンテナ内の `qoo-control.sock`）| `sockaddr_un.sun_path` は 104 バイトしかなく、外から任意のパスを受けると溢れる。サンドボックス下ではどのみちコンテナの外に bind できない |
| CT-03 | **1 接続 1 往復・改行区切りの JSON** | シェル・Python・Swift のどれからでも 3 行で叩ける |
| CT-04 | **メインへのホップは `RunLoop.main.perform(inModes: [.common])`** | `Task { @MainActor }` も `DispatchQueue.main.async` もメインキューのドレインを要するので、AppKit が入れ子のイベントループを回している間は走らない——口がいちばん要る場面で応答しなくなる |
| CT-05 | **`ax:*`（AX 系）もメインで実行する** | 同一プロセスへの AX はプロセス間のメッセージにならず**呼んだスレッドでそのまま走る**。ワーカーから押すと SwiftUI の `ButtonAction` が `MainActor.assumeIsolated` を実行して表明が破れ、`SIGTRAP` でプロセスごと落ちる［実測］ |
| CT-06 | **応答の文字列は既定で伏字**。許可語はアプリ自身の文字列カタログとプリセットの語彙から作る | 検証の道具は毎回作り直され、そのたびに許可リストを組み直しては漏らしてきた（記録に残るだけで 6 回）。**許可リストの出どころはアプリが持っている**ので、ここで作れば正確で、二度と作り直さずに済む [MT-32] |
| CT-07 | 伏字の規則は「**許可語をすべて取り除いた残りが記号・数字・空白だけなら通す**」 | 「許可語を含むか」の部分一致にすると、プリセットの語を含むだけで未知のファイル名が丸ごと素通りする［過去に実際に起きた事故］ |
| CT-08 | **名前空間の区切りにドットを使わない**（`menu:dump`）| `menu.dump` は文字列カタログの鍵とまったく同じ形で、`check-localization-keys` が「定義されていない鍵」として拾う。検査を緩めると、この配下で本物の鍵を書いたときに黙る |
| CT-09 | **同じ機能に 2 つの経路を作らない** | `NSAccessibilityProtocol` を直に読む経路も一度書いたが、AX 経由に劣るので削除した。残すと次に触る人が弱い方を使う |
| CT-10 | **右クリックはプロセス内から `NSView.menu(for:)` で組み立てる** | 外部の AX クライアントからは見えないが、**内からは取れる**［実測、2026-09-08］。SwiftUI の `.contextMenu` は最終的にこの API へ橋渡しされる。これで**破壊的操作のほぼ全部の入口**（登録解除・ラベルの付け外し・保管庫へ移動・重複を比較・以後無視する）が GUI 無しで通る |
| CT-11 | 右クリックの対象は**AX の要素で指す**（座標は補助）| 一覧の行位置は項目の増減・スクロール・並べ替えで動くので、座標を控えると次に押したときには別の行を指す［記録済みの教訓］ |
| CT-12 | **1 回に 1 点だけ**組み立てる | 点ごとに SwiftUI がメニューを組み立てるので、約 12,500 点を走査したところ AttributeGraph が枯渇して異常終了した［実測］。格子状に舐めない |
| CT-13 | **メニューの題も伏字を通す** | メニューの題は静的とは限らない——Undo の題（「「作品名A」を移動を取り消す」）や「(名前)に展開」には**利用者のファイル名がそのまま入る**。ウインドウの題（＝現在のフォルダ名）とホームパス（＝利用者名）も同じ。**初版はこの 3 つとも素通しだった** |
| CT-14 | **DB は読み取り専用**。書き込みの口は作らない | `read { }` は SQLite の読み取りトランザクションなので、書き換えはエンジン自身が拒む——検査を書く必要が無く、うっかり書ける経路も生えない。**状態を変える検証は本物の操作を通す**——口から直に書けると「アプリを経ずに作った状態」で検証したことになる |
| CT-15 | **時間のかかる操作は待たずに返す。終わったかは `progress:list` で見る** | 口の応答はメインへホップして作る [CT-04] ので、待つとその間メインを塞ぐ。走査の完了は進捗の受け皿（本物の `OperationProgressCenter`）を見て判断する |
| CT-16 | **アプリ層が足したコマンドだけは `Task` を挟む** | `RegisteredFolderStore` は `actor` なので `await` が避けられない。そのぶん AppKit が入れ子のイベントループを回している間は応答せず、上限時間で失敗として返る。ここへ足すのは、そういう場面で叩かない類の操作に限ること |
| CT-17 | **既定では前面化しない。`{"activate": true}` で選ばせる** | 口の存在理由は利用者の画面を奪わないこと。ただし `@FocusedValue` を見るメニューの有効/無効を読むには前面化が要る（下記）——奪うなら呼ぶ側が承知して呼ぶ形にする |
| CT-18 | **メニューバーを押す前に `update()` で実体化する。しかもランループを 1 周挟む** | SwiftUI が組むサブメニューは、項目が見えていても押して何も起きないことがある［実測］。`menu:dump` を先に走らせると通る——`Scripts/qooctl` の `menu:invoke` はそのために 2 呼び出しに分けている |
| CT-19 | **`ax:dump` はアプリ要素の下へ降りない（根だけは 1 段降りる）** | `kAXWindowsAttribute` は役割が `AXApplication` の疑似ウインドウを返すことがあり、それは**自分自身を子として持つ**。素直に降りると `Application → Application → …` がメニューバーごと枝分かれしながら深さぶん増え、**読むだけの口がメインスレッドを数十秒止める**［実測 2026-09-08、2 度踏んだ］。**ウインドウ一覧を役割で絞ってはいけない**——`AXWindow` だけにしたら本物のウインドウまで消えた（AX のウインドウ一覧は当てにならない）|
| CT-20 | **走査したノード数に上限（20,000）を置き、打ち切ったら `truncated` を返す** | 深さだけでは止められない（枝の数が掛け算で効く）。黙って途中で止めると「要素が無い」と読まれる |

### これで置き換わるもの・残るもの

| 分類 | 口で取れるか |
|---|---|
| DB・ファイルシステムの状態 | ○（実アプリの本物） |
| 判定（メニューやボタンの有効/無効、既定値の推定） | ○ |
| 文言（画面に出る文字列） | ○ |
| メニュー経由の操作 → 効果 | ○ |
| ウインドウ内のボタン・入力欄 → 効果 | ○ |
| モーダルのダイアログ | ○（**外部 AX では見えなかったもの**）|
| 起動シーケンス・移行・サンドボックス下の実挙動 | ○ |
| **右クリック（コンテキストメニュー）** | **○** [CT-10]（外部 AX からは見えないが、プロセス内からは取れる）|
| **一覧の行の選択（複数選択を含む）** | ○ `ax:select` |
| **DB の中身** | ○ `db:query` / `db:counts`（外から `sqlite3 -readonly` でコンテナを読めないことがある壁が消える）|
| **ライブラリの登録・走査・解除** | ○ `library:*`（**`NSOpenPanel` の壁が消える**——パネルが担うのは「どのフォルダか」を決めることだけ）|
| **走っている処理・その完了** | ○ `progress:list` |
| メニューの有効/無効のうち `@FocusedValue` を見るもの | △ 前面化が要る [CT-17]。しかも**アプリを切り替えて戻ると nil になる**（SwiftUI の既知の不具合）——読めないときは `ctx:*` と `ax:press` で代替する |
| 見た目（色・レイアウト・はみ出し）| ×（画素を測るには画面が要る）|
| ドラッグ＆ドロップ | × |

### 使い方

```sh
Scripts/qooctl launch                 # ウインドウを 1 枚も出さずに起動
Scripts/qooctl counts                 # DB の全テーブルの行数
Scripts/qooctl library:register '{"path":"/Volumes/X/蔵書","template":"builtin.general-comic"}'
Scripts/qooctl wait                   # 走査が終わるまで待つ
Scripts/qooctl ctx 第01巻              # 行を右クリックしたときのメニュー
Scripts/qooctl ctx:invoke '{"title":"第01巻","path":["保管庫に移動"]}'
Scripts/qooctl db:query '{"sql":"SELECT relativePath, isArchived FROM managedFile"}'
Scripts/qooctl library:unregister '{"name":"蔵書"}'
Scripts/qooctl quit
```

**この一続きが、実機検証 1 回分そのものである**——使い捨てボリュームを作って
合成名を置く（シェル）以外に、画面へ触れる操作が 1 つも無い。

**プリセットの `key` は `builtin.general-comic` / `builtin.adult-comic` /
`builtin.doujinshi` / `builtin.doujin-cg` の 4 つ**（`library:list` が返す）。
`"template"` を省くか `"custom"` にすると白紙から登録する。

**合成名を読みたいときは `{"allow": ["作品名A", ...]}` で通す** — 既定では
伏字になる。**socket ファイルの有無で生存を判定しない**（アプリが落ちても
残る。`ping` で確かめる）。

## 16.9 アプリ層をテストできるようにする — `QooUI` [MT-33]

**アプリターゲット（`qooLibraryApp`）はテストターゲットを 1 つも持てない**
——Xcode のターゲットであって SwiftPM のパッケージではないため。そこに
33,574 行（133 ファイル）の判定・状態機械が溜まり、**実機で GUI を操作しな
ければ検証できない**状態が続いていた。過去の実装記録に繰り返し現れる
「判定を `QooApplication` へ切り出した（View に書いたままではテストで固定
できない）」は、その場しのぎの対処だった。

### 何が根拠になったか（実測）

**SwiftUI／AppKit に依存するコードは `swift test` から普通に走る。**
`LocalizedStringKey` を返す関数も、`NSRunningApplication` を触る関数も、
`ImageRenderer` で View を実際に描いて寸法を得ることさえできる——
**画面を 1 枚も出さずに**。「UI のコードはテストできない」という前提が
そもそも成り立っていなかった。

### 置き場所の規則

```
qooLibraryApp（View と描画）→ QooUI（画面が何をするか）→ QooApplication → …
```

| ここに置く | ここに置かない |
|---|---|
| 状態機械（`WindowState` の履歴・タブ・入口の追跡）| SwiftUI の `View` |
| メニューの出し分け（`*MenuActions`）| 描画・レイアウト |
| 場所の解決（`StandardLocations`・`FavoriteLocations`）| AppKit のブリッジのうち、View の一部であるもの |
| 制御口 [§16.8] | |

**`Sources/QooUI` に View を置けない**ことは
`Scripts/check-layer-dependencies.swift` が機械的に守る（`some View` と
`: View` の宣言を見る。変異で落ちることを確認済み）。境目を人の記憶に委ねると、
**何をテストできるのかが読めなくなる**。

### 移す順序

**モジュールを分けると `internal` が見えなくなる**ので、実際の作業量は
「移すこと」ではなく「View 側から使うものを `public` にすること」。移す集合を
機械的に測ったところ、View を含まない 48 ファイルのうち **36 ファイル
（約 4,600 行）はコード上 View 側の型に依存していない**（残り 12 は
`DialogWindowPresenter` や `FolderEntry` を使う）。判定の濃い種から閉包を
取ると **18 ファイル・2,976 行**にまとまる。

- **第 1 弾（済）**: `Control/`（口の拡張後は約 1,300 行）。経路
  （`Package.swift`・`project.yml`・テストターゲット・静的検査）を確立するのが
  目的だった。**`swift test` から `NSMenu` を組み立てて走査・照合・押下まで
  固定できている**（`ControlMenuTreeTests`）——`performActionForItem` は
  `NSApplication.sendAction` を通るので、テストでは `NSApplication.shared` に
  触れて `NSApp` を用意しておく必要がある［実測］。
- **第 2 弾（未）**: `WindowState`（904 行）を中心とする残り。`WindowState` は
  View から使われるメンバが多く、公開面がそのまま作業量になる。
