## 13.2 ラベル配色 [8.1 節 配色要件]

**既定色は 10 色のリテラル配列ではなく、色相環を N 等分して生成するアルゴリズムとして実装する** [MT-13][CO-01]。

```swift
public enum LabelPalette {
    /// グループ数 N に応じた既定色を生成する。 [MT-13]
    /// - light: HSV(S: 0.20, V: 0.90) [CO-02]
    /// - dark : HSV(S: 0.35, V: 0.40) [CO-07]
    public static func defaultColors(count n: Int, appearance: Appearance) -> [String]

    /// 背景の相対輝度から黒／白のコントラストが高い方を返す。 [CO-05]
    public static func foreground(on background: String) -> ForegroundChoice

    /// WCAG の相対輝度。単体テスト必須。 [CO-03][CO-05]
    public static func relativeLuminance(_ hex: String) -> Double
    public static func contrastRatio(_ a: String, _ b: String) -> Double
}

public enum ForegroundChoice: Sendable {
    case black(ratio: Double)
    case white(ratio: Double)
    case insufficient(bestRatio: Double)   // 4.5:1 未満 → 警告アイコン [CO-05]
}
```

```pseudo
defaultColors(n, .light):
    for i in 0..<n:
        hue = 360.0 * Double(i) / Double(n)           # 色相環を N 等分 [MT-13][CO-01]
        s, v = 0.20, 0.90                             # [CO-02] 彩度15〜25%, 明度85〜92%
        hex = hsvToHex(hue, s, v)
        assert contrastRatio(hex, black) >= 4.5       # [CO-03] 自動検証
```

要件定義書 8.1 節の 10 色表は「アルゴリズム生成の結果例」として扱い、`Tests/LabelPaletteTests` で n=10 のときに近い色相配置になること、および全色で黒とのコントラスト比 4.5 以上を検証する [CO-03][MT-13]。

|---|---|

| CO2-02 | ラベルの既定色は所属グループと同色。個別変更可 [CO-06] |
| CO2-03 | 背景色に対するフォント色は自動調整。4.5:1 未満なら警告アイコン [CO-05] |

## 13.4 エラー提示の実装 [13.1 節]

`NotificationSeverity` から提示手段への写像は 1 箇所に閉じる。

```swift
@MainActor
extension NotificationRouter {
    func presentationStyle(for s: NotificationSeverity) -> PresentationStyle {
        switch s {
        case .appModal:  return .alert                       // 続行不可のみ [ER-02]
        case .sheet:     return .sheet(attachedToWindow: true)
        case .inline:    return .inline
        case .transient: return .toast(duration: 4)
        case .logOnly:   return .none
        }
    }
}
```

| 強度 | 使用条件 | 実装 |
|---|---|---|
| 1 | 続行不可（DB 破損、移行失敗、フルディスクアクセス未付与）[ER-02] | `NSAlert` 相当のアプリモーダル |
| 2 | 判断が必要（名前の衝突、破壊的操作の確認、Undo 不可の警告）| `.sheet` |
| 3 | 一覧の行やフィールドとして特定できる（衝突行 CW-13、未変換行 CW-12、ペンディング理由 MV-19）| 行内バッジ + ツールチップ |
| 4 | 直接結果かつ判断不要（完了報告、軽微な失敗、結果サマリ導線）| ステータスバー／トースト |
| 5 | 自動回復した事象、診断目的 | ログのみ |

| # | 要件 |
|---|---|
| ER2-01 | 機能ごとに独自の提示方法を作らない [ER-01] |
| ER2-02 | メッセージは「何が起きたか」「なぜ」「次に何ができるか」の 3 要素。技術詳細は折りたたむ [ER-03] |
| ER2-03 | 無言で握りつぶさない。ただし強度 5 で足りる事象まで通知しない [ER-04][RB-01] |
| ER2-04 | 強度 4 以上をすべて通知履歴に記録 [ER-05][NT-01] |
| ER2-05 | バックグラウンド処理のエラーは強度 4 以下に留め、作業を中断させない [ER-20][ER-21] |

## 13.6 キーバインド [7.4 節]

`QooKit` は Foundation 以外に依存できない [A-01] ため、`SwiftUI.KeyboardShortcut`
を直接保持することはできない。代わりに QooKit 内で完結する `KeyCombo`
（キー1つ + 修飾キーの組み合わせのみを表す最小限の値型）を定義し、
`SwiftUI.KeyboardShortcut` への変換は View 層（`qooLibraryApp`）でのみ行う
[設計判断、A-01 との整合]。

```swift
// QooKit
public struct KeyModifiers: OptionSet, Sendable, Codable, Equatable {
    public let rawValue: UInt8
    public static let command = KeyModifiers(rawValue: 1 << 0)
    public static let shift = KeyModifiers(rawValue: 1 << 1)
    public static let option = KeyModifiers(rawValue: 1 << 2)
    public static let control = KeyModifiers(rawValue: 1 << 3)
}

/// 単一文字（"r"）または記号キー名（"return"/"space"/"delete"/
/// "up"/"down"/"left"/"right"/"escape"/"tab"）のいずれか。
public struct KeyCombo: Sendable, Codable, Equatable {
    public let key: String
    public let modifiers: KeyModifiers
}

public struct KeyBinding: Sendable, Codable, Identifiable, Equatable {
    public let id: ActionID
    public var combos: [KeyCombo]              // 空配列 = 未割り当て
    public let isDestructive: Bool             // 完全削除など
}

public protocol KeyBindingStore: Sendable {
    func binding(for: ActionID) -> KeyBinding
    func setBinding(_ combos: [KeyCombo], for: ActionID) throws  // [KB-01]
    func conflicts(of combo: KeyCombo) -> [ActionID]             // [KB-04]
    func resetToDefaults()                                       // [KB-05]
}
```

1つの操作に複数のキーの組み合わせを割り当てられる（`combos` は配列）。実運用
では「戻る／進む」を Finder 流の `⌘[`/`⌘]` とブラウザ流の `⌘←`/`⌘→` の
両方で使いたい、という要望から導入した設計判断。他の操作は既定では
1つのキーしか持たないが、型としてはどの操作にも複数割り当てられる。

View 層は `KeyCombo` を `SwiftUI.KeyboardShortcut`（`KeyEquivalent` +
`EventModifiers`）に変換してから `.keyboardShortcut(_:modifiers:)` へ渡す。

### マウス／トラックパッドによる戻る・進む（実装済み）

要件定義書 v2.8 には無い項目（1-8 の実機検証時にユーザーから要望があり、
「将来検討」として記録していたものを 1-9 完了後に実装した。正式な要件 ID は
要件定義書改訂時に振る）。実装詳細・根本原因の調査記録は CLAUDE.md「1-8」
節の「マウスのサイドボタン・トラックパッドのスワイプによる戻る/進むを実装
した」を参照。

- **マウスのサイドボタン**（ボタン3＝戻る／ボタン4＝進む）と**トラックパッド
  の2本指/3本指スワイプ**の両方に対応。`WindowState.goBack()`/`goForward()`
  （1-8 で実装済み）をそのまま呼ぶ。
- 2本指の横スワイプを戻る/進むと通常の横スクロールのどちらに使うかは
  ユーザーが選べる（`twoFingerSwipeForNavigation`、既定は戻る/進む）。
  スクロールを選んだ場合は3本指スワイプが戻る/進むの手段になる。
- **フォローアップ（1-12 環境設定で対応すること）**: 上記の切替設定は
  現状コンテキストメニューに暫定配置しており、環境設定 UI へ移すこと。
  あわせて、戻る/進むの左右（スワイプ方向）を入れ替えられる設定も
  環境設定に追加すること（未実装）。

**⌥ による項目の入れ替えは行わない（実装不能）** [1-14 で実測確認]。Finder は ⌥ 押下中だけ「ゴミ箱に入れる」→「すぐに削除…」、「コピー」→「パス名をコピー」のように項目を差し替えるが、AppKit の `NSMenuItem.isAlternate` に相当する API は SwiftUI に無い。加えて、**SwiftUI はメニューの内容を初回表示時に構築してキャッシュし、2 回目以降は `body` を再評価しない**ことを最小の検証アプリで実測した（同じ右クリックを ⌥ なし → ⌥ ありで繰り返しても body の評価は 1 回だけ）。そのため `NSEvent.modifierFlags` を読む機会自体が存在しない。該当する項目（パスをコピー [FM-10]・完全削除 [FM-14]）は「その他 ▸」サブメニューへ退避する [ユーザー判断、8章 §8.5 PD-15]。
