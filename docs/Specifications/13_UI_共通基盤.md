## 13.2 ラベル配色 [8.1 節 配色要件]

**既定色は 10 色のリテラル配列ではなく、色相環を N 等分して生成するアルゴリズムとして実装する** [MT-13][CO-01]。

```swift
public enum LabelPalette {
    /// グループ数 N に応じた既定色を生成する。 [MT-13]
    /// - light: HSV(S: 0.20, V: 0.90) [CO-02]
    /// - dark : HSV(S: 0.35, V: 0.40) [CO-07]
    public static func defaultColors(count n: Int, appearance: Appearance) -> [String]

    /// 背景の相対輝度から黒／白のコントラストが高い方を返す。 [CO-05]
    public static func foreground(on background: String) -> ForegroundChoice

    /// WCAG の相対輝度。単体テスト必須。 [CO-03][CO-05]
    public static func relativeLuminance(_ hex: String) -> Double
    public static func contrastRatio(_ a: String, _ b: String) -> Double
}

public enum ForegroundChoice: Sendable {
    case black(ratio: Double)
    case white(ratio: Double)
    case insufficient(bestRatio: Double)   // 4.5:1 未満 → 警告アイコン [CO-05]
}
```

```pseudo
defaultColors(n, .light):
    for i in 0..<n:
        hue = 360.0 * Double(i) / Double(n)           # 色相環を N 等分 [MT-13][CO-01]
        s, v = 0.20, 0.90                             # [CO-02] 彩度15〜25%, 明度85〜92%
        hex = hsvToHex(hue, s, v)
        assert contrastRatio(hex, black) >= 4.5       # [CO-03] 自動検証
```

要件定義書 8.1 節の 10 色表は「アルゴリズム生成の結果例」として扱い、`Tests/LabelPaletteTests` で n=10 のときに近い色相配置になること、および全色で黒とのコントラスト比 4.5 以上を検証する [CO-03][MT-13]。

## 13.4 エラー提示の実装 [13.1 節]

`NotificationSeverity` から提示手段への写像は 1 箇所に閉じる。

```swift
@MainActor
extension NotificationRouter {
    func presentationStyle(for s: NotificationSeverity) -> PresentationStyle {
        switch s {
        case .appModal:  return .alert                       // 続行不可のみ [ER-02]
        case .sheet:     return .sheet(attachedToWindow: true)
        case .inline:    return .inline
        case .transient: return .toast(duration: 4)
        case .logOnly:   return .none
        }
    }
}
```

| 強度 | 使用条件 | 実装 |
|---|---|---|
| 1 | 続行不可（DB 破損、移行失敗、フルディスクアクセス未付与）[ER-02] | `NSAlert` 相当のアプリモーダル |
| 2 | 判断が必要（名前の衝突、破壊的操作の確認、Undo 不可の警告）| `.sheet` |
| 3 | 一覧の行やフィールドとして特定できる（衝突行 CW-13、未変換行 CW-12、ペンディング理由 MV-19）| 行内バッジ + ツールチップ |
| 4 | 直接結果かつ判断不要（完了報告、軽微な失敗、結果サマリ導線）| ステータスバー／トースト |
| 5 | 自動回復した事象、診断目的 | ログのみ |

## 13.6 キーバインド [7.4 節]

`QooKit` は Foundation 以外に依存できない [A-01] ため、`SwiftUI.KeyboardShortcut`
を直接保持することはできない。代わりに QooKit 内で完結する `KeyCombo`
（キー1つ + 修飾キーの組み合わせのみを表す最小限の値型）を定義し、
`SwiftUI.KeyboardShortcut` への変換は View 層（`qooLibraryApp`）でのみ行う
[設計判断、A-01 との整合]。

```swift
// QooKit
public struct KeyModifiers: OptionSet, Sendable, Codable, Equatable {
    public let rawValue: UInt8
    public static let command = KeyModifiers(rawValue: 1 << 0)
    public static let shift = KeyModifiers(rawValue: 1 << 1)
    public static let option = KeyModifiers(rawValue: 1 << 2)
    public static let control = KeyModifiers(rawValue: 1 << 3)
}

/// 単一文字（"r"）または記号キー名（"return"/"space"/"delete"/
/// "up"/"down"/"left"/"right"/"escape"/"tab"）のいずれか。
public struct KeyCombo: Sendable, Codable, Equatable {
    public let key: String
    public let modifiers: KeyModifiers
}

public struct KeyBinding: Sendable, Codable, Identifiable, Equatable {
    public let id: ActionID
    public var combos: [KeyCombo]              // 空配列 = 未割り当て
    public let isDestructive: Bool             // 完全削除など
}

public protocol KeyBindingStore: Sendable {
    func binding(for: ActionID) -> KeyBinding
    func setBinding(_ combos: [KeyCombo], for: ActionID) throws  // [KB-01]
    func conflicts(of combo: KeyCombo) -> [ActionID]             // [KB-04]
    func resetToDefaults()                                       // [KB-05]
}
```

1つの操作に複数のキーの組み合わせを割り当てられる（`combos` は配列）。実運用
では「戻る／進む」を Finder 流の `⌘[`/`⌘]` とブラウザ流の `⌘←`/`⌘→` の
両方で使いたい、という要望から導入した設計判断。他の操作は既定では
1つのキーしか持たないが、型としてはどの操作にも複数割り当てられる。

View 層は `KeyCombo` を `SwiftUI.KeyboardShortcut`（`KeyEquivalent` +
`EventModifiers`）に変換してから `.keyboardShortcut(_:modifiers:)` へ渡す。

### 13.7.1 ⌥ による項目の入れ替え（Finder 準拠）

Finder は ⌥ 押下中だけ「ゴミ箱に入れる」→「すぐに削除…」のように項目を差し替える。**これは `View.modifierKeyAlternate(_:_:)`（macOS 15.0+、macOS 専用）で実装する。**

```swift
Button("action.copy") { copy(targets) }
    .modifierKeyAlternate(.option) {
        Button("folder.copyPath") { copyPaths(targets) }   // [FM-10]
    }
```

**[訂正] 1-14 の時点では「SwiftUI では実装不能」と記載していたが、これは誤りだった。** 当時は「⌥ の押下を検知してメニュー内容を作り直す」方向で調べ、「メニュー内容は初回表示時に構築されて以後 `body` が再評価されない」ことを実測して不能と結論した。その実測自体は正しいが、**再評価は最初から不要**である — SwiftUI は両方の項目を含む `NSMenu` を一度だけ作り、代替側に `NSMenuItem.isAlternate` を立てる。**入れ替えは AppKit が表示時に行う**（Finder 自身と同じ仕組み）。前提が誤っていたために正しい API に届かなかった。

実測で確認済みの性質（生成された `NSMenu` を直接ダンプして検証）:

- `.contextMenu` / `Table` の `.contextMenu(forSelectionType:)` / `LazyVGrid` セル / `Menu`（サブメニュー）/ メニューバーの `.commands` の**すべてで機能する**。`Menu` 自体に付ければサブメニューごと入れ替わる。
- 代替項目のキー等価は入力不能な `U+0000` になり、修飾キーマスクだけが設定される。**意図しないキーボードショートカットは生えない**（[FM-16]「完全削除に既定のキーバインドを割り当てない」と矛盾しない）。
- 代替ビルダーが空（条件が偽）のときは**代替項目自体が作られず、主項目がそのまま残る**。条件付きで代替を出す場合はこれに依存してよい。
- **代替は「基底と同じキー等価を持ち、修飾マスクだけが違う」ときにだけ現れる**［実測。実機で踏んで発覚］。代替側に基底と違うキー（例: 基底 ⇧⌘H に対して ⇧⌘L）を `.keyboardShortcut` で与えると、AppKit が組と見なさず**⌥ を押しても一生出てこない**。`modifierKeyAlternate` は基底のキー等価を引き継いで修飾だけ足すので、**代替側に別のキーを付けないこと**が条件になる。1 つの基底に ⌥ と ⌃ の代替を 2 つぶら下げるのも、3 つが同じキー等価を共有していれば機能する（`.modifierKeyAlternate` は連鎖できる）。
- **メニュー項目の実際のキー等価・修飾マスクは、実行中のアプリに AX で問い合わせて確かめられる**（`AXMenuItemCmdChar` / `AXMenuItemCmdModifiers` / `AXMenuItemCmdVirtualKey`）。同じ手順を Finder に対して行えば、Finder が実際に何を設定しているかと直接突き合わせられる。ただし矢印キーの項目は `AXMenuItemCmdChar` が空・修飾マスクの報告も当てにならない（`AXMenuItemCmdVirtualKey` のほうを見る）。

**コンテキストメニューでは条件を満たさない代替を「出さない」、メニューバーでは「無効にする」**。メニューバーで項目の有無を `@FocusedValue` に依存させると、フォーカス中のウインドウが値を公開していない起動直後などに項目が消える（実測）。`@AppStorage` を `if` 条件で読む回避策は、Observation が無限に再評価してハングする既知の不具合（§13.7 タブバーの事例）を踏むため採れない。

実装している対応関係と、Finder にあって対応しなかった項目の理由は CLAUDE.md「Finder の ⌥ 代替項目」節にまとめてある。

### 13.7.2 「移動」メニューの Finder 準拠 [ユーザー要望]

Finder の `MenuBar.nib` を `NSNib` で実体化して全 25 項目（タイトル・SF Symbol・
キー・`isAlternate`・セレクタ）を読み出し、1 項目ずつ突き合わせて構成した。

無いグループはサブメニュー自体を出さない。

**「ホーム」は実ホームを指す**［ユーザー判断］。以前は仮想ホーム（サンドボックス
コンテナ）だったが、標準の場所を並べるにあたり「ホームの中の書類」と
「移動 > 書類」が別の場所を指す矛盾が生じるため統一した。仮想ホームの中身は
実ホームとほぼ同じ（Desktop/Downloads/Movies/Music/Pictures はいずれも実物への
シンボリックリンク）で、実際に違うのはコンテナ専用の Documents と Library だけ
——どちらもアプリの内部実装領域なので失うものは無い。起動時フォルダ設定の
「ホーム」も同じ意味に揃えてあり、**実ホームが読めないときだけ仮想ホームへ
落ちる**（`StandardLocation.defaultHome`）。

#### アクセスの求め方

未許可の場所を選んだときは**その場で `NSOpenPanel` を出し、1 回だけ許可を求める**
［ユーザー判断］。フォルダツリーの `AccessDeniedRow` が環境設定「アクセス権」
タブへ**誘導**するのとは意図的に変えている——あちらは「アクセス権がありません」
という状態表示に添えたボタンだが、こちらは「書類へ行きたい」という明示的な
要求の直後なので、環境設定が開くのは遠回りになる。許可した結果はどちらも
`VolumeAccessStore` に入り「アクセス権」タブに現れるため、一元管理は保たれる。

**実際に読めるかどうかは試さない**［設計判断］。TCC 保護フォルダに触ること自体が
ダイアログの引き金になり得るため、「触らずに分かる材料」＝自分が持っている許可
だけで判定する（`VolumeAccessStore.hasGrant(covering:requiringExactMatch:)`）。
判定が保守的に外れた場合の害は「一度だけ余分にパネルが出る」ことに留まり、
逆向きの誤り（本来出すべきパネルを出さない）よりはるかに軽い。

どの場所に何が要るかは 1 章 §1.4 の実測表（B-24〜B-27）が根拠。

**移動メニューを経由しない到達にも同じ導線を出す。** ツリーのクリック・中央ペインの
ダブルクリックで潜った場合は上の事前判定が働かないため、**実際に読み込みに失敗した
1 箇所**（`FolderContentView` の `loadError`）から `StandardLocationOpener.requestAccess`
へ繋ぐ。発生源ごとに手当てせず、失敗した側から拾うことで経路によらず成立する
（`WindowState.relocateCurrentTabIfFolderVanished()` と同じ考え方）。**権限エラーの
ときだけ**出すこと——消えている・壊れている失敗と区別しないと、実体の無いフォルダで
許可パネルを勧めてしまう（判定は `NSFileReadNoPermissionError` / POSIX の
`EACCES`・`EPERM`、`NSUnderlyingErrorKey` の入れ子も辿る）。

### 13.7.3 「サーバへ接続…」（⌘K）— 実装しないと決定［ユーザー判断］

**App Sandbox は既定で `NetFSMountURLSync` を拒否する**（実測: `rc=1` EPERM を
0.00 秒で返す。非サンドボックスでは `rc=65` EHOSTUNREACH まで進み、実際に接続を
試みている）。`com.apple.security.network.client` を追加すると通ることも実測済み
（`com.apple.security.temporary-exception.mach-lookup.global-name` は不要）。

つまり実装には**ネットワーク entitlement の追加が必須**で、これは §9 の
「ネットワーク通信を実装しない [SC-01][LG2-08]」に直接触れる。**技術的には可能だが
実装しない**と決めた——共有のマウントは Finder に任せ、qooLibrary は 1-16b で
対応済みの「マウント済みボリュームを扱う」役割に留める。

**判断の経緯を残す理由**: ユーザーは当初「実装する」と回答していたが、それは
entitlement が要ると分かる前の判断だった。**手段が禁止事項に触れると判明した
時点で承認を取り直した**結果この決定になっている。再検討するときは、必要なのは
`network.client` 1 つだけ（一時例外は不要）という実測から始めてよい。
